## 1 设计文档里真实有的东西（重读后）

### 1.1 三层采集入口（`docs/04 §3.5`，原文 L522-534）

| 入口 | 机制 | 产出 | M1 状态 |
|---|---|---|:--:|
| **A. MCP 主动写** | agent 自己调 `memory_write` | L1 原子记忆 | ✅ 已实现 |
| **B. Proxy 旁路采集** | 对话经 proxy 转发时，**把 round 追加到 `l0`（原始对话）** | **L0** | ❌ M3 |
| **C. Hook 采集** | 生命周期钩子触发抽取 | **L0 → L1** | ❌ M3 |

**设计明确写了**（L532）：
> "**采集与写入分离**：采集只产出 `l0` 原始对话（append-only），抽取是异步批处理；
> **抽取失败可以重放 `l0`**。"

**⇒ 这就是业界的 L0 层，设计早就有了。**

### 1.2 设计里**确实没有**的（真缺口）

| 项 | 状态 |
|---|---|
| **L2 场景块**（按项目/主题聚合） | ❌ 只在 `§5` L658 提了一句"先给 L3/L2 摘要"，**没有数据模型、没有表** |
| **L3 Persona**（用户画像） | ❌ 同上，只有一句提及 |

**但 L2/L3 是有意取舍还是遗漏？** 看 §1.4 的"自研边界"：

> "自研边界因此收敛为：**存储引擎不造**（SQLite + 三通道 + 单写队列），
> 自研集中在**采集适配 / 写入入口的 agent 身份必填 / 中文检索 / 去重与冲突 / 操作台 GUI**。"

**⇒ 设计把精力放在"别人做不好的地方"（多 agent 身份、中文检索、冲突、GUI），
而不是复刻 TencentDB 的四层。这是合理的取舍，不是遗漏。**

## 2 修正后的判断

### 2.1 不需要新增"L0 导入"任务

**为什么**：
- L0 的设计**已经存在**（§3.5 的 B/C 采集）；
- 它是 **M3** 的任务（原计划就是）；
- 我建议的"读 agent 会话文件"其实是 **C. Hook 采集**的变体，**重复设计已有内容**。

**唯一值得补充的**：设计里 B/C 都依赖 hook/proxy，而 **WorkBuddy 没有 hook**（我们实测过）。
所以 WorkBuddy 的 L0 只能**读它的会话文件**（`projects/*/*.jsonl`）——
这是对 §3.5 的一个**补充**，不是新建一层。

### 2.2 L2/L3 要不要做？——**做 L2，不做 L3**

| 项 | 判断 | 理由 |
|---|:--:|---|
| **L2 场景块** | ✅ **建议做**（M3） | 用户的真实需求是"关于某项目的所有事"；`edges` 图关系不等于场景聚合；而且 M2-03「图谱」**没有 L2 就是无源之水** |
| **L3 Persona** | ❌ **不做** | 三个 agent 各有一份画像（WorkBuddy `memory/<uid>_memory.md` V154、DSH mnemon、Hermes USER.md），Orbital 再造一份会矛盾；**值得做的是"跨 agent 画像对照"**（只有 Orbital 能做） |

**⇒ 关于 M2 的建议修正**：
- **T-M2-03 图谱 → 改为"场景视图"仍然成立**（但理由是"图谱需要聚合基础"，不是"L2 缺失"）
- **不需要新增 T-M2-06**（我之前提的 L0 导入与 M3 的采集层重复）
