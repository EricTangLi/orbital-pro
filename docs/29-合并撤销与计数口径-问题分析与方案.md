## 1 F1a：为什么"合并后边消失"不是缺陷

`merge_inner` 的边处理（`service.rs:2769-2832`）：

1. 取 `drop` 的全部边（作为 source 或 target）
2. 把指向 `drop` 的端点改指 `keep`（`new_src` / `new_tgt`）
3. **若改指后 `new_src == new_tgt` → 判为自环，丢弃**（`:2810-2813`，注释在 `:2770`：「自环对图遍历毫无信息量，留着只会让 related 自指」）
4. 否则 `INSERT OR IGNORE` 写新边

我实测的场景：`J4 建的边是 keep→drop`（a9ac→ab18），合并后变 `keep→keep` → 自环 → 丢弃，`edges_moved: []`。**这是预期行为**。

而且 `undo_merge` 有专门一段恢复它（`:3013-3023`「被当自环丢掉的那些边，原样恢复」）。
⇒ **F1a 撤销，我的原判断作废。**

## 2 F1b：真 bug —— 撤销会删掉 keep 原有的边

### 2.1 机制（读码）

`merge_inner`（`:2799-2832`）：

```rust
tx.execute("DELETE FROM edges WHERE source_id=? AND target_id=? AND edge_type=?", ...)?; // 删 drop 的旧边
if new_src == new_tgt { self_loops.push(e); continue; }
tx.execute("INSERT OR IGNORE INTO edges ...", ...)?;      // ← 可能被忽略，但没看返回值
moved_edges.push(json!({ "old": e, "new": {..} }));        // ← 无条件记录
```

`undo_merge`（`:2984-3012`）：

```rust
for e in detail["edges_moved"].as_array() {
    DELETE FROM edges WHERE source_id=new AND target_id=new AND edge_type=new;  // ← 无条件删
    INSERT OR REPLACE ... old;
}
```

**触发条件**：`keep` 与 `drop` 都有**指向同一第三方、同 `edge_type`** 的边。

- merge 时 `INSERT OR IGNORE` 因为 keep 已有同 key 边而被忽略 → keep 原边保留（这一步是对的）
- 但 `moved_edges` 仍记了这条"新边"
- undo 时无条件 `DELETE` 这条"新边" → **删掉的是 keep 的原有边**，随后只 `INSERT` 回 drop 的旧边
- 结果：**keep 原有的边永久丢失**

### 2.2 SQL 层模拟（副本库实测）

```
A(keep) / B(drop) / C(target) 三条真实记忆
[初始]        A→C semantic 0.5   B→C semantic 1.0
[merge 之后]  A→C semantic 0.5                     ← INSERT OR IGNORE 忽略，keep 原边保留（正确）
[undo 之后]                      B→C semantic 1.0  ← A→C 消失（错误）
判定：A→C（keep 原有边）undo 后 **消失了（丢边）**
```

> 口径说明：这是 **SQL 层模拟**（复刻 merge/undo 的 SQL 序列），不是调用 Rust `merge()`。
> Rust 侧两条路径（无条件 push / 无条件 DELETE）已逐行读码确认；完整端到端仍需 §4 的红绿测试。

### 2.3 修法（推荐）

**在 merge 时记录"这条新边是不是真的插进去了"**，undo 时只删"确实由 merge 创建"的边：

```rust
// merge_inner
let inserted = tx.execute("INSERT OR IGNORE INTO edges ...", params![...])? > 0;
moved_edges.push(json!({
    "old": e,
    "new": { "source_id": new_src, "target_id": new_tgt, "edge_type": et },
    "inserted": inserted,          // ← 新增
}));
```

```rust
// undo_merge
let created_by_merge = e["inserted"].as_bool().unwrap_or(true);  // 旧事件没有该字段 → 默认 true（兼容）
if created_by_merge {
    tx.execute("DELETE FROM edges WHERE ...", ...)?;
}
tx.execute("INSERT OR REPLACE ...", ...)?;
```

- **兼容性**：旧事件（`inserted` 字段缺失）默认按旧行为处理，不会让历史撤销变坏；新事件才精确
- **为什么不选"undo 时先判断 keep 原边是否早于合并"**：边表只有 `created_at`（浮点秒），
  且 `INSERT OR REPLACE` 会覆盖时间戳，无法可靠区分"合并前就有"与"合并时插入"⇒ 不可行

### 2.4 验收（先红后绿）

新增测试 `merge_undo_keeps_existing_edge_of_keep`（`service.rs` tests 内）：

1. A、B、C 三条；`link(A,C,"semantic",0.5)`；`link(B,C,"semantic",1.0)`
2. `merge(A,B)` → 断言 A→C 仍在（当前为真）
3. `undo_merge` → **断言 A→C 仍存在且 weight=0.5**
4. 红绿：修复前该断言失败（红）→ 修复后通过（绿）；并保留原 `merge_can_be_undone` 全绿

## 3 F1c：文案（P3）

`merge_preview` 返回 `edges_moved = edges_total - self_loops`（`:2625-2632`），前端显示"搬走 N 条关系"。
问题是**被丢弃的自环数没展示**：用户在"只有 keep↔drop 一条边"的场景会看到"搬走 0 条关系"，
不知道那条边去哪了（其实撤销会回来）。

**改法**：结果提示拆成两段——「改指 N 条关系，丢弃 M 条自环（合并后两端变成同一条）」，M 来自 `self_loops_dropped.len()`。

## 4 F2：计数口径

### 4.1 已经正确的部分

- 界面 `total` = `SELECT count(*) FROM memories WHERE deleted_at IS NULL`（`data.rs:412`）
- 副本库实测：总行 **95** · `deleted_at IS NULL` **89** · 软删 **6** · 自洽 `89 + 6 = 95` ✓
- 维护页"可恢复 6 条"与软删 6 条**同源自洽** ⇒ 这部分**不是 bug**

### 4.2 真正的问题：版本链旧条被算成"有效记忆"

- 89 条里有 **1 条** `superseded_by` 非空（被替代的旧版本），`deleted_at` 仍为 NULL
- 真正"三空"有效（`deleted_at` / `superseded_by` / `valid_to` 皆空）= **88**
- **口径不一致**：召回已过滤 `valid_to`（T-M2-04 修过），但**列表与总数不过滤 `superseded_by`**
- 影响：编辑越频繁，旧版本越多，"记忆 N 条"越虚高；用户列表里能点到"已被替代"的旧内容

### 4.3 三个方案

| 方案 | 做法 | 优点 | 代价 | 建议 |
|---|---|---|---|---|
| **A 统一为"当前有效"** | total 与列表都加 `superseded_by IS NULL AND valid_to IS NULL` | 口径唯一、与召回一致 | 数字会变小；历史版本在列表里消失（可能有人想看历史） | 若用户明确"只看当前"再切 |
| **B 保持数据口径 + 界面说清** | 总数旁加注「当前有效 88 · 历史版本 1」；详情页已有"当前有效"标识 | 改动最小、信息最全、不动召回 | 多一处文案要维护 | ✅ **推荐** |
| **C 只写文档** | `docs/04` 写清 total 口径 | 零代码 | 用户仍困惑 | 作为 B 的补充 |

**推荐组合：B + C**（界面加注 + `docs/04` 写清），A 留作后续可选项。
理由：B 不改变任何已有行为（不会让"记忆 90"突然变 88 引发"数据丢了"的误判），但把口径**显式化**。

## 6 不要做的事

- **不要**把自环"恢复成边"（keep→keep 自环对图遍历无意义，`docs/04` 与代码注释都说明了）
- **不要**靠"合并时不 DELETE 旧边"来省事——会让 drop 的边残留在已软删条上，产生孤儿边
- **不要**在没写 ADR 的情况下改 `total` 语义（会影响总览、托盘、体检、备份校验等多处）
- **不要**用 `created_at` 时间戳来判断"边是否合并前就有"（`INSERT OR REPLACE` 会覆盖它）
