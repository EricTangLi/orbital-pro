## 0 一句话

> **Orbital Pro 的记忆层 = 一个可独立安装的 SQLite 库 + 三条数据通道 + 一套可逆的治理规则；
> 向上用 MCP 服务 N 个 agent，用 Proxy 自动注入，向下不依赖任何已装组件。**

四个设计约束（缺一个就不是这个产品）：
1. **独立安装**：新电脑解压即用，不依赖 Docker / WSL2 / 已装 CLI；
2. **多 agent 共享**：一套库服务 N 个 agent，归属与隔离同时成立；
3. **可操作**：能查看、能改、能合并、能退役（不是只读）；
4. **坏不了**：写入不静默丢失、隔离不越界、遗忘可逆。

#### 1.1.1 mnemon 的 `effective_importance` 公式（源码原文）

```go
// node.go:313
// base_weight(imp) * log(1 + access_count) * 0.5^(days_since_access / half_life) * (1 + 0.1*min(edges,5))
func ComputeEffectiveImportance(importance int, accessCount int, daysSinceAccess float64, edgeCount int) float64 {
    base := baseWeight(importance)              // 5→1.0, 4→0.8, 3→0.5, 2→0.3, 其他→0.15
    accessFactor := math.Log(1.0 + float64(accessCount))
    if accessFactor < 1.0 { accessFactor = 1.0 } // 0-1 次访问的保底
    decayFactor := math.Pow(0.5, daysSinceAccess/30.0) // HalfLifeDays=30
    edges := edgeCount; if edges > 5 { edges = 5 }
    edgeFactor := 1.0 + 0.1*float64(edges)
    return base * accessFactor * decayFactor * edgeFactor
}
```

**含义**（按源码逐项算，不是估）：
- 一条 `importance=5`、被访问 10 次、有 3 条边的记忆：`1.0 × ln(11)=2.398 × 1.0 × 1.3 = **3.12**`；停用 30 天后 `×0.5 = **1.56**`；90 天后 `**0.39**`。
- 一条 `importance=3`、从未被访问的新记忆：`0.5 × 1.0 × 1.0 × 1.0 = **0.50**`；30 天后 `0.25`；90 天后 `0.0625`。

**我们借用这一公式**（§6），但改两处：加来源权重、且**只用于排序与候选，不用于自动删除**。

### 1.2 TencentDB-Agent-Memory（30,775★，TypeScript）

| 机制 | 真实实现 | 证据 |

| 迁移 | `ALTER TABLE ... ADD COLUMN` + try/catch（注释自述为 SQLite 标准写法） | `memory-store.ts:506-517` |

| 审计 | `memory_audit` 表 | 同文件 `:842` |
| 部署 | **Docker 三件套**（core + hub + proxy），默认 sqlite 落容器卷 | `INSTALL_CN.md` 全文；`deploy/global-images/start-all.sh` |
| 已知问题 | 静默失败（#1432 health ok 但 store degraded、#1523 游标永久推进导致丢内容） | `research/evidence/01` |

**它最值得记住的一处失败（对我们的 ADR-005/007 是直接支撑）**：
它的 schema 是"多 agent 就绪"的（`user_id/agent_id/session_id/team_id` 四列 + 组合索引），
但**写入链路没有把 agent 身份贯通**——写入入口的公共类型 `CompletedTurn` 根本没有 `userId/agentId/teamId` 字段（`MemoryCore/src/core/types.ts:257-276`），
于是 L0 落盘只能落到默认桶（`l0-recorder.ts:278-284`：`agentId: agentId || DEFAULT_ISOLATION_ID`）；
而声称做校验的 `assertIsolation()` **从未被调用**（全仓只有定义处与再导出），设计文档 `docs/l0l3-tenant-isolation-design.md` 在仓库里**不存在**（死链）。
⇒ "多 agent"实际靠"每个 agent 独立安装 / 独立 dataDir"规避，而不是系统保证。这正是 issue #995（硬编码 `agent_id="default"` 造成迁移后孤儿）的土壤。

**结论**：Orbital Pro 的 agent 身份**必须在写入入口就是必填参数**，缺字段**拒绝写入**而不是填默认值（ADR-005）。

### 1.3 Graphiti（32,732★，Python）
- 图原生（Neo4j/FalkorDB）+ 双时态；**但**其自动失效（invalidation）实测错误退役率 70%~75.6%（见 `docs/09 A2`）。
- 教训直接决定我们的 ADR-009：**禁止自动硬删/自动失效**。

### 1.4 结论：三家的共同缺口

| 缺口 | mnemon | TencentDB | Graphiti | Orbital Pro |
|---|:--:|:--:|:--:|:--:|
| 多 agent 归属 | ❌ 无 agent 列 | ⚠️ schema 有四维，**但写入 API 没贯通**（缺字段静默填 `default`） | ⚠️ group 级 | ✅ `agent_id` + 作用域 + SQL 门控 |
| 独立安装（无 Docker） | ✅ 单二进制 | ❌ 要 Docker | ❌ 要图库 | ✅ 单 exe |
| 图关系 | ✅ 5 类边 | ⚠️ 实体表 | ✅ | ✅ 5 类边 + 意图权重 |
| 结构化属性 | ❌ | ✅ 实体表 | ⚠️ | ✅ `memory_facts` |
| 可操作界面 | ✅ Web | ✅ MemoryPanel | ❌ | ✅ 五页操作台 |
| 遗忘可逆 | ⚠️ 软删但有自动修剪 | ⚠️ | ❌ 自动失效 | ✅ 零自动删除 |

⇒ **没有一家同时满足四条约束**，这就是自研成立的理由（不是"想自己造"）。

**另需单独说明：basic-memory（4,550★）**
横向对比 8 个项目里，它是**唯一严格满足"多 agent ✅ + 本地 ✅ + Windows ✅"三项**的（有 `windows-latest` 真机 CI）。
但：**AGPL-3.0**（违反本项目红线，不能作为依赖）、**无 GUI**、**无 ACL**、`created_by` 只是字符串、没有图上的强属性查询。
⇒ **只借机制，不引入包、不 fork**（见 §2.6 与 §3.5）。
**自研边界因此收敛为**：存储引擎不造（SQLite + 三通道 + 单写队列），自研集中在**采集适配 / 写入入口的 agent 身份必填 / 中文检索 / 去重与冲突 / 操作台 GUI**。

## 2 数据模型（**六张表** + 索引）

> ⚠️ 2026-11-12 修订（ADR-031 / schema v2）：原为"五张表"，`memories.layer` 已删除，
> **L0 原始对话独立成 `conversations` 表**（见 §2.5.1）。表数从 5 变为 **6**，
> 另含两张 FTS5 虚表（`memories_fts` / `conversations_fts`）与 6 个同步触发器。

> SQLite 3.54（`rusqlite` bundled，**不用系统库**，见 ADR-002）。时间统一存 **REAL 类型的 Unix 秒**（避免字符串比较与时区问题）。

### 2.1 `memories`（自由文本通道，主表）

```sql
CREATE TABLE memories (
  id                 TEXT PRIMARY KEY,              -- mem_<ULID>
  content            TEXT NOT NULL,
  -- 归属与可见性
  agent_id           TEXT NOT NULL,                 -- dsh / hermes / pi / workbuddy
  scope              TEXT NOT NULL DEFAULT 'private'
                     CHECK(scope IN ('private','shared','entity')),   -- ADR-007
  -- 来源与性质
  origin             TEXT NOT NULL DEFAULT 'agent_derived'
                     CHECK(origin IN ('user_endorsed','agent_derived')),
  category           TEXT DEFAULT 'fact',           -- fact/decision/preference/constraint/context
  -- ⚠️ `layer` 字段已废弃（ADR-031，2026-11-12）：
  --   实测全代码零引用、库里 50 条全是 1；分层改为「L0 独立成 conversations 表」，
  --   「属于哪一层」由它在哪张表决定，不再存标记位。schema v2 迁移时删除。
  -- layer           INTEGER NOT NULL DEFAULT 1 CHECK(layer BETWEEN 0 AND 3),
  importance         INTEGER NOT NULL DEFAULT 3 CHECK(importance BETWEEN 1 AND 5),
  confidence         REAL NOT NULL DEFAULT 0.8,     -- 0..1，用于可信度排序与污染防护
  source_ref         TEXT,                          -- 原文引用（session id / 文件路径 / URL）
  session_id         TEXT,
  -- 标签与实体（JSON 数组，便于 FTS 与筛选）
  tags               TEXT NOT NULL DEFAULT '[]',
  entities           TEXT NOT NULL DEFAULT '[]',
  -- 时间语义（双时态）
  created_at         REAL NOT NULL,
  updated_at         REAL NOT NULL,
  valid_from         REAL NOT NULL,                 -- 事实何时开始为真
  valid_to           REAL,                          -- NULL = 仍然有效
  recorded_at        REAL NOT NULL,                 -- 我们何时记录它（事务时间）
  last_accessed_at   REAL,
  access_count       INTEGER NOT NULL DEFAULT 0,
  -- 治理
  pinned             INTEGER NOT NULL DEFAULT 0,    -- 1 = 免疫自动降权
  superseded_by      TEXT REFERENCES memories(id),   -- 被哪条取代（链式）
  effective_importance REAL NOT NULL DEFAULT 0.5,   -- 见 §6
  content_hash       TEXT NOT NULL,
  -- 向量
  embedding_status   TEXT NOT NULL DEFAULT 'pending'
                     CHECK(embedding_status IN ('pending','ok','failed','skipped')),
  embedding_source   TEXT,                          -- {model}@{endpoint}
  -- 软删
  deleted_at         REAL
);

-- 去重（同一 agent 同一会话同内容只存一条）
CREATE UNIQUE INDEX ux_mem_agent_content
  ON memories(agent_id, content_hash) WHERE deleted_at IS NULL;

-- 房间/作用域检索
CREATE INDEX ix_mem_agent_active ON memories(agent_id, deleted_at, created_at DESC);
CREATE INDEX ix_mem_scope_valid  ON memories(scope, valid_to) WHERE deleted_at IS NULL;
CREATE INDEX ix_mem_retention    ON memories(deleted_at, pinned, effective_importance);
CREATE INDEX ix_mem_entity       ON memories(entities) WHERE deleted_at IS NULL;
```

**为什么加 `version` 不放进 `memories`**：乐观并发由 writer 队列串行化天然解决（ADR-003），表里加 `version` 反而诱导绕过队列直接写。TencentDB 需要 `version` 是因为它允许多写者。

**用途**：按实体查（"Orbital 的所有已知属性"）、按属性过滤（"端口是 8790 的记录"）、冲突检测（同实体同属性多个有效值）。

### 2.3 `edges`（图关系通道）

```sql
CREATE TABLE edges (
  source_id  TEXT NOT NULL,
  target_id  TEXT NOT NULL,
  edge_type  TEXT NOT NULL CHECK(edge_type IN
             ('temporal','semantic','causal','entity','supersedes')),
  weight     REAL NOT NULL DEFAULT 1.0,
  metadata   TEXT NOT NULL DEFAULT '{}',
  created_at REAL NOT NULL,
  PRIMARY KEY (source_id, target_id, edge_type),
  FOREIGN KEY (source_id) REFERENCES memories(id) ON DELETE CASCADE,
  FOREIGN KEY (target_id) REFERENCES memories(id) ON DELETE CASCADE
);
CREATE INDEX ix_edges_type   ON edges(edge_type);
CREATE INDEX ix_edges_source ON edges(source_id, edge_type);
CREATE INDEX ix_edges_target ON edges(target_id, edge_type);
```

**五种边 + 生成规则**（这是 mnemon 的真实设计，我们照抄并补规则）：

| 边类型 | 何时生成 | 权重 | 与 mnemon 的差异（**重要**） |
|---|---|---|---|
| `temporal` | **同一 agent 且同一 `session_id`** 内，相邻两条自动连 | `1/(1+小时差)` | mnemon 原版是「同 `source`（只有 user/agent 二值）的上一躯 + 24h 内最近 10 条」，SQL **不过滤 source** ⇒ 会跨 agent 连；我们没有 `source` 二值，必须显式加 `agent_id` 与 `session_id` 过滤（`store/db.go:651-672`、`graph/temporal.go:76`） |
| `semantic` | 写入时与已有记忆向量余弦 ≥0.85 建；跨 agent 相同 `content_hash` 也建（"共识信号"） | 相似度值 | 同向，但 **mnemon 无 FTS**；阈值与配额见 §12 #1 |
| `causal` | 显式 `memory_link(type=causal)`；或抽取时命中因果词 | 0.8（**我们定的常数**） | mnemon 用的是 **token overlap**（`graph/causal.go:83`），不是常数 |
| `entity` | 两条记忆的 `memory_facts` 共享同一 `(entity_type,entity_id)` 时自动建 | 0.9（**我们定的**） | mnemon 固定 1.0（`graph/entity.go:333,345`） |
| `supersedes` | 更新流程：新条取代旧条时写入，同时旧条 `superseded_by=new_id` | 1.0 | 同 mnemon（`model/edge.go:35` 的 `IsDirected()`） |

**注意**：`supersedes` 是 mnemon 的真实第五类（`db.go:334`），旧项目文档只写了四类——这是本轮代码级调研纠正的事实。

### 2.5.1 `conversations`（L0 原始对话，**ADR-031 新增**）

> 编号用 2.5.1 而不是顺延 2.6~2.8，是为了不打乱既有小节引用。

```sql
CREATE TABLE IF NOT EXISTS conversations (
  id            TEXT PRIMARY KEY,              -- conv_<uuid>
  agent_id      TEXT NOT NULL,
  session_id    TEXT NOT NULL,
  round_index   INTEGER NOT NULL,
  role          TEXT NOT NULL CHECK(role IN ('user','assistant','tool','system')),
  content       TEXT NOT NULL,
  raw_json      TEXT,                          -- 原始事件（含工具调用）
  created_at    REAL NOT NULL,
  extracted_at  REAL,                          -- 抽取状态：**失败不推进** → 可重放
  extract_error TEXT
);
CREATE UNIQUE INDEX ux_conv_round   ON conversations(agent_id, session_id, round_index);
CREATE INDEX        ix_conv_pending ON conversations(extracted_at) WHERE extracted_at IS NULL;
CREATE INDEX        ix_conv_session ON conversations(agent_id, session_id, round_index);
-- 只有 FTS5（L0 不需要向量）
CREATE VIRTUAL TABLE conversations_fts USING fts5(content, content='conversations', content_rowid='rowid', tokenize='trigram');
```

**为什么独立成表**（ADR-031）：L0 与 L1 的写入频率、保留期、索引策略三者都不同——
混在一张表里只能靠 `layer` 标记位区分，而该标记位在实测中"全代码零引用、库里 50 条全是 1"（等于没生效）。
物理分层后"这条属于哪一层"由**它在哪张表**决定，不需要再存标记位。

**抽取可重放**：`extract_error` 有值时 `extracted_at` 必须保持 NULL，下次批处理会重试同一条；
推进 `extracted_at` 只在抽取成功后（这条是"游标先于成功推进"坑的防线）。

### 2.6 「文件即真相、索引可重建」（借 basic-memory 的核心思想）

basic-memory 的设计是"笔记是 Markdown 文件，SQLite 只是可重建的索引"（`models/knowledge.py:103-166` 的 `file_path`/`checksum`/`sync_checksum`）。
对我们的启示（**采纳，作为降级保险**）：

| 层 | 内容 |
|---|---|
| **真相层** | `%LOCALAPPDATA%\OrbitalPro\data\journal\YYYY-MM.ndjson`：每次写入追加一行（id/agent/content/facts/时间戳），**只追加不改写** |
| **索引层** | SQLite（五张表 + FTS + 向量）：随时可删，启动时从 journal 重建 |
| **判据** | 删掉 `orbital.db` 后重启，记忆条数与内容摘要与删除前一致；否则"可重建"不成立 |

**为什么值得多写一份 journal**：用户最怕"记忆没了"。SQLite 损坏、迁移失败、误删库都能从 ndjson 重建。
代价约 1.5~2 倍磁盘（一条记忆存两份）；按 10 万条 × 平均 200 字估算约 40 MB，可接受。

**⚠️ 修正（审核 P0-4）**：journal 必须是**事件流**，不能只记写入——否则"删掉 db 可重建"不成立。

```jsonc
// 每行一个事件，按 ts 单调递增，重建时顺序回放（幂等）
{"op":"write",        "id":"mem_x", "agent_id":"dsh", "scope":"private", "payload":{...}, "ts":1762900000.123}
{"op":"update",       "id":"mem_x", "payload":{"content":"...","importance":4}, "ts":...}
{"op":"soft_delete",  "id":"mem_x", "ts":...}
{"op":"restore",      "id":"mem_x", "ts":...}
{"op":"invalidate",   "id":"mem_x", "valid_to":..., "ts":...}
{"op":"pin",          "id":"mem_x", "pinned":1, "ts":...}
{"op":"fact_add",     "id":"mem_x", "payload":{...}, "ts":...}
{"op":"edge_add",     "src":"mem_x","dst":"mem_y","edge_type":"semantic","weight":0.91,"derived":true,"ts":...}
{"op":"edge_remove",  "src":"mem_x","dst":"mem_y","edge_type":"semantic","ts":...}
```

**重建规则**：
1. 按 `ts` 顺序回放；同一 `op` 重复回放结果不变（幂等）；
2. `derived:true` 的边（temporal/semantic/entity 自动生成）**不参与回放**，重建时按当前规则重新生成；
3. **重建判据**（改口径）：`content` 摘要一致 + **可见条数**一致 + **显式边数**一致；`effective_importance` 是派生值，**不承诺**一致。

### 2.7 向量与全文索引（**审核 P0-1 补充，原设计缺失**）

主表只存"状态"，向量与 FTS 各自独立，避免主表膨胀与迁移困难。

```sql
-- ① 向量：**普通表 + BLOB**（ADR-019：暂不引入 sqlite-vec 扩展）
CREATE TABLE memories_vec (
  memory_id  TEXT PRIMARY KEY REFERENCES memories(id) ON DELETE CASCADE,
  agent_id   TEXT NOT NULL,        -- 分区键：检索先按 agent 过滤，再算余弦
  embedding  BLOB NOT NULL,        -- f32 小端字节序列
  dim        INTEGER NOT NULL,     -- 维度 = embedding.dimensions（默认 1024）
  updated_at REAL NOT NULL
);
CREATE INDEX ix_vec_agent ON memories_vec(agent_id);

-- ② 全文：FTS5 外部内容表（content 不重复存）+ trigram 分词
CREATE VIRTUAL TABLE memories_fts USING fts5(
  content, tags_text, entities_text,
  content='memories', content_rowid='rowid',
  tokenize='trigram'                -- 中文用 trigram；2 字查询另走 LIKE 兜底（§4）
);

-- ③ 三个同步触发器（insert / update / delete）
CREATE TRIGGER trg_mem_ai AFTER INSERT ON memories BEGIN
  INSERT INTO memories_fts(rowid, content, tags_text, entities_text)
  VALUES (new.rowid, new.content, new.tags, new.entities);
END;
CREATE TRIGGER trg_mem_ad AFTER DELETE ON memories BEGIN
  INSERT INTO memories_fts(memories_fts, rowid, content, tags_text, entities_text)
  VALUES ('delete', old.rowid, old.content, old.tags, old.entities);
END;
CREATE TRIGGER trg_mem_au AFTER UPDATE ON memories BEGIN
  INSERT INTO memories_fts(memories_fts, rowid, content, tags_text, entities_text)
  VALUES ('delete', old.rowid, old.content, old.tags, old.entities);
  INSERT INTO memories_fts(rowid, content, tags_text, entities_text)
  VALUES (new.rowid, new.content, new.tags, new.entities);
END;
```

**维度迁移规则**（改 `embedding.dimensions` = 换向量空间）：
1. 新建 `memories_vec_v2`（新维度）→ 2. 后台批量重算全库向量 → 3. 校验条数与抽样相似度 → 4. 事务内 `DROP memories_vec; ALTER TABLE memories_vec_v2 RENAME TO memories_vec` → 5. 写 `memory_events(operation='rebuild_index')`。
**判据**：迁移期间旧表可用（读旧）、新表建好后一次性切换；失败保留旧表。

> ✅ **已定（ADR-019，2026-11-12）**：**不引入 sqlite-vec**，向量用普通表 + Rust 余弦计算。
> 升级触发条件：活跃记忆 > **5 万条** 或 recall P95 > **200ms**（届时再评估扩展）。
> 已由 `crates/orbital-core/src/schema.rs` 落地并有单测（向量按 agent 分区可查）。

**向量与 FTS 的失败降级**：
- 嵌入端点全挂 → 只走 FTS，`degraded:true` + 原因（F7）；
- `memories_vec` 损坏（sqlite-vec 已知故障模式，TencentDB #1709）→ **向量写入失败必须可见**，不能静默；降级到 FTS 并托盘标黄。


### 2.8 嵌入配置（**ADR-022，2026-11-12 新增**）

**一个模型规格 + N 个端点**（不是"主模型 + 备模型"）。

```text
ModelSpec { id, name, dimensions }        // 全局唯一一份。改它 = 换向量空间，必须重建索引
Endpoint  { id, kind(cloud|local), base_url, model_name, api_key, priority, timeout_ms, enabled }
```

**为什么不能有第二个模型**：主备是可用性冗余，不是"同时用两个模型"。一旦允许配两个模型，
就永远要回答"它们兼不兼容"，而这件事**靠名字答不出来**——
实测反例：云端 `Qwen/Qwen3-Embedding-0.6B` 与本地 `qwen3-embedding:0.6b` 是同一模型，名字完全不同。

**兼容性验证（唯一判据）**：5 条固定探测句，所有可用端点各算一遍，与基准端点逐条比余弦，
**全部 ≥ 0.99** 才算同一向量空间（`BASELINE_PASS = 0.99`）。

**本机实测结果（2026-11-12）**：

| 端点 | 类型 | 模型 | 维度 | 耗时 | 结论 |
|---|---|---|---:|---:|---|
| siliconflow | cloud | `Qwen/Qwen3-Embedding-0.6B` | 1024 | 1135ms | 基准 |
| ollama | local | `qwen3-embedding:0.6b` | 1024 | 263ms | **最小余弦 0.9992** ✅ |

⇒ 判定同一向量空间，可混用。

**配置来源与优先级**：环境变量 > `~/.orbital/secrets.json` > 内置默认。
**密钥永不进仓库**（`.gitignore` 已排除 `secrets.json` / `secrets/` / `*.token`）。

**写入前校验**：`check_dimension()`——返回维度 ≠ `ModelSpec.dimensions` 直接拒绝，
因为换模型后旧向量作废，混写会让召回静默出错。

**一个实测坑**：本机 `HTTP_PROXY=127.0.0.1:10808` 实为 SOCKS5，reqwest 当 HTTP 代理用会
**静默超时**（无有用错误信息）。嵌入请求默认 `no_proxy()`；需要代理的用户用 `ORBITAL_EMBED_USE_PROXY=1`。

### 2.9 计数口径（T-M10-05 / ADR-048）

界面上所有"记忆 N 条"走同一套口径，读文档时务必分清三层：

| 口径 | SQL 条件 | 谁在用 | 含义 |
|---|---|---|---|
| **有效计数** `total` | `deleted_at IS NULL` | 总览、托盘、体检、备份校验、记忆页标题 | 未被删除的记录数（**含**版本链旧条） |
| **历史版本** `total_history` | `deleted_at IS NULL AND (superseded_by IS NOT NULL OR valid_to IS NOT NULL)` | 记忆页标题加注、设置页「记忆总数」加注 | `total` 里已被新版本替代/已失效的旧条 |
| **真正当前有效** | 上两者之差（`total − total_history`） | 未直接暴露 | 参与召回、能被注入的那批 |

**为什么不合并成一个数**：`total` 被四处消费（总览 / 托盘角标 / 体检判据 / 备份校验），
改语义会连锁，且这些地方都没有"口径版本"标记（ADR-048 的被否方案）。
界面用「N 条 · 其中历史版本 M 条」把差异**显式化**——不改变已有行为，也不让用户对着数字猜。

**数据库行数 ≠ 界面数字**：表行数 = `total` + 软删条。软删条在维护页「可恢复」里；
副本库实测 `89 + 6 = 95`（`docs/29 §4.1`）。

**加注只在默认视图显示**：记忆页带筛选（agent / 类型 / 状态 / 待办）时，
标题里的 `total` 是**筛选后**的数量，与全局 `total_history` 不同源，混用会给出错误口径。

## 3 写入路径（agent → core）

```
agent ──MCP memory_write──┐
                          ▼
① 身份校验：进程启动参数推导 agent_id；请求里带的 agent 只做比对，不符 → 403
② 参数校验：content 非空、≤64KB；scope 合法；importance 1..5
③ 去重：SELECT id FROM memories
        WHERE agent_id=? AND content_hash=? AND deleted_at IS NULL
        → 命中则返回 { id, duplicate: true }，不重复写
④ 入写队列（单队列，批 100 条或 50ms 强制 flush）
⑤ 事务内（BEGIN IMMEDIATE）：
     INSERT memories（status 先返回 accepted_id）
     INSERT memory_facts（若带结构化属性）
     INSERT edges（temporal / entity / semantic 自动边）
     INSERT memory_events（operation='write'）
   COMMIT
⑥ 回执：{ id, status: 'committed', duplicate: false }
⑦ 异步：批量嵌入（32 条/批）→ 更新 embedding_status
```

**三条硬规则**：
1. **先 COMMIT 再回执**——回执说成功，数据必须已落盘（防静默丢失 F1）；
2. **失败返回错误码**，绝不返回"假成功"；
3. **回执里的 `id` 必须能查回**：`memory_get(id)` 立即返回同一条内容（验收项）。

**并发基线（借鉴 TencentDB，`MemoryCore/src/core/store/sqlite/memory-store.ts:313-325`）**：
```sql
PRAGMA journal_mode      = WAL;
PRAGMA busy_timeout      = 5000;    -- 毫秒
PRAGMA cache_size        = -65536;  -- 负数 = KB，即 64MB
PRAGMA mmap_size         = 134217728; -- 128MB
PRAGMA wal_autocheckpoint = 1000;   -- 页
```
> TencentDB 设了这 5 项，但**没有 `SQLITE_BUSY` 专项重试**（`git grep SQLITE_BUSY` 0 命中）。我们在 writer 队列上再加一层：BUSY 时按 50/100/200ms 退避重试 3 次，仍失败则返回 `WRITE_BUSY`（可重试错误码），并把计数上报体检。

**"0 条结果必须带原因"（借鉴 TencentDB `l1-empty reason=<label>`）**：写入链路任何一步丢数据，都必须落一条带原因的事件（`empty_reason`），而不是只打 warn 日志。这是"为什么这轮没记住"能被 grep 出来的前提。

**去重的边界**：只对同一 agent 去重。**跨 agent 相同内容不合并**，而是建 `semantic` 边——因为"两个 agent 都记得同一件事"是**重要信号**（可用于冲突判断与可信度加权），合并会丢掉这个信号。

#### 3.5.1 Agent 接入必须配置化（ADR-021）

**问题**：本产品要交付给其他用户。如果把 agent 的配置路径/格式写死在代码里，
换个用户就完全不可用（别人的 Hermes 不在 `%LOCALAPPDATA%`、别人装的 agent 也不在名单里）。

**设计**：用数据描述"怎么接入"，不写代码。

```text
AdapterSpec {
  id                 // agent 标识（同时是记忆归属名）
  display_name
  mcp_config_path    // 支持 %VAR% 与 ~/（跨用户可移植）
  format             // json | yaml
  mcp_key            // mcpServers / mcp / insert
  supports_mcp       // false 时只能走 proxy 旁路
  supports_proxy
  note               // 该 agent 的接入坑（路径之外的信息才是接入难的地方）
}
```

**扩展方式（不需要改代码、不需要重新编译）**：在 `~/.orbital/adapters/` 放任意 `*.json`：

- 与内置同 `id` → **覆盖**（例如你的 Hermes 装在别处）
- 新 `id` → **追加**（例如接 Codex / Cursor / 你自己写的 agent）

**内置 4 条**：hermes / pi / dsh / workbuddy（**四个都支持 MCP**）。
⚠️ WorkBuddy 的 MCP 配置在 `~/.workbuddy/mcp.json`，**不是** `%APPDATA%\WorkBuddy\User\settings.json`（后者是 VSCode 系设置，无 MCP）——首版曾据此误判为「不支持 MCP」，已纠正。

**接入的唯一入口**：`attach::attach_by_spec(db, spec, mcp_command)`
- `format=json` → 结构化 patch（保其他字段）
- `format=yaml` → 文本级插入（保注释）
- `supports_mcp=false` → 明确拒绝并提示走 proxy（**不假装支持**）
- 更新语义：**键级合并**（`env` 里用户自己加的键保留，本项目字段覆盖）

**MemoryService 对外方法**（`crates/orbital-core/src/service.rs`）：

| 方法 | 用途 |
|---|---|
| `open(db, journal)` | 建服务（含加载嵌入配置） |
| `write(&va, input)` | 写入（限流 → 队列 → COMMIT → 回执 → 尝试嵌入） |
| `get / recall / update / forget / link / related / stats` | 记忆操作（全部走同一 `VISIBLE` 门控） |
| `health()` | 体检（见 §2.8 与 T-M1-10） |
| `backfill_embeddings(limit)` | 补算缺失向量（幂等） |
| `mark_embedding_failed(id, reason)` | 把失败可见化 |
| `verify(token) / check_claim(&va, claimed)` | 身份校验与声明比对 |
| `db_path()` | 暴露库路径（体检/备份用） |

**硬约束**：
1. 内置路径**只许用环境变量**（`%LOCALAPPDATA%` / `%USERPROFILE%` / `%APPDATA%`），不许写本机绝对路径；
2. 幂等判断必须比较 `command` **指向哪里**，不能只看键是否存在
   （实测：Hermes 与 DSH 都曾"已有 orbital 键但指向旧版本"，只看键名会静默跳过）；
3. 每条 spec 必须写 `note`。


### 3.5 采集层：记忆怎么"进来"（`docs/04` 首版漏掉的一层）

> ⚠️ **2026-11-12 补充（ADR-028）**：本节讲"记忆怎么进来"，但**实际只实现了 MCP 主动写**——
> 而 agent **不会自觉调 `memory_write`**（除非用户说"记住这个"）。
> 与读取镜像：读要"推+拉"，**写也要"推+拉"**。
>
> | 写 | 状态 |
> |---|---|
> | 主动（MCP `memory_write`） | ✅ 4/4 已实测 |
> | **自动采集** | ❌ **未实现**——两条路见 ADR-028（hook 事件 / 文件反向导入） |
>
> **本机已有素材**（路 B 的输入）：`~/.mnemon/runtime/MEMORY.md`(9.4 KB)、
> `hermes/memories/MEMORY.md`(3.5 KB)+`USER.md`(2.6 KB)、WorkBuddy `MEMORY.md`(8.3 KB)——**合计约 23 KB**
> 的各 agent 已沉淀记忆，目前**一条都没采集进 Orbital**。

> ⚠️ **2026-11-12 重大修正（见 `docs/17`）**：本节原把 proxy 当"注入主力"，该假设**站不住**。
>
> 业界实证（本机 `research/evidence/01-03`）：
> - **TencentDB** 用 `MemoryProxy :8096` 做 LLM 请求代理（**需改 base_url**），但它同时有工具路径；
>   且自身踩过 **issue #1133「网关故障对 agent 不可见，记忆消失数天」**；
> - **claude-mem（115,935 stars，20+ agent）走的是 hook 旁路**：**完全不动 agent 的 API 配置**，
>   靠 hook 抓会话 → 压缩 → 下次会话注入；
> - 本机调研原文："hook 旁路采集是『统一管理 4 个 agent』**唯一现实可行的采集方式**"。
>
> **最终形态（ADR-027）——不是"某一个主力"，而是"按宿主能力择一"**：
>
> | agent | 注入适配 | 落点 | 实测 |
> |---|---|---|:--:|
> | DSH | hook（`dsh-hooks-claude-code`） | `cordis.patch.yml` 挂载 | 路径已确认，未挂载验证 |
> | Hermes | hook（`hooks_auto_accept`） | `config.yaml` | 路径已确认，协议待查 |
> | pi | 扩展（`before_agent_start` → `{message}`） | `~/.pi/agent/extensions/*.ts` | 有 `mnemon.ts` 活例 |
> | **WorkBuddy** | **文件注入**（每次会话自动读） | `~/.workbuddy/user-<uid>-personal/MEMORY.md` | ✅ **ORANGE-42 实测生效** |
>
> **MCP 是存取主干**（9 工具，4/4 已实测）；hook / 扩展 / 文件是**三种注入适配器**。
> **proxy 降为可选**（默认关闭）——它需改 agent 的模型 base_url，
> **代价是丢失 agent 官方模型体系**（如 WorkBuddy 积分）且构成单点故障。
>
> **✅ 2026-11-12 最终定论（见 ADR-027）**：
> 4 个 agent 的自动注入路径**全部找到**，但**不是同一个机制**——
> DSH/Hermes 用 hook、pi 用扩展、**WorkBuddy 用文件注入**（`user-<uid>-personal/MEMORY.md`）。
> 且注入必须分**两层**：
> - **静态索引层**（hook/扩展/MEMORY.md 区块）：让 agent「知道有记忆」并看到最近几条；
> - **动态检索层**（MCP `memory_recall(query)`）：按**当前问题**取「对应」记忆。
>
> **静态层注入的不是「对应记忆」，而是「索引 + 调用指引」** ——
> 因为会话开始前不可能知道用户会问什么（详见 ADR-027 决策二）。


三层入口，按可靠性排序：

| 入口 | 机制 | 适用 | 失败处理 |
|---|---|---|---|
| **A. MCP 主动写** | agent 自己调 `memory_write` | agent 明确要记的事 | 返回错误码，agent 可见 |
| **B. Proxy 旁路采集** | 对话经 proxy 转发时，把 round 追加到 **`conversations` 表**（L0 原始对话，ADR-031） | 4 个 agent 全覆盖、agent 无感 | **必须落 journal**；失败要大声报错，不许只 warn |
| **C. Hook 采集** | agent 生命周期钩子（会话结束/压缩前）触发抽取 | DSH 等支持 hook 的 agent | 同上 |

**关键设计**：
1. **采集失败必须"大声"**：调研中 TencentDB 最致命的缺陷就是抽取失败被吞成 `{success:false}` 而游标照样前进（`l1-extractor.ts:216` + `pipeline-factory.ts:615-669`）⇒ 瞬时失败变永久丢失。我们的规则：**抽取失败不推进游标**，并写 `empty_reason` 事件。
2. **采集与写入分离**：采集只产出 **`conversations` 表**里的原始对话（append-only），抽取是异步批处理；抽取失败**不推进 `extracted_at`**，可以重放（ADR-031）。
3. **DSH 需要自写 adapter**：basic-memory 已有 claude / codex / **pi** 三家 hook adapter（`hooks/adapters/`），可照抄事件形状；DSH 没有现成的，必须在 M3 之前定义事件契约（契约内容最终落在 `docs/04` §10 与 `docs/16-Proxy审核与上游配置设计.md`）。
4. **重复采集要去重**：同一会话同一轮被 hook 与 proxy 各采一次时，用 `(agent_id, session_id, round_hash)` 幂等。

## 4 召回路径（agent → core）

```
query ──▶ ① 解析意图（when/what/why/how）→ 决定边类型权重（借 mnemon intent.go 思路）
          ▼
       ② SQL 层硬门控（不是应用层过滤）：
          WHERE deleted_at IS NULL
            AND (valid_to IS NULL OR valid_to > now)
            AND (agent_id = ? OR scope IN ('shared','entity'))
          ▼
       ③ 四路召回（并行，各取 top-K）
          ├─ A. 向量：cosine ≥ 0.40，K=50
          ├─ B. 关键词：FTS5（trigram + 中文 bigram），K=50
          ├─ C. 图扩展：命中节点的 1 跳邻居，按 edge_type 意图权重，K=30
          └─ D. 结构化：memory_facts 命中 entity/property 过滤，K=30
          ▼
       ④ RRF 融合（k=60）：score = Σ 1/(60+rank_i) × 通道权重 × edge意图权重
          ▼
       ⑤ 重排（可选阶段）：effective_importance × confidence 加权
          ▼
       ⑥ 预算裁剪（maxItems / maxTokens 从配置读）
          ▼
       ⑦ 返回 [{ id, content, score, facts, edges, provenance }]
```

**关键设计点**：

| 点 | 选择 | 理由 |
|---|---|---|
| 门控位置 | **SQL 里** | 应用层过滤在并发/大库下会漏（调研 A3：共享句柄改写读别人数据） |
| 作用域 | `private` 只自己可见；`shared`/`entity` 跨 agent | ADR-007，避免"混库噪声" |
| 时效 | 召回默认排除 `valid_to < now`，但**允许查历史**（GUI 有"显示已失效"开关） | 既不召回过期事实，又保留可追溯 |
| Rust/中文 | FTS5 **trigram**（SQLite 内置）+ 中文 bigram 预处理 | 中文分词不能用默认 unicode61。**mnemon 没有 FTS**（它用全表 token 交集，每次 recall 全表加载 ⇒ O(N)），这是我们的改进项，不是"照抄 mnemon" |
| 融合 | RRF 而非分数加权 | 不同通道分数量纲不可比（mnemon 与 TencentDB 都走融合） |
| 重排 | 先不做，等基线 | 没有基线无法证明重排有效（ADR-012） |
| **向量分区** | 向量表 `memories_vec` 带 `agent_id` 列（ADR-019 用普通表），检索**先按 agent/作用域过滤再算余弦** | basic-memory 的 `project_id` 分区键正是为解决"大分区的候选挤掉小分区"（`models/search.py:310-326` 注释原文）；**禁止全库 top-k 后再过滤**——那等于让小分区永远召不回 |

### 4.1 作用域语义与图遍历门控（**审核 P0-2 / P0-3 补充**）

三种作用域的**完整语义**（此前只写了名字，没写规则）：

| 作用域 | 写入规则 | 召回可见性 | 图遍历（related / 扩展） |
|---|---|---|---|
| `private`（默认） | 任何 agent 可写自己的 | **只有写入它的 agent** 可见 | 只能连到自己的记忆；**不得**连到别人的 private |
| `shared` | 任何 agent 可写；多 agent 写同一内容 → 建 semantic 边 | 所有 agent 可见 | 可跨 agent 连 |
| `entity` | 写入**允许**（此时可能还没有 fact，因为 facts 在写入后添加，见 ADR-043）；**召回时**要求该记忆至少有一条有效 `memory_facts`，否则视同 `private` | **仅当调用方 agent 在该实体上有过记忆**时可见 | 可按实体连；跨 agent 仅对同实体参与者可见 |

**图遍历的三条硬门控**（`edges` 表本身没有 agent 归属，这是审核发现的泄漏点）：

1. **遍历后必须重新过门控**：任何 `memory_related` / 图扩展召回，都必须
   ```sql
   JOIN memories m ON m.id = e.target_id
   WHERE m.deleted_at IS NULL
     AND (m.valid_to IS NULL OR m.valid_to > :now)
     AND (m.agent_id = :caller OR m.scope IN ('shared','entity'))
   ```
   **禁止**只按 `edges` 表遍历完就返回。
2. **跨 agent 的 `semantic` 边只允许两端都是 `shared`**：写入建边时检查两端 scope；不满足则**不建边**（在 `memory_events` 记一条 `edge_skipped(scope_mismatch)`），不降级、不静默丢。
3. **软删后边残留**：`ON DELETE CASCADE` 只在硬删触发；软删的记忆必须靠上面的 `deleted_at IS NULL` 过滤掉，另设维护任务清理孤儿边（只清边，不动记忆）。

**验收用例（必须进 M1 对抗测试）**：
- A 写 private「端口 8791」→ B 写 private「端口 8791」→ 系统**不得**建 A↔B 的 semantic 边；若强行用 `memory_link` 建，B 的 `related` **不得**返回 A 的条目。

**关于"召回低"的定性诊断顺序**（避免瞎调参）：
1. 先看**候选集是否被门控砍掉**（作用域/agent 写错）；
2. 再看**嵌入是否真的生成**（`embedding_status='ok'` 占比）；
3. 再看**FTS 是否命中**（中文分词是否生效）；
4. 最后才调阈值与权重。

## 5 注入路径（proxy，只读）

### 5.0 前提：proxy 凭什么能"拦到" agent 的请求？（2026-11-12 补，原先缺失）

**问题**：MCP 是 agent **主动调工具**（pull），它只能让 agent"想起来查一下"，
**没法在 agent 已经发出 LLM 请求之后往 prompt 里塞东西**。
要在 prompt 里注入，proxy 必须**站在 agent 与上游 LLM 之间**。

**做法**：改写 agent 的**模型端点地址**，让它以为上游是 proxy。

| agent | 配置位置 | 字段 |
|---|---|---|
| WorkBuddy | `~/.workbuddy/models.json`（数组） | 每项的 `url` |
| pi | `~/.pi/agent/models-store.json` | 每项 `baseUrl` |
| 其他 OpenAI 兼容客户端 | 环境变量 | `OPENAI_BASE_URL` / `ANTHROPIC_BASE_URL` |

把 `https://api.deepseek.com/v1` → `http://127.0.0.1:8790`，agent 的每次对话就会先到 proxy：
proxy 解析 → 查记忆 → 注入 → **再转发给真正的上游**（原地址由 proxy 配置里保存）。

**⇒ 所以 proxy 不是"记忆系统提供的代理服务"，而是"把 agent 的模型出口改道"**。
这不是可选项：**不改 base_url，proxy 永远收不到任何请求，注入就是空的**。
（这也是为什么首版只做 `/health` 完全无用——它连转发都没接。）

### 5.0.1 两种模式必须并存（MCP + proxy 是互补，不是二选一）

| | MCP（pull） | proxy（push） |
|---|---|---|
| 触发 | agent 主动调用工具 | 拦到 LLM 请求就自动注入 |
| 能写吗 | ✅ 能（`memory_write`） | ❌ 只读（ADR-008） |
| 能注入 prompt 吗 | ❌ 不能 | ✅ 能 |
| 需要改 agent 配置 | 加一条 MCP server | **改模型 base_url** |
| 挂掉的影响 | agent 少个工具 | **对话直接断**（最高风险） |
| 适合什么 | 精确存取、管理操作 | 让 agent"不用问也能想起来" |

**设计含义**：
1. **MCP 是主力**（安全、可控、可撤销），proxy 是增强（自动、但风险高）；
2. proxy 必须有**熔断与直连兜底**：上游不可达 / 自身异常时，原样转发、绝不阻塞对话（ADR-008）；
3. proxy 的配置必须能**一键还原**（备份原始 base_url），否则用户装了就回不去。

```
agent ──▶ proxy:8790 ──▶ 上游 LLM
            │
            ├ ① 解析协议（OpenAI / Anthropic / Google）
            ├ ② 提取会话标识（session_id 或 请求指纹 hash）
            ├ ③ 查 session cache（key = session_id + query_hash，TTL 30s）
            │     命中 → 直接用（<1ms）
            │     未命中 → 查 core（超时 300ms 直接跳过注入，转发继续）
            ├ ④ 按预算裁剪 + 渐进投递（先 L3/L2 摘要，追问再给 L1 明细）
            ├ ⑤ 注入到协议规定位置（system 或 user 前缀，按协议）
            └ ⑥ 转发上游（SSE 原样透传）
```

**四条硬规则**：
1. **proxy 从不写库**（ADR-008）；
2. **超时跳过**，绝不阻塞对话；
3. **降级要可见**：注入失败/跳过时，响应头带 `X-Orbital-Inject: skipped(原因)`，GUI 可统计；
4. **缓存失效靠事件版本**：core 每次写库递增 `revision`，proxy 拿到旧 revision 的缓存即失效（比纯 TTL 更准）。
   ——这一步是我们对"多 agent 写同一实体，缓存看到旧值"（一致性）的回答。

## 6 时效与遗忘（可逆）

### 6.1 `effective_importance` 公式（借 mnemon，加来源权重）

```
ei = base(importance)
   × max(1.0, ln(1 + access_count))
   × 0.5^(days_since_last_access / H)
   × (1 + 0.1 × min(edge_count, 5))
   × origin_weight
```
- `base`: 5→1.0, 4→0.8, 3→0.5, 2→0.3, 1→0.15（mnemon 原值）
- `H`（半衰期）= 30 天，**可配置**
- `origin_weight`: `user_endorsed`=1.0，`agent_derived`=0.8（**我们新增**：人说的话比 agent 自己推断的更持久）
- `pinned=1` 时直接 `ei = max(ei, 1.0)`（免疫降权）

**用途仅两处**：召回排序权重、退役候选排序。**不用于自动删除。**

> ⚠️ **实现现状（2026-11-13 审计校正）**：`effective_importance_of()` 已按上式计算（读时、不落盘），
> 但**目前还没有被任何排序路径使用**——`recall()` 仍是 `ORDER BY bm25(...)`（纯全文相关度）。
> 所以"召回排序权重"这句是**设计目标**，不是已落地行为。
> 落地在 **M3**（四路召回 + 加权 RRF，docs/11 P1-9）；退役候选在 **M4**。
> 在那之前，ei 只用于详情页展示与测试断言。**不许**在报告里说"召回已按 ei 排序"。

**为什么强调"读时计算"**：mnemon 是在写入时算一次快照。实测本机 `shared` 库 139 条活跃记忆里按公式"现在重算"**0/139 命中**；**36 行 EI 全等 0.75**（批量 import 时算的），而这些行现在 `access_count` 已 32–263、按公式应 ≈4.18。拿这份过期值做退役决策，等于用错误的尺子做不可逆操作（ADR-013）。

### 6.2 四档处理（全部可逆）

| 档 | 触发 | 动作 | 可逆方式 |
|---|---|---|---|
| 排序降权 | 每次召回计算 | 只影响顺序 | 自动 |
| 退役候选 | `ei < 0.15` 且非 pinned 且创建 >24h | 进"待退役"列表，**等人确认** | 不处理即无变化 |
| 降权 | 人点"降权" | `importance -= 1`（记录原值到 events） | 点"恢复"回原值 |
| 标记失效 | 人点"标记失效" | `valid_to = now`，保留历史 | 清除 `valid_to` |
| 软删 | 人点"删除" | `deleted_at = now` | 恢复 |
| 硬删 | 人点"彻底删除"+二次确认 | 物理删除 | **不可逆**（需备份） |

**重要实现约定（与 mnemon 相反）**：`ei` **读时计算、不落盘为真值**；若为性能落盘缓存，必须带 `ei_computed_at`，且召回时校验「缓存时间 > 最后访问/边变更时间」才可用。
mnemon 是在 `remember/import/gc` 时落盘（`RefreshEffectiveImportance`），读路径不重算 ⇒ 会得到「写入时快照」，与"最近访问"脱节。我们**不复制这个缺陷**（见 `docs/07` ADR-013）。

**免疫规则**（借 mnemon `IsImmune`）：`pinned=1` 或 `importance>=4` 或 `access_count>=3` → 永不进退役候选。

**禁止**（ADR-009）：任何"自动把 `valid_to` 设为过去"或"自动软删"的逻辑。mnemon 有 `AutoPrune` 自动软删，**我们不照抄**——因为用户场景是"个人知识库"，误删代价远高于多占几百 KB。

## 7 一致性（多 agent 并发写同一实体）

学术界把 multi-agent memory consistency 列为最紧迫开放问题（`research/00 §1`）。我们的规则必须是**可执行的三条**：

| 场景 | 规则 | 实现 |
|---|---|---|
| 同一 agent 重复写同内容 | 幂等，返回已有 id | `UNIQUE(agent_id, content_hash)` |
| 不同 agent 写同一实体同一属性 | **后写胜 + 保留历史**：新 fact 的 `valid_from=now`，旧 fact `valid_to=now`；两者都保留 | 事务内先关旧再插新 |
| 不同 agent 写同一实体不同属性 | 并存 | 无冲突 |
| 同一内容跨 agent 重复 | 不合并，建 `semantic` 边（共识信号） | 写入时检测 |
| 并发更新同一条 | writer 单队列串行化；后到者覆盖并在 events 留痕 | ADR-003 |

**冲突检测**：同一 `(entity_type, entity_id, property)` 存在**多个 `valid_to IS NULL` 且 value 不同** → 冲突，进冲突收件箱。
**冲突条目不参与注入**（调研 A4：持续暴露冲突记忆是唯一让所有模型都掉点的条件）。

### 10.1 写入/删除的「承诺强度」必须显式返回（借 dsh-mnemon，`evidence/05 §6.1④`）

| 字段 | 取值 | 含义 | 为什么必须有 |
|---|---|---|---|
| `write_mode` | `exact` | 写进去就是最终形态 | — |
| | `async-extracting` | 已入原始层，**提炼稍后完成** | UI 不能显示"已记住"，只能显示"已提交，等待提炼" |
| `deletion_mode` | `soft` / `hard` / `unsupported` | 能不能删、删了能不能回 | 防止"删了其实是隐藏"或"以为能恢复其实不能" |
| `update_action` | `saved` | 只改元数据，行不变 | — |
| | `superseded` | 内容变更 → 新行 + 旧行进版本链 | UI 必须说"旧版本已保留"，否则用户以为内容被覆盖丢失 |
| | `merged_scope` | 同内容已存在且 scope 升级 → **合并到已存在那条** | 不说清会出现"我改了 B，结果提示合并，可 B 内容没变"的困惑 |
| | `duplicate` | 同内容已存在、scope 未升高 → **本条没写** | 必须与 `saved` 区分，否则 UI 会谎报"已保存" |

> `update_action` 是 **T-M2-02 落地时新增的**（原表只有 write/deletion）。代码里叫 `UpdateOutcome.action`。
> ⚠️ **UI 必须按 `action` 分支，不许用 `note` 文案做判断**——文案会改，action 不会。

**文案对应**：`已提交，等待确认`（异步）/ `已入库`（同步）/ `内容已存在，没有重复写入`（去重）/
`超过单条上限 64KB`（拒绝）/ `已保存（旧版本已进版本链，可回滚）`（superseded）/
`已合并：…scope 已从 X 升级为 Y`（merged_scope）。
**判据**：UI 上任何"保存成功"，必须能对应到上表的一种确定状态；对不上就是撒谎。

### 10.2 `merged_scope` 的已知语义缺口（2026-11-13 审计发现）

`merged_scope` 目前的行为是：**把"已存在那条"的 scope 升级，被编辑的那条保持原样**。
于是会出现这样的场景，且**当前文案没能说清**：

```
用户编辑 B（内容 "Y"）→ 改成 "X"，并想把 X 设为 shared
库里已有 A（内容 "X"，private）
实际结果：A.scope 变成 shared；B 仍是 "Y" 没有变化；返回 merged_scope(id=A)
文案：「已合并：内容与已有一条相同，scope 已从 private 升级为 shared」
```

用户很可能理解成"B 被合并进 A 了"，但 B 还在、内容也没改。
**这不是数据损坏，是反馈歧义**。后续二选一（需在 M2 收口前定）：

1. **把 B 软删**（内容已由 A 代表），文案改成「已合并到 A（A 的 scope 已升级），本条已软删」；
2. **保持现状但改文案**：明确说「本次修改没有写入，命中了已存在的 A；A 的 scope 已升级」。

在那之前，**不许**在测试或报告里把 `merged_scope` 描述成"两条合并成一条"。

## 11 迁移与兼容

| 来源 | 处理 |
|---|---|
| 旧项目 `~/.orbital-dev/orbital.db` | 一次性导入：memories → memories（补 `agent_id`/`scope='private'`/双时态）；**不导入**其单一通道假设 |
| mnemon `~/.mnemon/data/shared/mnemon.db` | 只读导入：`insights` → memories、`edges` → edges；**导入后不反向写 mnemon**。两条硬约束见下 |
| 无 | 空库首启（建 schema + 写 `user_version`） |

**mnemon 导入的两个陷阱（实测）**：

1. **列存在性分支**：`origin` / `source_ref` / `valid_from` / `valid_to` / `recorded_at` **只存在于 `shared` 库**；`default` / `evalbench` / `verifyprobe` / `audit-*` / `guardtest` 都是 15 列、没有 `origin`。脚本必须 `PRAGMA table_info(insights)` 后按列存在性分支，否则直接报 `no such column: origin`。
2. **类型转换必须断言**：mnemon 的 `edges.created_at` 是 **TEXT（RFC3339）**，我们是 **REAL（epoch 秒）**。SQLite 的 REAL 亲和性遇到 `'2026-09-14T06:31:23Z'` 转不成数字会**原样存成 TEXT**——不报错，但之后所有 `created_at >= ?` 范围查询**静默失效**。导入后必须断言 `typeof(created_at)='real'` 且样本可比较，失败即回滚。

**导入必须留证据**：条数对账（源 N 行 → 目标 N 行，失败 M 行要列原因）。
