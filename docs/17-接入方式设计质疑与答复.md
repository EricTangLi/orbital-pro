# 三个设计质疑的答复（并推翻一处既有设计假设）

> 触发：用户三问——
> ① 记忆系统是否必须替换所有 agent 的 API 配置？其他系统（TencentDB 等）是这么做的吗？优势是什么？
> ② WorkBuddy 有积分、走官方模型体系，proxy 接管后是否就用不了官方模型了？
> ③ MCP + proxy 双路对记忆系统有多大意义？
> 日期：2026-11-12 ｜ 证据：本机 `research/evidence/01-03`（代码级调研，非二手转述）

---

## 0 结论（先给答案）

| 问题 | 答案 |
|---|---|
| ① 必须改所有 agent 的 API 配置吗？ | ❌ **不必须**。业界有**三种**接入方式，proxy 是代价最高的一种 |
| ② WorkBuddy 接管后还能用官方积分/模型吗？ | ❌ **不能**。接管 = 绕过官方体系 = 失去积分（且可能违约） |
| ③ MCP + proxy 双路有意义吗？ | ⚠️ **方向对，但搭档错了**。应该是 **MCP + hook**，proxy 降为"可选增强" |

**最重要的一点**：我们 `docs/04 §3.5` 把 proxy 当成主力注入通道，**这个假设站不住**。
本机调研证据（`research/evidence/03` L244）原文：

> "**hook 旁路采集 + 队列 + 会话结束压缩**：不看 agent 源码就能拿到全过程，
> 这是『统一管理 4 个 agent』**唯一现实可行的采集方式**"

---

## 1 业界三种接入方式（都有实证）

### 方式 A：MCP 工具（agent 主动调）

| 项 | 内容 |
|---|---|
| 代表 | basic-memory（`hooks/adapters/{claude,codex,pi}.py`） |
| 做法 | 在 agent 配置里加一条 MCP server |
| 能做的 | agent **主动**写/查 |
| 不能做的 | **改不了已经发出的 prompt** |
| 代价 | 低（只加一条配置，可撤销） |

### 方式 B：hook 旁路采集（**最强，且不改 API**）

| 项 | 内容 |
|---|---|
| 代表 | **the-dotmack/claude-mem（115,935 stars，本次调研最大）**，支持 **20+ agent** |
| 做法 | 在 agent 旁边跑"第二个 agent"，通过 **hook** 抓会话内容 → 压缩成 observation/摘要 → **下次会话注入** |
| 能做的 | 全自动：采集 + 注入，**不需要改 agent 的模型 API** |
| 代价 | 需要 agent 有 hook 机制；常驻 worker 有端口/版本脆弱性（#380、#3857） |
| 证据 | `research/evidence/03` §1.4（stars 115,935 / 最后推送 2026-11-11 / Apache-2.0） |

### 方式 C：proxy 接管 base_url（代价最高）

| 项 | 内容 |
|---|---|
| 代表 | **TencentDB Agent Memory 的 `MemoryProxy :8096`**（LLM 请求代理，注入/回写，**代理不改协议**） |
| 做法 | 改 agent 的模型 base_url → 请求经 proxy → 注入 → 转发上游 |
| 能做的 | 自动注入，且能**看到完整请求/响应**（回写记忆） |
| 代价 | ① 必须改 agent 配置；② **丢失 agent 官方模型体系**（见 §3）；③ **单点故障**（proxy 挂 = 对话断） |
| 真实事故 | `research/evidence/01` L382：TencentDB 自己的 issue **#1133「网关故障对 agent 不可见，记忆『消失』数天」** |

### 三种方式对比

| 维度 | MCP | hook 旁路 | proxy 接管 |
|---|:--:|:--:|:--:|
| 要改 agent 的 API 配置吗 | ❌ 不需要 | ❌ 不需要 | ✅ **必须** |
| 能主动写记忆吗 | ✅ | ✅ | ✅（旁路回写） |
| 能自动注入 prompt 吗 | ❌ | ✅ | ✅ |
| 保留 agent 官方模型/积分吗 | ✅ | ✅ | ❌ **丢失** |
| 单点故障风险 | 低 | 中（worker） | **高（对话断）** |
| 覆盖 agent 数（实证） | 3 家（basic-memory） | **20+ 家（claude-mem）** | 需逐家改配置 |
| 实现复杂度 | 低 | 中 | 高（协议解析 + 流式兼容） |

## 2 回答问题①：**不必须**，我们之前的假设错了

**原假设**（`docs/04 §3.5`）：A=MCP 主动写 / B=proxy 旁路 / C=hook，proxy 是注入主力。

**事实**：
1. TencentDB **确实**用 proxy（`MemoryProxy :8096`），但它同时有工具路径；
2. **stars 最高的 claude-mem（115k）走的是 hook 旁路，完全不动 agent 的 API 配置**，且覆盖 20+ agent；
3. 本机调研早已结论："hook 旁路是唯一现实可行的采集方式"——**但设计文档没采纳这个结论**。

**⇒ 设计应改为**：**hook 旁路为主（自动注入）→ MCP 为辅（精确操作）→ proxy 为可选（需要看完整请求时才用）**。

**优势对比**（回答"proxy 的优势是什么"）：
- proxy 的唯一独有优势：**能看到完整的请求与响应**（可用于"自动回写记忆"、用量统计、成本核算）；
- hook 的优势：**不动用户配置**、覆盖广（20+ agent）、不碰官方模型体系；
- MCP 的优势：**精确、可控、可撤销**，且不依赖任何 hook/proxy 机制。

## 3 回答问题②：WorkBuddy 接管后**用不了官方积分**

### 技术事实

WorkBuddy 的模型配置在 `~/.workbuddy/models.json`，每一项长这样：

```json
{ "id": "agnes-2.0-flash", "url": "https://apihub.agnes-ai.com/v1",
  "apiKey": "sk-...", "supportsToolCall": true, ... }
```

**`url` 和 `apiKey` 是绑定的**。把 `url` 改成 `http://127.0.0.1:8790` 后：
- 请求不再发往 WorkBuddy 的官方端点；
- WorkBuddy 的**积分体系、模型路由、额度控制全部被绕过**（它凭服务端计费，改了走不到那儿）；
- 而且 proxy 转发时还得带上**原本的 apiKey**，等于用你的 key 直连第三方；
- 如果 WorkBuddy 的服务条款禁止改 endpoint，还可能**违反条款**。

### 结论与建议

| 场景 | 建议 |
|---|---|
| 用户想保留 WorkBuddy 官方积分/模型 | **只用 MCP + hook**，绝不接管 base_url |
| 用户愿意用自己 DeepSeek key 换"自动注入" | 才启用 proxy 接管，且必须**明确告知后果**、一键可还原 |

**⇒ 产品上 proxy 必须是"可选高级功能"，默认关闭，开启时明确写清"将失去 agent 官方模型与积分"。**

## 4 回答问题③：MCP + proxy 双路**意义有限，应改为 MCP + hook**

### 原设计的逻辑

"proxy 负责自动注入，MCP 负责精确操作" → 双路互补。

### 问题所在

1. **proxy 的代价被低估**：改所有 agent 配置 + 丢官方模型 + 单点故障；
2. **hook 旁路能同时做到"自动注入 + 不改配置"**——它才是 proxy 的替代品，不是 MCP 的替代品；
3. 因此真正的互补关系是：
   - **hook**：自动采集 + 自动注入（主力，不动配置）
   - **MCP**：精确写入、管理、按需查询（配合）
   - **proxy**：只在"必须看完整请求/响应"（成本统计、协议级回写）时才用（可选）

### 修正后的采集/注入矩阵

| 能力 | hook 旁路 | MCP | proxy |
|---|:--:|:--:|:--:|
| 自动采集会话 | ✅ 主力 | ❌ | ✅ |
| 自动注入 prompt | ✅ | ❌ | ✅ |
| agent 主动精确写入 | ❌ | ✅ 主力 | ❌ |
| 不改 agent 配置 | ✅ | ✅ | ❌ |
| 保留官方模型/积分 | ✅ | ✅ | ❌ |
| 看到完整请求响应 | 部分 | ❌ | ✅ 独有 |

**关键判断**：
1. **WorkBuddy 一定可行**——已有第三方项目（deja-vu）在用 Claude-shape hooks 给它接记忆；
2. **DSH 一定可行**——本机就有 hook 插件体系；
3. Hermes / pi 需各花 0.5 天实测"有没有 hook 点、能拿到什么（会话内容？工具调用？）"。

**⇒ hook 方案不是理论上的，至少 2/4 有明确证据，1/4 有第三方适配证据。**

## 9 三种方式的组合建议（最终形态）

```text
                  ┌────────────────────────────────┐
agent 会话 ──hook─▶│ 采集（旁路，不改配置）          │
                  │  · 会话内容 / 工具调用           │──▶ 写队列 ──▶ SQLite
                  └────────────────────────────────┘
                  
agent 主动 ──MCP──▶ 8 个工具（精确写/查/管理）      ──▶ 同一库
                  
agent 请求 ─proxy─▶（可选）看到完整请求/响应        ──▶ 用量统计 / 协议级回写
                   默认关闭，开启会丢官方模型体系
```

**注入发生在哪**：
- **hook 方案**：在 agent **下一次**会话开始时，把上次的摘要/索引注入到上下文（claude-mem 的做法）
- **proxy 方案**：在**本次**请求发出时注入（实时，但代价高）

**⇒ hook 的"下次会话注入"对多数场景已经够用**（记忆本来就是跨会话的），
proxy 的"实时注入"只在"同一轮对话内需要立刻带上记忆"时才有独特价值。

---

## 10 本轮结论的一句话总结

> **要记忆生效，不必改 agent 的 API 配置。**
> 主流做法（且 stars 最高的项目）是 **hook 旁路**：不动你的模型配置、不碰你的积分，
> 在会话边界采集与注入。**proxy 是"能看到全部流量"的重武器，代价是接管你的模型出口**——
> 它应该是可选功能，不是默认路径。

我们原设计把 proxy 当主力，是**把接入成本转嫁给了用户的模型配置**，这个方向要改。
