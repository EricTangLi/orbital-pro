## 2 P0 发现（开工前必须修，共 5 条）

### [P0-1] 向量与 FTS 的存储完全没有定义

- **证据**：
  - `docs/04 §2` 的五张表 DDL 里**没有** `embedding` 列、没有 `vec0` 虚表、没有 `memories_fts` 虚表；
  - 但 `docs/04 §4` 的召回明确写「A. 向量：cosine ≥ 0.40」「B. 关键词：FTS5（trigram + 中文 bigram）」；
  - `docs/02 §4.1` 却有 `embedding BLOB` 与 `embedding_status`——两处不一致。
- **影响**：实现者无法建表；"向量分区键"（`docs/04 §4` 表格最后一行）无处落；FTS 的触发器（insert/update/delete 同步）也没定义。
- **修复**（已在 `docs/04 §2.7` 补，见 §6）：
  1. 向量放**独立的 vec0 虚表**（`memories_vec(memory_id, agent_id, embedding float[N], updated_at)`），不塞进主表；
  2. FTS 放**独立外部内容表**（`memories_fts(memory_id, content, tags_text, entities_text)`）+ 3 个触发器；
  3. 维度 `N` 由配置决定（默认 1024），**改维度 = 换向量空间 = 必须重建**，写进迁移流程。

### [P0-2] `edges` 没有 agent/作用域归属 → `memory_related` 可跨作用域泄漏私密记忆

- **证据**：`docs/04 §2.3` 的 `edges` 只有 `source_id/target_id/edge_type/weight/metadata/created_at`，**没有 agent_id、没有 scope**；而 `docs/04 §10` 给 `memory_related` 的权限写的是"同 agent"。
  - 攻击路径：agent A 写一条 `private` 记忆 → agent B 写了一条内容相同的 `private` 记忆 → 系统按"跨 agent 相同 content_hash 也建 semantic 边"（§2.3）建了 A↔B 的边 → B 调 `memory_related(id_B)` → 遍历到 A 的 `private` 记忆 → **泄漏**。
- **影响**：违反"作用域隔离"这一产品前提；`docs/04 §8 F3` 的"160 次对抗查询 0 命中"会失败。
- **修复**（已补 `docs/04 §4.1`）：
  1. `memory_related` 与图扩展召回**必须在遍历后重新应用作用域门控**（`JOIN memories` 并加 `(agent_id=? OR scope IN ('shared','entity'))`）；
  2. 跨 agent 的 `semantic` 边**只允许连接双方都是 `shared` 的记忆**；否则不建边（或降级为"仅统计不遍历"）；
  3. 对抗测试里必须包含"私有记忆经 related 泄漏"这一用例。

### [P0-3] 作用域 `entity` 的语义没有定义，无法实现

- **证据**：`docs/04 §2.1` 注释写 `entity` 是"按实体隔离，跨 agent 可见但必须带来源"；但 `docs/04 §4` 的门控 SQL 写的是 `agent_id = ? OR scope IN ('shared','entity')`——这等于 **entity 对所有 agent 全开**，与"按实体隔离"矛盾。
- **影响**："实体作用域"要么实现成全局可见（失去隔离），要么根本没有判据。
- **修复**（已补 `docs/04 §4.1` 的三条规则）：
  - `entity` 记忆**必须**绑定至少一个 `(entity_type, entity_id)`（即至少一条 `memory_facts`）；
  - 召回时 `entity` 记忆的可见性 = **调用方 agent 是否有该实体的关联记忆**（同实体出现过），否则不可见；
  - 无实体绑定的记忆**不允许**设为 `entity`（写入时拒绝，`INVALID_ARGUMENT`）。

### [P0-4] journal 不足以支撑"删掉 DB 可重建"

- **证据**：`docs/04 §2.6` 承诺"删掉 `orbital.db` 后重启，记忆条数与内容摘要与删除前一致"；但 journal 只记**写入**（id/agent/content/facts/时间戳），**不记** update / soft_delete / invalidate / merge / pin / edges。
- **影响**：重建后：已删记忆会"复活"、编辑前的旧版本会回来、`edges` 全丢、`effective_importance` 归零。承诺不成立。
- **修复**（已补 `docs/04 §2.6`）：
  1. journal 改为**事件流**：每行 `{op, id, payload, ts}`，覆盖 write/update/soft_delete/restore/invalidate/pin/edge_add/edge_remove；
  2. 重建 = **回放事件流**（按 ts 排序，幂等）；
  3. 自动生成的边（temporal/semantic/entity）在重建时**重新生成**，并在 journal 里标记 `derived: true`，避免与显式边重复；
  4. 判据改为"重建后 content 摘要 + 可见条数 + 显式边数一致"，不再承诺 `effective_importance` 一致（它是派生值）。

### [P0-5] `docs/02 §4/§5/§7/§8` 仍是第一版旧内容，与 ADR 和 `docs/04` 冲突

- **证据**（逐条）：
  | 位置 | 旧内容 | 冲突对象 |
  |---|---|---|
  | `docs/02 §3.2` | `spawn hub-core.exe / hub-proxy.exe` | ADR-015（同一 exe spawn 自身 `--role`） |
  | `docs/02 §4.1` | `agent` 列、`UNIQUE(agent, session_id, content_hash)`、`embedding BLOB` | `docs/04 §2`（`agent_id`、`UNIQUE(agent_id, content_hash)`、无 BLOB） |
  | `docs/02 §4.3` | `edges.edge_type` 只有四类 | `docs/04 §2.3` 五类（含 `supersedes`） |
  | `docs/02 §5.1` | 返回 `{id, duplicate}` | `docs/04 §10`（含 `status/write_mode/deletion_mode`） |
  | `docs/02 §5.2` | `WHERE agent = ?` | `docs/04 §4`（含 scope） |
  | `docs/02 §7` | SQLite **3.51**；"本机仅 4.5GB 空闲"；Tauri 2.12；axum | ADR-002（bundled 3.54）；实测 31.3GB/11.6GB；`docs/10` 2.12.5 |
  | `docs/02 §8` | 开机自启"注册表 **或计划任务**" | ADR-016（明确不用计划任务） |
- **影响**：`docs/02` 自己声明"以 `docs/04` 为准"，但正文仍是旧内容——**声明与内容矛盾**，实现者按哪份都可能错。
- **修复**（本报告 §6 已执行）：把 `docs/02` 的 §3.2、§4、§5、§7、§8 全部改为**指向 `docs/04` 的索引**，不再重复 DDL 与流程；只保留进程/分层/部署视角。

## 3 P1 发现（M1 前修，共 12 条）

### [P1-1] 退役候选用"过期派生值"做索引排序
- **证据**：`docs/04 §2.1` 有 `ix_mem_retention(deleted_at, pinned, effective_importance)`；但 ADR-013 规定 `ei` **读时计算**、落盘值可能过期。
- **修复**：退役候选列表**不得**依赖该索引排序；改为读时计算后排序（候选量小，可全表扫 + 计算）。索引仅用于"快速筛出候选集"（`pinned=0 AND deleted_at IS NULL AND created_at < now-24h`）。

### [P1-2] 去重键阻止"同内容从 private 升级为 shared"
- **证据**：`UNIQUE(agent_id, content_hash) WHERE deleted_at IS NULL`。agent A 先写 private，后想把同内容设为 shared → 命中唯一约束 → 返回 duplicate，scope 不变。
- **修复**：去重命中时**比较 scope 与 origin**，若请求 scope 更高（private → shared/entity）则执行"升级"（更新 scope、写 events、返回 `upgraded: true`），而不是直接返回 duplicate。

### [P1-3] 软删不触发边级联，related 会返回已删记忆
- **证据**：`edges` 的 `ON DELETE CASCADE` 只在**硬删**时触发；软删只改 `deleted_at`。
- **修复**：`memory_related` 与图扩展的 SQL 必须 `JOIN memories` 并过滤 `deleted_at IS NULL`；另外提供"清理孤儿边"的维护任务（不算自动删除记忆，只清边）。

### [P1-4] 冲突收件箱没有数据模型
- **证据**：`docs/04 §7` 说"冲突 → 进冲突收件箱"，但五张表里没有 conflicts 表。
- **修复**：新增 `memory_conflicts(id, entity_type, entity_id, property, fact_ids, status, created_at, resolved_at, resolution)`；状态 `open/resolved/ignored`。冲突是"视图"还是"表"必须定：**定为表**（需要记录裁决结果）。

### [P1-5] shared 记忆的写权限模型缺失
- **证据**：`docs/04 §10` 只写"同 agent"能 update/forget，但 shared 记忆是**多 agent 可读**的；谁能改/删它？
- **修复**：定三条——① 写入者（origin agent）可改/删自己的；② 其他 agent **只能追加**（新建一条并建 `supersedes` 边），不能覆盖；③ 人（GUI）有最高权限。

### [P1-6] 没有写入限流与配额
- **证据**：`docs/04` 全文无速率/配额；一个 agent 循环写入可撑爆磁盘（journal 双份）。
- **修复**：`agents` 表加 `daily_write_quota`；core 侧滑动窗口限流（默认 200 条/分钟/agent），超限返回 `RATE_LIMITED`（可重试）；GUI 显示用量。

### [P1-7] 64KB 上限口径不明
- **证据**：`docs/04 §10` 文案写"超过单条上限 64KB"，未说字节还是字符。
- **修复**：明确 **UTF-8 字节**（`content.len()` in Rust），并在 UI 显示"剩余 x 字"（按字符估算，标注"约"）。

### [P1-8] "四路并行"与 SQLite 单连接矛盾
- **证据**：`docs/04 §4` 写"四路召回（并行）"；但 SQLite 单写队列 + 单连接下，查询实际串行。
- **修复**：明确用**只读连接池**（2-3 个 `mode=ro` 连接）做召回，写仍单连接；若 P95 不达标，再考虑把 FTS/向量查询合并成一条 SQL（UNION + 子查询）。

### [P1-9] RRF 公式把"意图权重"乘错位置
- **证据**：`docs/04 §4` 写 `score = Σ 1/(60+rank_i) × 通道权重 × edge意图权重`；`edge意图权重` 只对图通道有意义，乘在总和上会让所有通道都受影响。
- **修复**：改为加权 RRF：`score = Σ_c w_c/(k + rank_c)`，其中 `w_c` 是通道权重；图通道内部再乘 `edge_type` 的意图权重后**重新排序**（而不是直接乘到最终分）。

### [P1-10] 会话缓存的 `revision` 生命周期未定义
- **证据**：`docs/04 §5` 说"core 每次写库递增 `revision`"，但没说存在哪、core 重启后是否归零。
- **修复**：`revision` 存 `meta` 表（`key='revision', value=<整数>`），**持久化**；core 启动时读出并 +1；proxy 缓存条目带 revision，不匹配即失效。另加 30s TTL 兜底。

### [P1-11] 备份/恢复只有验收项，没有设计
- **证据**：`docs/05 M5` 有"备份→改数据→恢复→一致"的验收；`docs/04` 没有备份策略。
- **修复**：定三档——① 自动：每日 03:00 全量快照（`VACUUM INTO`），保留 7 份 + 每周 4 份；② 手动：状态页"立即备份"；③ 恢复：从快照 + journal 回放到快照之后（避免丢当日数据）。备份文件带 sha256 与 schema 版本。

### [P1-12] agent 身份只靠"启动参数推导"，可被伪造
- **证据**：`docs/04 §3` 写"agent 从进程启动参数推导；请求里带的只做比对"。但任何进程都能 `OrbitalPro.exe --role mcp --agent hermes` 冒充。
- **修复**：每 agent 一个 **32 字节 token**（接入时生成，存 DPAPI 保护的 secrets），MCP 请求必须带 token；core 校验 token→agent 映射。启动参数只作默认值，**不作唯一凭据**。
