# 产品定位审计：为什么 Orbital 变成了"外挂库"，真正应该怎么实现

> 触发：用户 2026-11-14 指出——"Orbital Pro 的设计目标（为各 agent 提供统一记忆）**没有达到**，
> 现在变成每个 agent 各有记忆，Orbital 只是外挂共享库"。
> 本文是**全面审计**：设计目标 → 实现现状 → 业界对标 → 根因 → 真正可行的实现路径。
>
> 证据等级标注：**【实测】**=本轮跑出来的；**【实读】**=读源码/配置原文；**【官方】**=官方文档/README；**【未核实】**=没拿到原文。

---

## 0 结论先行（用户判断成立，但根因不是"设计错"，是"实现路径押错"）

| 用户判断 | 审计结论 |
|---|---|
| "设计目标没有达到" | ✅ **成立**。Orbital 目前对 agent 只提供 **MCP 工具**（agent 主动调才动），**没有任何自动注入** |
| "变成每个 agent 单独一个记忆" | ✅ **成立**。DSH 用 dsh-mnemon、Hermes 用内置 memories、pi 用扩展、WorkBuddy 用 MEMORY.md，各管各的 |
| "Orbital 是外挂共享库" | ✅ **现状如此**，但**不是设计目标**——`docs/00 章程` 写的是"跨 4 个 agent 的记忆统一、可检索、可治理、**可注入**" |

**真正的根因（三条，逐条有证据）**：

1. **注入路径押在 proxy 上**，而业界与 DSH 生态的正确答案是 **hook/插件**（不改 agent 的模型 API）。
   `docs/04 §5` 把 proxy 写成唯一注入路径；`ADR-024` 要求改 agent 的 `base_url`；
   而 `ADR-025` 后来已经改成"hook 优先、proxy 可选"——**但文档没同步，实现也没做**。
2. **hook 注入从未实现**：全仓 grep `hook|additionalContext|SessionStart` 在业务代码里 **0 命中**【实测】。
   ADR-025 里"待验证"的 ①（DSH 挂 hook 后是否生效）到今天仍是待验证。
3. **没有"注入是否发生"的可观测性**：MCP 调用有 memory_events，但"这一轮到底注入了什么"无法从界面上看到，
   用户只能靠"感觉 agent 记得/不记得"判断——正是用户这次被迫来问的直接原因。

## 1 设计 vs 实现：四张表

### 1.1 目标（docs/00 章程原文）

> **Orbital Pro 是一个 Windows 独立桌面应用：让一台电脑上的所有 AI agent 共用一套可信的记忆——记得住、找得到、管得动、忘得掉。**

四个动词：记得住（多 agent 写同一库）· 找得到（四通道检索）· 管得动（操作台）· 忘得掉（衰减退役）。
**"记得住"隐含了"agent 会自己想起来"**——这是与"MCP 工具"最关键的差别。

### 1.2 实现现状（逐项实测）

| 能力 | 设计方案 | 实现状态 | 证据 |
|---|---|---|---|
| 统一存储（多 agent 同库） | SQLite 单库 | ✅ **已实现且在用** | 4 个 agent 都有活跃记忆：workbuddy 55 / hermes 16 / dsh 10 / pi 8【实测】 |
| 统一接入（MCP） | 7 工具 | ✅ **超预期：10 个工具** | `crates/orbital-mcp/src/main.rs` tool_defs：memory_write/recall/fact_add/get/update/forget/link/related + orbital_health/stats【实读】 |
| 治理台 | 合并/退役/冲突/审计 | ✅ 已实现 | M2~M4 里程碑 |
| **自动注入（hook）** | **ADR-025：注入主力** | ❌ **完全没做** | grep `hook|additionalContext|SessionStart` in `crates/` `src-tauri/src/` `src/` = **0 命中**【实测】 |
| 自动注入（proxy） | ADR-024：改 base_url | 🟡 **半成品** | 只支持 OpenAI `/chat/completions` 一种协议【实读】；**没有改 base_url 的代码**（grep `baseUrl|models.json|OPENAI_BASE_URL` 无业务实现）【实测】；默认关闭 |
| 注入可观测 | J6 注入统计卡片 | 🟡 只能看 proxy 的 | 有 `injection-*.jsonl` 与状态页卡片；但只覆盖 proxy 路径，hook 路径为 0 |

**一句话**：**"管"做到了，"记"只做到了"存"，"让 agent 自己想起来"这一半没做。**

### 1.3 实际使用数据（真实库，2026-11-14）

| agent | 活跃记忆 | 最近 7 天事件 | 说明 |
|---|---:|---:|---|
| workbuddy | 55 | 59 | 有 MCP，也在写 |
| hermes | 16 | 18 | 有 MCP，也在写 |
| dsh | 10 | 12 | 有 MCP（token 校验通过、sha256 一致）；最近一次写入 2026-11-13 22:10 |
| pi | 8 | 10 | 有 MCP，也在写 |

⇒ **MCP 这一层是活的**（4/4 都写过）。**死的是"自动注入"**——所以用户日常感受到的是"各自记忆"。

### 1.4 文档自身的矛盾（根因的一部分）

| 文档 | 说法 | 时间 |
|---|---|---|
| `docs/04 §5` | "注入路径（proxy，只读）"，改 base_url 是唯一办法 | 早期 |
| `ADR-024` | proxy 的注入点是改 agent 的 `base_url`，且必须有直连兜底 | 2026-11-12 |
| `ADR-025` | **hook 旁路 > MCP > proxy**；"4 个 agent 全部有自动注入路径，且都不是 proxy" | 2026-11-12 |
| `ADR-025 修正` | hook 实测 3/4（WorkBuddy 桌面版 hook 不被调用，改用 MEMORY.md） | 2026-11-12 |

**⇒ 决策层已经改对了（hook 优先），但 `docs/04` 没更新，实现按 `docs/04` 做了 proxy。**
这是典型的"决策更新了、实现没跟上、文档没同步"。

## 2 业界对标：五家主流项目**没有一家**靠改 API 注入

> 调研时点 2026-11-14，全部基于 GitHub 仓库原文（README / hooks.json / 源码）。

### 2.1 一页横评

| 项目 | ★ | 注入主路径 | 触发点 | 是否要求改 agent 的模型 API |
|---|---:|---|---|---|
| **claude-mem** | 116,863 | **hook → `additionalContext`** | SessionStart + UserPromptSubmit + **PreToolUse** | **否** |
| **mem0** | 68,927 | hook（仅首轮）或 hosted MCP | UserPromptSubmit(首轮) / SubagentStart | **否** |
| **OpenViking** | 42,206 | **hook → `<openviking-context>`** | SessionStart + 每轮 auto-recall | **否** |
| **TencentDB-Agent-Memory** | 30,881 | **宿主插件 API**（`prependContext` + `appendSystemContext`） | 每轮 before-prompt | **否** |
| **basic-memory** | 4,569 | hook → stdout 纯文本 | 仅 SessionStart | **否** |

**关键结论**：被广泛误传为"proxy 路线"的 TencentDB，实测也是**进程内插件 + 本地 HTTP sidecar**；
它唯一出现 "proxy" 字样的地方是 `embedding.proxyUrl`（只代理向量化请求，不代理对话请求）【实读】。

### 2.2 最锋利的一句官方原话（OpenViking）

> "Agent Plugins 1.0 deliberately excludes hooks … **If your harness has a hook system, prefer the dedicated plugin** — hook-driven recall and capture cost no tool calls and don't depend on the model choosing to remember."
> —— [OpenViking agent-plugins/README.md](https://github.com/volcengine/OpenViking/blob/main/agent-plugins/README.md)【官方】

**这句话正是 Orbital 当前的病根**：只做 MCP = 把"记忆是否生效"押在模型自觉性上。

### 2.3 三条可抄的工程细节

| 来自 | 细节 | 为什么重要 |
|---|---|---|
| claude-mem | 预算器用**字符**不用条数（10,000 字符硬上限）+ 超限逐级整项丢弃 | 条数不是固定大小，"按条数控"必然超限 |
| OpenViking | **降级梯度**（装不下→只列名字→一行提示）+ 跨轮去重（同 URI 5 轮内不重复注入） | 不静默丢、不重复刷屏 |
| basic-memory | **adapter（解析方言）/ renderer（拼上下文）/ writer（落库）三层彻底拆开** | 加宿主时不改注入逻辑 |

### 2.4 一条必须写成验收项的血泪教训（TencentDB issue #1133）

> 状态 **open**（2026-08-22 创建）。标题：gateway outage is invisible to the agent — **memory silently vanishes for days**。

后果：2026-08-11 ~ 08-20 **10 天**记忆写入全部静默失败，agent 零报错、内置记忆工具报成功，
最后靠外部 cron 轮询 `/health` 才发现，**10 天数据不可恢复**【官方 issue】。

⇒ **注入系统必须能证明"它死了"**：注入结果里带 `degraded` 标记，而不是返回空串让模型误以为"没有相关记忆"。

## 3 DSH 的实际情况：注入只能走 `decision.messages`

> 本机实读 `app.asar` 内 `dsh-agent-loop/src/agent.ts` 与官方生成文档。

### 3.1 关键事实（推翻一个常见误解）

| 事实 | 证据 | 等级 |
|---|---|---|
| **`dsh-hooks-claude-code` 本机没装**，asar 336 个依赖里没有它，其 peer `dsh-hook-protocol` 也不存在 | asar 全量索引 21,717 文件检查 | 【实测】 |
| pre-step 决策**只有 `kind` 与 `messages` 两个消费点**，写 `additionalContexts` = **静默丢弃** | `agent-loop/src/agent.ts:302-318` | 【实读】 |
| `additionalContexts` 的真实归属是**工具执行流水线**，不是 pre-step | `dsh/docs/subsystems/tools.zh.md` | 【官方】 |
| **dsh-mnemon 的注入形式**：`agent/pre-step` 里（step 1）往 `decision.messages` 追加一条 **user-role 插件消息**，`source.kind="dsh-mnemon", form="recall"` | `dsh-mnemon/lib/index.js:14126-14145` | 【实读】 |
| mnemon 的数据源是**本地文件**（`~/.mnemon/runtime/memories.json` → USER.md 3,997 B / MEMORY.md 7,163 B 投影），**不经 Mnemon CLI** | `source-runtime/lib/index.js:445-466` | 【实读】 |
| mnemon 每轮注入预算：配置 **12,000 字符**（light-context），runtime 源 eager 约 10,800；**实测每轮约 7.5k 字符** | profile `cordis.patch.yml:91-148` + 会话存档解帧 | 【实测】 |

### 3.2 两条可行路径（DSH 生态内）

| 路线 | 形态 | 注入点 | 可行性 |
|---|---|---|---|
| **A. 写 mnemon provider**（本报告新发现） | `dsh-mnemon-provider-orbital` 插件包 | 由 mnemon 的注入通道代劳 | ✅ **最轻**：mnemon 自带 `./extension-sdk`（`defineMemoryPlugin/defineMemorySource/defineMemoryStrategy/installMemory`）+ **10 个现成 provider 范本**（OpenViking/mem0/Hindsight/Honcho/Byterover/RetainDB/Supermemory/holographic/mnemon-native）【实读 package.json】 |
| **B. 写薄原生插件** | 独立 DSH 插件（~100 行） | `agent/pre-step` → `decision.messages` | ✅ 稳：照抄 mnemon 的写法，用 `execFile` 调 Orbital CLI |
| C. 补装官方 CC hook 桥 | `dsh-hooks-claude-code` + hooks.json | `UserPromptSubmit.additionalContext` | ⚠️ 高风险：包未装、peer 缺失、configPath 进程级只读一次 |
| D. 继续投 proxy（改 base_url） | 改 agent 模型端点 | proxy 拦请求 | ❌ **业界零采用**，且会丢 agent 官方模型/积分（ADR-024 自己写了） |

**⇒ 最优：A（最轻）或 B（最稳）；C 作兜底；D 降级为"高级用户可选"。**

## 4 真正应该怎么实现（推荐方案）

### 4.1 定位重新表述（一句话）

> **Orbital 不是"再做一个记忆库"，而是"坐在 agent 注入通道上的记忆服务"。**
> 存储与治理它已经做好了（这是它的壁垒）；缺的是**被 agent 自动调用**的那一层。

### 4.2 架构：一库、两通道、一治理台

```
                    ┌─────────────── Orbital 核心（已有） ───────────────┐
   agent 写入 ─────▶│ SQLite 单库 · 四通道检索 · 治理台 · 审计           │
                    └───────▲───────────────────────────┬───────────────┘
                            │                           │
              ┌─────────────┴──────────┐    ┌───────────▼────────────┐
              │ 通道 1：注入（新建）    │    │ 通道 2：MCP（已有）     │
              │ hook / provider / 插件  │    │ 10 个工具（主动存取）    │
              │ 每轮自动、0 tool call   │    │ 深查 / 写入 / 治理       │
              └─────────────▲──────────┘    └────────────────────────┘
                            │
     ┌──────────┬───────────┼───────────┬──────────────┐
   DSH      Hermes        pi        WorkBuddy      （未来）
  provider   hook      extension   MEMORY.md
```

**要点**：
- **MCP 保留**（写入与深查的主力，已做对）
- **新建"注入通道"**（真正的缺口），按 agent 各用各的机制
- **proxy 降级**为"需要看完整请求/用量的高级用户"可选，默认关

### 4.3 落地顺序（按"最快让用户看到效果"排）

| 步 | 内容 | 工作量 | 验收 |
|:--:|---|---|---|
| 1 | **DSH 注入**：写 `dsh-mnemon-provider-orbital`（或薄插件），让 mnemon 每轮从 Orbital 取 | 1~2 天 | 会话存档里出现 `source.kind="orbital"` 的消息；关掉 mnemon 本地文件后 DSH 仍能说出 Orbital 里的记忆【实测】 |
| 2 | **注入可观测**：把"这轮注入了 N 条 / M 字符 / 来源 / 耗时 / degraded"记进 memory_events 或新表，GUI 状态页显示 | 0.5 天 | 状态页能看到"最近一轮注入"的时间与内容摘要 |
| 3 | **降级可见**：注入失败/超时返回 `degraded` 而不是空串（学 TDAM #1133） | 0.5 天 | 故意停掉 Orbital，DSH 上下文里出现"记忆服务不可用"标记 |
| 4 | **Hermes / pi / WorkBuddy** 各自 hook | 各 0.5~1 天 | 同样验收 |
| 5 | proxy 降级 + 文档修正（`docs/04 §5` 与 ADR-025 对齐） | 0.5 天 | docs/05 的注入指标改为"hook 优先" |

### 4.4 立即能做的三件事（本轮之后）

1. **修正文档矛盾**：`docs/04 §5` 改为"注入 = hook 优先，proxy 可选"，与 ADR-025 对齐（今天可做）
2. **给 DSH 写 provider/插件**（步 1）——这是用户能"亲眼看到 Orbital 在工作"的唯一途径
3. **加"注入可观测"**（步 2）——否则下次还是靠用户"感觉"

## 7 一句话给用户

> Orbital 的"库"和"治理台"已经做好了，**缺的是"让 agent 每轮自动想起来"的那根管子**。
> 业界和 DSH 生态都不靠改 API，而是**挂到 agent 自己的生命周期上**。
> 最小一步：给 DSH 写一个 provider/插件，让它每轮从 Orbital 取记忆——这一步做完，你就能在会话里亲眼看到 Orbital 在工作。
