## 2 架构分层（对应论文的三层记忆层次）

| 层 | 职责 | 组件 | 论文对应 |
|---|---|---|---|
| **I/O 层（注入）** | 把记忆「推」给 agent | **按宿主能力择一**：hook（DSH/Hermes）/ 扩展（pi）/ 文件（WorkBuddy）；**proxy 为可选** | I/O |

> ⚠️ **2026-11-12 修订（ADR-025/026/027）**：注入**不再只有 proxy 一条路**。
> proxy 需改 agent 的模型 base_url，会**丢失 agent 官方模型体系**（如 WorkBuddy 积分）并构成单点故障，
> 故降为**可选功能（默认关闭）**。
> 实际注入按宿主能力择一：DSH/Hermes 用 hook、pi 用扩展、WorkBuddy 用文件（`user-<uid>-personal/MEMORY.md`）。
> 另：注入分**两层**——静态索引（让 agent 知道有记忆）+ 动态检索（MCP `memory_recall` 按问题取）。

| **Cache 层** | 会话/实体内缓存，避免每步查库 | Core 的 session cache | cache |
| **Memory 层** | 持久化：自由文本 + 结构化属性 + 图关系 | SQLite + writer 队列 | memory |

**关键设计**：I/O 层**只读 cache/memory，从不写**（ADR-008）。

## 3 三进程（不是"单 exe 多模式"）

### 3.1 为什么必须分进程

| 场景 | 单进程（我做错的） | 三进程 |
|---|---|---|
| GUI 全库扫描卡死 | proxy 跟着卡 → **4 个 agent 全停** | 只卡 GUI |
| proxy 崩 | 全停 | GUI 可重启 proxy |
| 记忆查询慢 | 拖慢 LLM 请求 | proxy 超时直接跳过 |

**依据**：本机 Hermes 曾因适配器阻塞事件循环 exit 75。

### 3.2 启动器职责（进程模型见 §3.3 与 ADR-015）

- 检查端口占用（8790/8791 **可配置**；冲突时按下方"孤儿回收"处理，仍冲突才顺延并把实际端口写回配置）
- **端口表（2026-11-13 确立，改端口必须三处同步：本节 / `HANDOFF.md` / 代码）**：

  | 端口 | 谁提供 | 环境变量 |
  |---|---|---|
  | 8791 | `--role core` 的 health 端点（`serve_http`） | `ORBITAL_CORE_PORT` |
  | 8790 | `--role proxy` | `ORBITAL_PROXY_PORT` |
  | **8799** | GUI 的只读召回端点（ADR-041，给 proxy 注入用） | 写死在 `local_api::spawn_recall_server` 调用处 |

  > ⚠️ **core health 与召回端点必须是两个端口**：M5 期间两者都绑 8791，core `bind` 失败 exit 2、
  > 自愈 3 次后放弃，导致记忆核心完全不可用（详见 `evidence/selfheal-20261113.md`）。
- spawn 两个子进程（**同一 exe**，`--role core` / `--role proxy`）
- 子进程崩溃时指数退避自动重启（1s/2s/4s，最多 3 次），失败后托盘标红
- 退出时优雅关闭子进程并 flush journal

**孤儿回收与端口接管（审核 P0-4，原设计缺失）**：

> 场景：启动器（GUI）被任务管理器强杀 → core/proxy 成为孤儿进程，继续占用 8790/8791。
> 若没有回收机制，用户下次双击会看到"端口被占用"，却找不到是谁占的，只能重启电脑。

1. 启动器把运行态写入 `%LOCALAPPDATA%\OrbitalPro\runtime\launcher.json`：`{pid, role, port, started_at}` 三条 + GUI 自身 pid；
2. 启动时若端口被占：读 `launcher.json` → 对每个 pid 校验
   - 进程存在 且 命令行是同一 exe 的 `--role core|proxy`（用 `Get-CimInstance Win32_Process` 的 `CommandLine` 判定）
   → 判为**孤儿**：先发 `WM_CLOSE`/终止信号，等 2s；仍在则 `taskkill /PID <pid> /T /F`；
3. 退不掉（例如被另一个用户会话占用）→ **顺延端口并在托盘显著提示**"已改用 8792，因为 8791 被占用"；**禁止静默换端口**；
4. 三个进程全部退出时删除 `launcher.json`（避免下次误判）。

## 3.3 「一个 exe」到底指什么（澄清 ADR-004 的边界）

用户要求：**"我需要是运行一个 exe 而实现所有的功能"**。
这与 ADR-004 的三进程**不矛盾**，但必须把两件事分开：

| 说法 | 是不是我们做的 | 说明 |
|---|---|---|
| 安装目录只有一个可执行文件 | ✅ **是** | `OrbitalPro.exe`，用户只点它 |
| 系统里只跑一个进程 | ❌ **不是** | 内部有 core / proxy / GUI 三个进程 |
| 一个进程按参数干所有事（旧项目做法） | ❌ **已被否决** | 没有隔离，GUI 卡死会拖垮注入（ADR-004） |

**实现方式（推荐 A）**：

```
用户双击 OrbitalPro.exe
        │
        ▼
  ┌──────────────────────┐
  │ 启动器（同一份 exe）   │
  └──────┬───────────────┘
         │ spawn 自己（current_exe），带 role 参数：
         ├─ OrbitalPro.exe --role core   （无窗口，:8791）
         ├─ OrbitalPro.exe --role proxy  （无窗口，:8790）
         └─ 自己作为 GUI（有窗口，Tauri 主窗口 + 托盘）
```

**关键点**：同一个 `exe` 文件被 spawn 成三个进程，每个进程只跑一个角色。
- 满足"只有一个 exe 文件"；
- 满足"进程隔离"（kill 掉 core，GUI 与 proxy 仍在）；
- 不需要 sidecar 的多个 exe 文件。

**实现约束（Tauri）**：`main()` 最先解析 `--role`；若不是 GUI，**必须在创建任何窗口/WebView 之前**走 headless 分支（否则会多出空白窗口与无谓内存）。GUI 分支才初始化 Tauri Builder 与托盘。

**被否方案**：
- B. sidecar（`externalBin` 带 2 个 exe）→ 否：安装目录出现 3 个 exe，违背用户"一个 exe"的字面要求（虽然也能接受，但 A 更省）。
- C. 单进程内嵌（core/proxy 做成线程）→ 否：见 ADR-004。

## 3.4 托盘常驻与单实例（借鉴 CC Switch 4.0.29 的实现，`research/evidence/04`）

| 机制 | 设计 | 判据 |
|---|---|---|
| **托盘图标** | Tauri `tray-icon` feature；图标随状态变化（正常 / 降级 / 错误） | 托盘图标右键有菜单；状态变化能看出来 |
| **托盘左键 → 面板** | **自绘 WebView 面板**（第二窗口 `tray-panel.html`，约 320×420，`decorations:false` + `transparent` + `always_on_top` + `skip_taskbar`，按托盘图标 `rect` 定位，失焦即隐藏） | 左键点托盘弹出面板；点外面自动收起 |
| **托盘右键 → 原生菜单** | 打开主窗口 / 服务状态（core·proxy·GUI 三点） / 立即备份 / 退出 | 菜单项可点，状态是真实探针 |
| **关闭窗口** | **不退出**，隐藏到托盘（默认行为，可在设置改为"直接退出"）；首次提示一次 | 点 X 后进程仍在 `Get-Process` 里 |
| **真正退出** | 只有托盘菜单「退出」或设置页「退出应用」；退出时**先释放单实例锁与托盘图标**再退 | 退出后 3 个进程全部消失 |
| **静默启动（防闪白）** | 主窗口 `visible:false`，等 `on_page_load(Finished)` 才 `show()`；开机自启时 silent | 启动不出现空白白屏 |
| **单实例** | `tauri-plugin-single-instance`；第二次启动**唤醒并聚焦**已有窗口 | 连点两次 exe，只有 1 个托盘图标、1 个窗口 |
| **单实例实现坑（实测）** | Windows 下 single-instance 回调在**主线程**，里面同步建窗会卡死 WebView2 ⇒ 必须 `spawn_blocking`；并用 `Mutex` 串行化两次并发唤醒 | 连点 5 次不卡死 |
| **退出/重启前释放锁** | `exit(0)` 会绕过 `Drop` ⇒ 重启与更新前显式 `destroy_single_instance_lock` + 移除托盘图标 | 更新后重启，不会出现"两个实例"或"图标残留" |
| **开机自启** | 可选（默认关）；用 `auto-launch` crate 写 `HKCU\...\Run`（不是计划任务） | 设置页开关与注册表状态一致 |

## 3.5 「避免进程被杀掉」的正确理解与边界

用户诉求：**"可以有一个程序常驻托盘，避免进程被杀掉"**。拆成三件事，只有前两件能做到：

| 诉求 | 能做到吗 | 做法 |
|---|---|---|
| 关掉窗口后程序继续跑 | ✅ | 关闭→隐藏到托盘（§3.4） |
| 子进程崩溃后自动恢复 | ✅ | 启动器监督：core/proxy 异常退出 → 指数退避重启（1s/2s/4s，最多 3 次），失败后在托盘标红并给「查看日志」 |
| 用户/任务管理器强制结束进程 | ❌ **不应该也不能阻止** | 技术上可用驱动/服务保护，但那属于恶意软件行为；我们只做**优雅退出**（退出时关闭子进程 + flush journal） |

**明确不做**：不用 Windows 服务（服务没有托盘、交互差）、不做进程守护驱动、不做"杀不掉"。
**理由**：用户要的是"省心常驻"，不是"无法关闭"。无法关闭的软件会被杀软误判，也违背用户自己的控制权。

## 5 关键流程（见 `docs/04 §3/§4/§5/§7`）

> 写入 / 召回 / 注入 / 一致性的唯一来源是 [`docs/04`](04-记忆系统设计.md)：
> - **§3 写入**：身份门控 → 去重 → 单写队列 → **先 COMMIT 再回执** → 异步嵌入

## 6 失败模式与防护（系统设计的第四步）

| # | 失败 | 后果 | 防护 |
|:--:|---|---|---|
| **F1** | **静默丢失**（返回成功但没库） | 用户以为记住了 | 写入返回 id 后可回查；GUI 显示"已接受≠已入库" |
| **F2** | 并发写同一实体 | 数据不一致 | 单写队列 + 明确一致性规则（后写胜 + 保留历史） |
| **F3** | 跨 agent 泄漏 | 串味 | **SQL 层硬门控** + 对抗查询测试 |
| **F4** | 迁移失败 | 库打不开 | schema 版本 + 启动自检 + 迁移前快照 |
| **F5** | Windows 特有 | 路径/编码/权限 | DPAPI、长路径、CRLF |
| **F6** | 注入超时阻塞对话 | agent 卡死 | 300ms 超时**直接跳过注入**，不影响转发 |
| **F7** | 嵌入不可用 | 语义检索失效 | 端点链降级到 FTS5，`degraded: true` 带原因 |
| **F8** | 单个坏记忆污染下游 | 幻觉扩散（EquiMem 论文） | `confidence` 字段 + 来源验证 + 可标记失效 |

## 10 诚实边界

1. **论文是"企业多 agent 工作流"场景**，本项目是"单机 4 个本地 agent"，规模差 1-2 个数量级
2. **50% token 降幅未在本机验证**
3. **`effective_importance` 的具体公式我还没定**（需实测）
4. **三进程的 spawn/重启机制未验证**（崩溃后重启、端口占用处理）
