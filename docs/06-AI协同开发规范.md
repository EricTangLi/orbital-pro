# AI 协同开发规范（v1.0）

> 适用：本项目所有 AI 助手（含 Lead、子代理、外部 agent）与人类协作者。
> 定位：这不是"提示词集合"，而是**可审计的作业协议**——每条规定都对应一个已发生过的失败。
> 依据：旧项目 `agent-memory-hub` 的 16 小时实战（48 轮对话、20+ 轮 UI 返工）与本机 `~/.dsh/AGENTS.md`。

---

## 0 为什么需要这份规范（一句话）

旧项目的失败不是"AI 不会写代码"，而是**AI 在没有契约的情况下连续做完了 11 个阶段的错误方向**：
读了任务分解没读界面设计、按周打勾而不是按验收、自己改了架构还写了 ADR 说服自己、连续三次交付"业余设计"。

⇒ 本规范只解决一件事：**让"做错"在 30 分钟内暴露，而不是 16 小时后。**

---

## 1 角色与写作用域（谁写什么，不许交叉）

| 角色 | 职责 | 允许写 | 禁止 |
|---|---|---|---|
| **Lead**（人类直连的主会话） | 定契约、拆任务、做取舍、最终验收、写设计文档 | `docs/**`、`AGENTS.md`、`README.md`、`HANDOFF.md`、`CHANGELOG.md`、`research/**` 汇总 | 不替调研员写证据文档 |
| **Researcher** | 只调研、只取证 | 自己那一个 `research/evidence/NN-*.md` | 不碰 `docs/`、不碰代码 |
| **Implementer** | 只在指定目录写代码 | 自己任务契约里声明的路径 | 不碰别的模块、不改 schema |
| **Reviewer** | 只读审查，出报告 | 自己的 `reviews/NN-*.md` | 不改被审文件 |

**铁律**：
- 一个文件同一时刻只允许一个写者。并行前先声明 `write_scopes`。
- 跨作用域修改必须先由 Lead 改契约（`team_task_update`），不许"顺手改一下"。
- 子代理之间**不得**互相修改对方的产物；发现对方有错，报告给 Lead，由 Lead 决定。

## 2 任务契约格式（每个任务开工前必须齐全）

```yaml
task_id:      # 共享任务板 id
goal:         # 一句话，可验收的终点
背景:         # 自包含上下文（子代理没有对话历史，不写就等于让它猜）
输入:         # 绝对路径（源码、文档、数据），不给路径就写"无"
写作用域:     # 精确到文件
验收标准:     # 可执行检查，不是"写得好"
禁止事项:     # 至少 3 条（含"不许改 X"）
交付格式:     # 文件路径 + 字节数 + 关键结论 N 条
```

**判据**：把这份契约单独发给一个从未参与对话的 agent，它能不提问就开工 ⇒ 契约合格。
（反例：旧项目里"继续做 W5"这种指令，压缩后必丢上下文，导致重复劳动。）

---

## 3 证据分级（所有结论必须带档）

| 等级 | 含义 | 写法 |
|---|---|---|
| `【代码级】` | 读过源码，能给 `file:line` | 必贴片段 ≤15 行 |
| `【实测】` | 本机跑过命令/查过库，有输出 | 必贴命令与关键输出 |
| `【issue级】` | 有公开 issue/PR 编号与状态 | 必贴 URL |
| `【文档级】` | 只有官方文档/README 表述 | 必须注明"未验证" |
| `【未核实】` | 没有一手证据 | 必须显式写这三个字，不许省略 |

**禁止**：
- 把 `【文档级】` 说成"已支持"；
- 把 stars / 营销页当能力证据；
- 引用数字不核口径（真实案例：把 TencentDB 单项目的 42/305 = 13.8% 说成"全赛道最高频"，数字真、命题假）。

---

## 4 完成定义（DoD）：没有证据不许说"完成"

| 改动类型 | 必须跑 |
|---|---|
| Rust/Core | `cargo check` + `cargo test` |
| 前端 | `npm run build` + `npm run lint`（或 tsc） |
| **界面** | **真机渲染截图**，与 `design/ui-hifi-v2.html` 1:1 对照（不许只看浏览器 dev 预览） |
| DB schema | 建库 + 迁移 + **旧库拒绝服务**红绿对照 |
| 检索 | 同一查询集的前后命中率对照（没有基线就先建基线） |
| API | `docs/10` 同步 + 前端类型同步 |
| 文档 | 链接可解析 + 关键术语与 `docs/08` 一致 |

**三条硬规矩**（来自本机踩坑）：
1. **证据必须是本轮的**——上一轮跑过的输出不算；
2. **修了缺陷必须给反向证据**——撤掉修复后同一检查会失败（红绿对照）；
3. **`remaining > 0` 不许说完成**。

---

## 5 交付格式（固定，不许自创）

```
做了什么：<一句话>
改了哪些文件：<列表，带行数或章节>
验证输出：<本轮命令的真实输出>
remaining：<还有几项没验证，0 才算完成>
下一步：<下一个任务编号>
```

禁止：
- 只说"已完成"不给输出；
- 用"应该没问题 / 现在应该能跑"替代运行；
- 把子代理的报告当自己的验证（Lead 必须自己看 diff 或重跑）。

---

## 6 设计变更流程（旧项目最大教训）

**任何架构/数据模型/交互规格的变更，必须做三件套**，缺一件下一个 AI 就会退回旧设计：

1. `docs/07-架构决策记录.md` 写 ADR：决策 / 背景 / 被否方案 / **不许回退的理由**；
2. 该文档末尾「已废止设计清单」追加一行（只许追加，不许删历史）；
3. 若项目有检查脚本（`scripts/check-docs.ps1`），在其废弃术语表加一条，并做四象限红绿对照。

**并且**：涉及"进程模型 / 数据模型 / 对外接口 / 用户可见交互"的变更，**必须先问用户**，不许自己论证后直接改。
（旧项目真实案例：为"不要点 4 个 exe"把三进程改成单进程多模式，用实测数据写了 ADR 说服自己，用户判定为"架构严重错误"。）

## 7 防偏三机制（每个里程碑开工前跑一次）

| 机制 | 做法 | 防什么 |
|---|---|---|
| **文档对照表** | 开工前把"设计文档的验收条目"逐条抄成 checklist，做完一条勾一条 | 只读任务分解、不读设计规格 |
| **真实数据显示** | 任何界面/统计，必须来自真实数据源，不许 mock 后说"已实现" | 假绿（角标 4 vs 待办 6） |
| **1:1 视觉对照** | 截图与设计稿并排，逐项看字号/间距/圆角/对齐 | "看起来挺好看"的业余感 |

## 8 多 agent 协作规则（Agent Teams）

| 规则 | 说明 |
|---|---|
| 只在可拆分时并行 | 独立调研、独立模块、独立验证；有先后依赖的用 `blocked_by` |
| 每个成员必须有唯一写作用域 | 在 `team_task` 里声明，冲突时由 Lead 重新切分 |
| Lead 不并行当执行者 | Lead 负责汇总、判定、写最终文档；执行交给成员 |
| 成员汇报必须带证据 | 文件路径 + 字节数 + 关键结论；否则 Lead 不采信 |
| Lead 必须等齐 | 交付前用 `list_agents` + `wait_agent` 确认所有成员结束，再给最终答案 |
| 冲突处理 | 两个成员结论矛盾时，以 `【代码级】` > `【实测】` > `【issue级】` > `【文档级】` 排序；同级则 Lead 自己复跑 |

---

## 9 会话交接（防上下文丢失）

| 时机 | 动作 |
|---|---|
| 开始 | 读 `HANDOFF.md`（≤40 行）+ `docs/07` 最近 3 条 ADR + `docs/05` 当前里程碑 |
| 过程中 | 任何"为什么这么改"立即写 `docs/07`，不要留在对话里 |
| 结束 | **重写**（不是追加）`HANDOFF.md`；`CHANGELOG.md` 追一条 |

依据：对话在上下文压缩后必丢；agent 会在两天后撤销自己之前的修复，因为它不知道当时为什么那么改。

---

## 10 红线清单（违反即返工）

1. **不许**在没有读对应设计文档的情况下开工（旧项目：没读 `docs/04` 就做了 11 个阶段）。
2. **不许**用"我觉得更好"覆盖已冻结的设计 token（字号/圆角/配色/间距）。
3. **不许**自己改数据模型而不写 ADR。
4. **不许**把"只读展示"当成"功能完成"——本项目是操作台，每个数字要能点进去。
5. **不许**在报告里混淆"设计承诺"与"已验证能力"。
6. **不许**深夜连续交付大改（旧项目 06:20/07:40/08:35 连续被否，用户通宵）。
7. **不许**把密钥/Token 打印进会话（旧项目把 WorkBuddy apiKey 打进了存档，无法回收）。
8. **不许**跳过 `remaining` 字段。

## 11 文档体系索引（写新文档前先查这里）

| 编号 | 文档 | 什么时候读 |
|---|---|---|
| 00 | 项目章程 | 新成员/新会话第一天 |
| 01 | 产品定义 PRD | 任何功能取舍 |
| 02 | 系统架构 | 动进程/服务/存储前 |
| 03 | UI/UX 设计规格 | 动界面/文案/交互前 |
| 04 | 记忆系统设计 | 动 schema/检索/注入前 |
| 05 | 研发路线图与验收标准 | 每次开工前 |
| 06 | 本文件（协同规范） | 每次会话开始 |
| 07 | 架构决策记录 ADR | 任何设计变更前 |
| 08 | 术语表 | 命名不一致时 |
| 09 | 踩坑与反模式 | 遇到"奇怪问题"时 |
| 10 | 技术栈选型 | **动界面/引依赖/选图表前必读**（唯一选型依据） |
| `PLAN.md` | 计划仪表盘 | **每次开工前必读**（当前任务/进度/门禁） |
| `plans/M<N>-*.md` | 任务卡 | 做对应任务时必读（含必读文档与待确认） |
| research/ | 调研与证据 | 做技术选型时 |

**新建文档规则**：先查上表，同主题已有有效版本 ⇒ **改它**，不要新建；确需新建必须在 `docs/05` 登记"取代谁/承接谁"。
