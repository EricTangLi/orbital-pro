# 记忆系统数据结构评审（2026-11-12）

> 问题：现在的数据结构是什么？合理吗？最佳吗？能解决调研中其他系统的问题吗？
> 依据：`docs/04 §2` 的设计 + `crates/orbital-core/src/schema.rs` 的实现 + 运行时库的实际数据

---

> **本报告的结论已由 `ADR-031` 定案**（L0 独立成表 / 删 `layer` 字段 / UI 分层卡改跨表统计）。
> 本报告是论证过程，ADR-031 是决策记录；二者冲突时以 ADR-031 为准。

---

## 0 先回答你的疑问：**设计确实不是只有一层**

`memories` 表里有这个字段：

```sql
layer INTEGER NOT NULL DEFAULT 1 CHECK(layer BETWEEN 0 AND 3),
```

**`layer 0-3` 就是 L0/L1/L2/L3。** 设计**考虑过分层**。

**但是**——我做了一次全代码搜索：

| 检查 | 结果 |
|---|---|
| `schema.rs` 里的 `layer` 定义 | ✅ 有（L21） |
| 代码里**写入** `layer` | ❌ 没有 |
| 代码里**查询/过滤** `layer` | ❌ 没有 |
| 运行时库的实际分布 | **`[(1, 50)]`** —— 50 条全是 layer=1 |

**⇒ `layer` 是"死字段"**：有列、有约束、但是**没有任何代码用它**。和 `effective_importance` 一样。

## 1 当前数据结构全貌（如实）

### 1.1 六张表

| 表 | 作用 | 关键设计 |
|---|---|---|
| **`memories`** | 主表（自由文本） | 21 个业务字段（见下） |
| **`memory_facts`** | 结构化属性（`实体/属性/值`） | 双时态（`valid_from/valid_to`） |
| **`edges`** | 图关系（5 种边） | 主键 `(source,target,type)` 天然防重 |
| **`memory_events`** | 审计链 | 任何状态变更必留痕 |
| **`agents`** | 接入状态 | `token_hash`（不存明文）、`config_sha256`（detach 校验） |
| **`memories_vec`** | 向量 | 按 agent 分区 |

### 1.2 `memories` 的 21 个字段（分成 6 组）

| 组 | 字段 | 评价 |
|---|---|---|
| 归属 | `agent_id` / `scope` / `origin` | ✅ **业界最强**：TencentDB 写入 API 都没有 agent 字段 |
| 性质 | `category` / `importance` / `confidence` | ✅ 合理 |
| **分层** | **`layer`** | 🔴 **死字段**（见 §0） |
| 来源 | `source_ref` / `session_id` | ✅ 好（能指回原文） |
| 双时态 | `created_at` / `updated_at` / `valid_from` / `valid_to` / `recorded_at` | ✅ **比 TencentDB 强**（它只有单时态） |
| 访问 | `last_accessed_at` / `access_count` | ✅ 供 EI 用（但 EI 未实现） |
| 治理 | `pinned` / `superseded_by` / `effective_importance` / `content_hash` | ⚠️ `effective_importance` 也是死值 |
| 向量 | `embedding_status` / `embedding_source` | ✅ 好（状态机可见） |
| 软删 | `deleted_at` | ✅ 零硬删 |

## 2 是否合理？——**大方向对，但有一个结构性错误**

### 2.1 做对的 6 件事（对照调研的坑）

| # | 我们的设计 | 解决的是哪个系统的哪个坑 |
|:--:|---|---|
| 1 | `agent_id NOT NULL` + 写入必填 | **TencentDB**：schema 有 agent 列，但写入 API `CompletedTurn` 没这字段 → 全落 `default` 桶（issue #995 孤儿） |
| 2 | SQL 层门控（`VISIBLE` 常量） | **mnemon**：根本没有 agent 列，多 agent 靠"各自装一份" |
| 3 | **零自动删除**（只有软删 + 可逆） | **Graphiti**：自动失效误退役率 **70%~75.6%**（`docs/09 A2`） |
| 4 | **抽取失败不推进游标 + 大声报错** | **TencentDB**：抽取失败被吞成 `{success:false}` 但游标照样前进 → 瞬时失败变**永久丢失** |
| 5 | **双时态**（`valid_from/to` + `recorded_at`） | **TencentDB 只有单时态**：分不清"事实何时为真"与"我们何时记录" |
| 6 | **去重唯一索引** `(agent_id, content_hash)` | 业界普遍靠应用层判重，会有竞态 |

**⇒ 这 6 条是设计里最硬的部分，都是"调研踩坑 → 针对性设计"。**

### 2.2 一个结构性错误：**`layer` 分层用错了方式**

**问题**：把 L0（原始对话）和 L1（提炼结论）塞进**同一张表**，只靠 `layer` 字段区分。

**为什么错**（三条）：

| # | 问题 | 后果 |
|:--:|---|---|
| 1 | **体量差异巨大** | L0 是原始对话（一个会话几万字，一年几十 MB），L1 是精炼结论（一条几十字）。同表 → L0 拖慢所有 L1 查询 |
| 2 | **字段完全不重叠** | L0 需要 `role/content/round/session_id/raw_json`；L1 需要 `importance/scope/valid_from`。同表 → 一半字段永远 NULL |
| 3 | **索引策略不同** | L0 只需要 FTS（不需要向量）；L1 需要 FTS + 向量 + 图边。同表 → 索引互相拖累 |

**对照 TencentDB**：它是**两张物理表**（`l0_conversations` vs `l1_records`），不是一张表加字段。

**⇒ 所以正确做法不是"把 layer 填上"，而是"L0 独立成表"。**

### 2.3 另一个死字段

`effective_importance`（EI，有效重要度）：公式在 `§6.1` 写得很细（借 mnemon，加来源权重），
但**从未实现**——库里全是默认值 0.5。

**好的一面**：schema 注释里已经写了"M1–M3 必须不驱动决策，禁止 ORDER BY"（我们**主动禁止用了**，不是忘了）。

## 3 是否能解决调研中遇到的问题？

| 调研发现的问题 | 我们的数据结构能否解决 | 依据 |
|---|:--:|---|
| **多 agent 归属丢失**（TencentDB #995） | ✅ **能** | `agent_id NOT NULL` + 写入必填 + SQL 门控 |
| **静默失败**（TencentDB 抽取失败被吞） | ✅ **能** | `embedding_status` 四态 + `memory_events` 审计 + health 的 `reasons` |
| **自动失效误删**（Graphiti 70%） | ✅ **能** | 零自动删除；`forget` 三档全部可逆 |
| **向量与 FTS 双路**（mnemon 无 FTS） | ✅ **能** | `memories_fts`(trigram) + `memories_vec` 并存 |
| **同内容重复存**（多 agent 互抄） | ✅ **能** | `(agent_id, content_hash)` 唯一索引 + 跨 agent `content_hash` 建 semantic 边 |
| **原文丢失导致无法重提炼**（TencentDB 的根本设计） | ⚠️ **数据模型能，实现没有** | `layer` 字段在，但没表、没代码（见 §2.2） |
| **中文检索弱**（mnemon 靠 token 交集） | ✅ **能** | FTS5 trigram + 中文 bigram |
| **时间语义混乱**（只有单时态） | ✅ **能** | 双时态（`valid_from/to` + `recorded_at`） |
| **冲突无法裁决** | ⚠️ **结构能，功能没做** | `memory_facts` 支持"同实体属性多有效值"，但 `memory_conflicts` 表还没建（M2-02） |

**小结：9 个坑里，7 个数据结构能解决，2 个是"结构够但功能没做"。**

## 4 是否"最佳"？—— **不是最佳，有两处可以更好**

### 4.1 必须改：L0 独立成表

**建议**（M3 做）：

```sql
CREATE TABLE conversations (      -- L0：原始对话，append-only
  id            TEXT PRIMARY KEY,  -- conv_<ULID>
  agent_id      TEXT NOT NULL,
  session_id    TEXT NOT NULL,
  round_index   INTEGER NOT NULL,  -- 第几轮
  role          TEXT NOT NULL,     -- user / assistant / tool
  content       TEXT NOT NULL,     -- 原文
  raw_json      TEXT,              -- 原始事件（含工具调用）
  created_at    REAL NOT NULL,
  -- 抽取状态（**关键**：失败不推进游标）
  extracted_at  REAL,
  extract_error TEXT
);
CREATE UNIQUE INDEX ux_conv_round ON conversations(agent_id, session_id, round_index);
CREATE VIRTUAL TABLE conversations_fts USING fts5(content, ...);
```

**好处**：
1. L1 查询不受 L0 体量拖累；
2. L0 可**重放**（`extracted_at IS NULL` 的就是待抽取的）；
3. 抽取失败落 `extract_error`，**不会静默**；
4. `layer` 字段就可以删掉了（物理分层后不需要逻辑标记）。

### 4.2 建议改：`memories_vec` 的分区键

现在按 `agent_id` 分区（`vec_table_partitions_by_agent` 单测验过）。
**但如果向量召回要跨 agent（shared/entity 作用域），按 agent 分区会让查询变复杂。**

**建议**：保留 `agent_id` 列（用于过滤），但**不做物理分区**——分区是优化，等基线数据说话（ADR-012）。

### 4.3 可以不改的

| 项 | 为什么不用改 |
|---|---|
| 单写队列（不用 `version` 列） | 队列串行化天然解决并发；加 version 反而诱导绕队列（§2.1 注释已说明） |
| 五张表 vs TencentDB 的十几张 | 我们的边界更窄（不做 Docker、不做多租户 team），表少是对的 |
| `edges` 五种边 | 与 mnemon 对齐，且补齐了 `temporal` 的跨 agent 过滤 |

## 5 结论

| 问题 | 答案 |
|---|---|
| **数据结构是什么？** | 6 张表：`memories`（主）+ `memory_facts`（结构化）+ `edges`（图）+ `memory_events`（审计）+ `agents`（接入）+ `memories_vec`（向量）；`memories` 有 21 个字段含双时态、软删、`layer` |
| **合理吗？** | **大方向合理**（6 处针对性设计解决了业界真实坑），**但有一个结构性错误**：`layer` 分层用"同表加字段"实现，导致字段一半永远 NULL、索引互相拖累 |
| **最佳吗？** | **不是**。应当 **L0 独立成表**（`conversations` + `conversations_fts`），同时删掉 `layer` 字段 |
| **能解决调研的坑吗？** | **9 个坑里 7 个能解决**，2 个是"结构够但功能没做"（L0 表、`memory_conflicts` 表） |
| **是只有一层吗？** | **设计有分层**（`layer 0-3` 字段 + §3.5 三层采集），**实现只有 L1**（layer 字段全默认值 1，没有 L0 表） |

---
