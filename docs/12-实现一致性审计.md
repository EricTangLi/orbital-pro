## 5 技术前置风险（必须在 T-M1-02 前解决）

**`sqlite-vec` 的接入方式未定**（`docs/04 §2.7` 要求用 `vec0` 虚表）。

`rusqlite` 自带的是 SQLite 核心能力，**`vec0` 属于 `sqlite-vec` 扩展**，必须显式加载：

| 方案 | 做法 | 风险 |
|---|---|---|
| A. 编译期静态链接 | `rusqlite` feature `loadable_extension` 或直接链接 `sqlite-vec` 的 C 源码 | 构建复杂度高，但运行时无额外文件 |
| B. 运行时加载 DLL | 打包 `vec0.dll`，启动时 `load_extension` | 需要随包分发二进制 + Windows 上要 `enable_load_extension` |
| C. 暂不用 vec0 | 向量存 `BLOB`（`memories_vec` 改为普通表），余弦在 Rust 里算 | 简单可靠，但失去向量索引加速；**10 万条以内可接受** |

**建议（待 T-M1-02 验证）**：先做 **C** 让 T-M1-02 闭环（表结构与 FTS 全部落地，向量按 BLOB + Rust 计算），把 **A/B 作为 M3 的性能升级**（届时用真实查询集测 P95 再决定是否需要 ANN 索引）。
**理由**：M3 才建召回基线（ADR-012），在没有数据前引入扩展编译风险，属于"过早优化"。
