# Orbital Pro · 产品定义（PRD v1.0）

> 方法：产品经理标准结构（Vision → Problem → Users → JTBD → Solution → Metrics → Non-goals）
> 依据：`research/00-广泛调研`（含 3 篇 2026 论文）+ 内部 5 份调研 + mnemon 库实测
> 日期：2026-11-12

---

## 1 Vision（愿景）

> **让一台电脑上的所有 AI agent 共用一套可信的记忆 —— 记得住、找得到、管得动、忘得掉。**

拆成四个动词，缺一个就不成立：

| 动词 | 含义 | 现状 |
|---|---|---|
| **记得住** | 多 agent 写进同一个库，归属清楚 | ✅ |
| **找得到** | 语义 + 关键词 + 图关系 + 结构化过滤 | 🟡 只有前两个 |
| **管得动** | 查看 + 编辑 + 合并 + 建关系 + 退役 | ❌ 几乎全缺 |
| **忘得掉** | 按有效重要度衰减、可逆退役 | ❌ 没有 |

## 2 Problem（问题定义）

### 2.1 用户的真实痛点（三条，按严重度）

| # | 痛点 | 具体表现 |
|:--:|---|---|
| **P1** | **记忆是黑箱** | 四个 agent 各记各的，用户不知道"我让它记的东西在哪、有没有记住、是不是记错了" |
| **P2** | **记忆只会涨不会老** | 重复、冲突、过期的东西越积越多，**没有任何机制让该忘的忘掉** |
| **P3** | **记忆用不上** | 记了不代表会被用上——注入到底有没有生效、花了多少 token，完全不可见 |

### 2.2 为什么现成产品不行（来自 research/C 的三硬约束）

用户 11-10 的 22 项目选型结论：

> 按「**多 agent 共享 + 本地部署 + Windows**」三条硬约束，Top 3 = basic-memory > hindsight > OpenViking。
> 其余项目要么 Windows 只有 issue 在报错、要么必须 Docker/WSL2。

**但没有一个同时满足**：
- 多 agent 共享（大多数是"给单个 agent 用"）
- 本地 Windows（多数要 Docker）
- **可操作**（大多是"API + 只读展示"）

⇒ **自研成立**。

## 3 Users（用户）

| 维度 | 描述 |
|---|---|
| **身份** | 单人使用者，本机跑 4 个 AI agent（DSH / Hermes / pi / WorkBuddy） |
| **技术水平** | 不写代码，但能看懂配置文件和命令行 |
| **核心诉求** | "看得懂、改得动、坏不了" |
| **使用频率** | 每天 1-3 次（查记忆、处理问题、接入新 agent） |

## 4 Jobs-to-be-done（用户要完成的任务）

> **注意**：JTBD 写"任务"，不写"功能"。这是产品设计与功能罗列的分界线。

| # | 当我… | 我想… | 以便… | 现状 |
|:--:|---|---|---|:--:|
| J1 | 不确定 agent 有没有记住 | **看到它最近写了什么** | 确认记忆在工作 | 🟡 |
| J2 | 发现记忆记错了 | **直接改掉或删掉** | 不让错误扩散 | ❌ |
| J3 | 库里出现重复/冲突 | **决定保留哪条，合并其余** | 库不腐烂 | 🟡 只能删 |
| J4 | 两条记忆相关 | **把它们连起来** | 召回时一起出现 | ❌ |
| J5 | 库越来越大 | **看到哪些该退役** | 控制规模 | ❌ |
| J6 | 怀疑记忆没被用上 | **看到注入次数/条数/token** | 判断值不值得开 | ❌ |
| J7 | 装了新 agent | **4 步接上** | 不用重新摸 | 🟡 |
| J8 | 系统出问题 | **一键体检 + 一键修** | 不用求人 | 🟡 |

**8 个任务，5 个完全空白（J2/J4/J5/J6/J8 的大部分）。**

## 5 Solution（方案边界）

### 5.1 产品定位

```
        ┌─────────────────────────────────┐
        │  记忆治理层（Governed Memory）    │
        │  不是"记忆库"，是"管理层"          │
        └─────────────────────────────────┘
                     ▲
     ┌───────────────┼───────────────┐
     │               │               │
  4 个 agent      注入层           人（GUI）
  （MCP）        （proxy）      （查看+操作）
```

**关键定位来自 `research/00` 的 Governed Memory 论文**：
记忆的价值不在"存"，在"**治理**"——谁能写、写成什么类型、谁能看到、什么时候失效。

### 5.2 能力架构（三层，对应论文的三层记忆层次）

| 层 | 论文对应 | Orbital 实现 |
|---|---|---|
| **I/O 层**（注入） | I/O | proxy 三协议注入 + **会话缓存**（避免每步重复查库） |
| **Cache 层** | cache | 同一会话/实体的召回结果缓存 → **省 token**（论文实测可省 50%） |
| **Memory 层** | memory | SQLite：自由文本 + **结构化属性**（Dual memory） |

### 5.3 数据模型的两个通道（Dual memory，来自论文）

```sql
-- 通道一：自由文本（现有）
memories(id, content, agent, ...)

-- 通道二：结构化属性（新增，这是"下游可用"的关键）
memory_facts(
  memory_id, entity_type, entity_id, property, value, confidence
)
```

**为什么必须有第二个通道**（论文原话）：
> 自由文本记忆"只能被相似度检索后贴进 prompt，除此之外是终点"——
> 它不能被过滤、排序、路由、同步。

### 5.4 一致性语义（论文认为最紧迫的开放问题）

多 agent 并发写同一实体时，必须有明确规则：

| 场景 | 规则 |
|---|---|
| 同一内容重复写 | `UNIQUE(agent, session, content_hash)` → 返回已有 id |
| 不同 agent 写同一实体同一属性 | **后写胜 + 保留历史**（双时态），GUI 标出冲突 |
| 同一 agent 更新自己的事实 | 走 `superseded_by` 链，旧条保留 |

## 7 Success Metrics（怎么算成功）

| 指标 | 目标 | 怎么测 |
|---|---|---|
| **可操作率** | 8 个 JTBD 里 ≥7 个能在 GUI 完成（**最终目标，落在 M6**；M2 门禁承诺 5 条，ADR-039） | 逐条点一遍 |
| **注入延迟** | p95 < 300ms（有缓存后应 <50ms） | proxy 日志 |
| **token 节省** | 相比无缓存降低 ≥30% | 对比开关缓存前后的注入 token |
| **静默失败** | 0（写入返回成功即必须能查到） | 随机抽 100 条写入后回查 |
| **跨 agent 泄漏** | 0 | 对抗查询（用 agent A 的身份查 B 的记忆） |
| **库健康** | 重复组 ≤5、冲突 ≤10、无向量缺失 | 体检 |

## 8 Non-goals（明确不做）

| 不做 | 理由 |
|---|---|
| 向量库 / embedding 模型自研 | PRD §1.3；用云 API 或 Ollama |
| 团队 / 多租户 / ACL | 单用户场景（PRD §1.3） |
| 通用 agent 适配器（支持 12 个工具） | 只服务本机 4 个 + 按需扩展 |
| 复用 dsh-mnemon 代码 | 它是 DSH 插件；只**参考设计**（docs/01 §10） |
| 技能自进化 | 前三阶段验证后再说 |
| **做成"看板"** | `docs/04` 铁律 1：必须是操作台 |
