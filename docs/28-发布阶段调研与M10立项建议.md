## 5 建议：立项 M10「可验证（Beta）」

**目标**：把「功能做完了」变成「有证据证明它对别人有用，且能被安全交付与更新」。

| 任务 | 一句话 | 验收（可勾选） | 依赖 |
|---|---|---|---|
| **T-M10-01** 产品指标实测 | 六项全局指标从"未测"→"实测 + 口径写死" | ① 8 JTBD 逐条走查通过率（目标 ≥7/8）② 注入 P95 分布（目标 <300ms，缓存 <50ms）③ 缓存开关前后 token 对照（目标省 ≥30%）④ 随机写 100 条回查静默失败数（目标 0）⑤ 160 次跨 agent 对抗查询泄漏数（目标 0）⑥ 召回基线复跑（对照 46/50·0.9267） | 无（可立即开工） |
| **T-M10-02** 真实用户内测 | 找 2~3 个**非作者**用户，各在干净机器走完「装 → 接 1 个 agent → 写 10 条 → 召回 → 忘掉」 | ① 每人一份走查记录（卡点 + 耗时）② 卡点分级（阻断/体验/文案）③ 至少修掉全部阻断级 ④ 结论写进 `evidence/beta-<日期>/` | T-M10-01（先知道该看什么）、T-M10-03 的版本号统一 |
| **T-M10-03** 发布基础设施 | 版本号统一 + 代码签名 + 自动更新 + 用户文档 + CI 最小集 | ① 三处版本号一致且有单一真源 ② 签名后安装不再显示"未知发布者" ③ updater 真机验证：0.72.x → 0.73.x 能收到并升级 ④ 一份面向用户的用户指南（拟名 `用户指南.md`，放 `docs/` 下，**当前未创建**，属 T-M10-03 产出）⑤ CI 跑通 build+test+clippy+3 个门禁脚本 | 签名证书需用户决策（花钱） |

**顺序理由**：
1. **先 01**：不需要外部人，且它是"内测该重点看什么"的输入；六项指标里任何一项不达标，内测就会变成"用户替你发现基础缺陷"。
2. **再 02**：唯一能证伪"只有作者觉得好用"的手段。按 dogfooding 的标准做法，要有**统一反馈入口**和**数字化的退出标准**（例：3 人全部完成 5 步、阻断级缺陷 = 0），否则会变成"十个爱好者好评"。
3. **最后 03**：签名要申请/花钱、更新要有用户才有意义；但**版本号统一是 0 成本的，可以立刻做**（否则内测用户报"我是 0.72.0"而 CHANGELOG 写 0.82.0，无法定位）。

**为什么不是"继续加功能"**：`docs/01 §8` Non-goals 已明确不做多租户/云端同步；现有能力已覆盖 4 个 agent 的读写与治理。在没有任何外部用户反馈前加功能，是拿开发时间赌假设。

**为什么不是"直接公开发布"**：未签名 + 无自动更新 + 无用户文档 + 无 CI/安全扫描，公开发布后用户端的崩溃与版本你都无法观测和修复，属于 Release Readiness Gate 里 Tier-1 多项 FAIL。
