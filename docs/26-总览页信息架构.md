# 总览页信息架构 v2（系统状态 + 数据状态集中展示）

> 触发：用户要求"集中展示系统情况、数据情况"，并明确工作顺序——**先分析能展示什么，再思考哪些值得展示、如何展示**。
> 配色与图表写法遵循 **ADR-033**（数据可视化标准 v3）。
> 日期：2026-11-12

---

## 1 数据源盘点（决定"能展示什么"的边界）

先看**后端现在真的能给出什么**，不看想象的指标。

| 数据源 | 已实现能力 | 现状 |
|---|---|---|
| `overview()`（`src-tauri/src/data.rs`） | 总数 / 按 agent 统计（`AgentStat`）/ 分层计数（`LayerCounts`）/ 最近写入 | ✅ 已有 |
| `list_memories` / `get_memory` / `filter_options` | 列表、详情、筛选项 | ✅ 已有 |
| `get_process_status()` | 3 进程 PID + 状态 | ✅ 已有 |
| `service.stats()` / `service.health()`（core 侧） | 统计与健康 | ✅ 有，但**未暴露给前端** |
| `memory_events`（审计链） | 每次写/改/删一条事件 | ✅ 有数据，**未聚合** |
| `conversations.extracted_at` | 待抽取积压 | ✅ 有字段，**未暴露** |
| `memories_vec` | 向量覆盖 | ✅ 有表，**未暴露** |
| recall 延迟 | **无埋点** | ❌ 要从零加 |

> 一句话：**能用的数据比界面展示出来的多**，第一步不是加功能，是把已有数据接出来。

## 2 可展示内容清单（逐条标注数据来源）

### A. 现在就有数据（改前端即可）

| # | 指标 | 来源 | 驱动什么行动 |
|:--:|---|---|---|
| A1 | 记忆总数 / 今日新增 | `overview` | 判断是否在长 |
| A2 | 按 agent 的条数分布 | `AgentStat` | 看出谁在写、谁没写 |

| A6 | 进程健康（3/3）+ PID | `get_process_status` | 出故障第一眼 |

### B. 加一条 SQL / 一个字段就能有（后端小改，1–2 小时）

| # | 指标 | 算法 | 为什么值得 |
|:--:|---|---|---|
| B1 | 待抽取积压 | `COUNT(*) FROM conversations WHERE extracted_at IS NULL` | 积压不清会导致"记了但搜不到" |
| B2 | 向量覆盖 | `memories_vec 行数 / memories 总数` | 覆盖率低 = 语义召回不可用 |
| B3 | 重复内容 | `GROUP BY agent_id, content_hash HAVING COUNT(*)>1` | 直接影响检索质量 |
| B4 | 未分类比例 | `category IS NULL` 占比 | 分类缺失会让"按类型筛选"失效 |
| B5 | 长期未访问 | `last_accessed_at < now - 90d` | 遗忘候选 |
| B6 | 各 agent 最后写入时间 | `MAX(created_at) GROUP BY agent_id` | 判断某个 agent 是否"掉线" |
| B7 | 审计事件速率 | `memory_events` 按小时分组 | 异常写入/删除的早期信号 |
| B8 | DB 与 journal 体积 | 文件 stat | 容量预警 |

### C. 需要新埋点（较贵，**M3 之后再考虑**）

| # | 指标 | 代价 |
|:--:|---|---|
| C1 | 召回 QPS / 延迟 p50/p95 | 每次 recall 要落一条记录（会显著增加写入量） |
| C2 | 注入命中率（给了几条 vs 被引用几条） | proxy 侧要解析响应 |
| C3 | 错误率（按错误码聚合） | 需要在错误出口埋点 |

### D. 明确**不展示**（虚荣指标 / 噪音）

| 指标 | 为什么不展示 |
|---|---|
| 累计写入总量（历史总和） | 只增不减，看一百次也不改变行为 |
| L2 场景块 / L3 用户画像 计数 | M3 之前恒为 0，展示就是噪音（当前已用"建议不做"文案替代，保留） |
| "系统评分" 类综合分 | 无法归因，用户看了也不知道改什么 |

## 3 筛选原则

一个指标进总览页，必须同时满足：

1. **能驱动一个动作**——看完知道"该点哪里"；
2. **有数据支撑**——不画占位饼图；
3. **异常时能变红**——正常是灰的，异常才显眼（灰色优先，ADR-033 规则 3）。

> 反例：当前 4 张指标卡里"待处理 3"没有点击入口，用户看到数字也不知道该干什么 ⇒ 新版每个数字都必须是**可点击的筛选入口**。

## 4 信息架构：三层，每层回答一个问题

```
┌ 第一层「现在正常吗」──────────────────────────────┐
│ 一键式状态条：进程 3/3 · 端点可用 · 最近写入 8 分钟前 │
│ （异常时整条变红，正常时是中性灰 + 一个小绿点）        │
└────────────────────────────────────────────────┘
┌ 第二层「里面有什么」──────────┬─────────────────┐
│ 规模与趋势（近 7 天写入）      │ 分布（按 agent / 按类型）│
│ 纯数字 + 单色条形              │ 单色条形 + 灰色底      │
└───────────────────────────────┴─────────────────┘
┌ 第三层「我该做什么」──────────────────────────────┐
│ 待办清单（每条可点击跳转到已筛选的列表）：           │
│ · 待抽取 12 条      → 记忆页（筛选：未抽取）        │
│ · 缺向量 3 条       → 记忆页（筛选：无向量）        │
│ · 重复内容 5 组     → 记忆页（筛选：重复）          │
│ · 未分类 40 条      → 记忆页（筛选：未分类）        │
└────────────────────────────────────────────────┘
```

**取舍理由**：
- 第一层放最上：用户打开应用的第一问题是"它活不活"；
- 第三层是要害：把"数字"变成"入口"，否则总览页只是仪表盘摆设；
- 第二层中间：有数据才画，没数据（如近 7 天趋势在 B 类未做前）**不画空图，直接显示"—"**。

## 5 版式与配色（对应 ADR-033）

| 元素 | 规则 |
|---|---|
| 指标数字 | 单色（`--text-primary`），不用彩色；只有异常值用 `--danger` |
| 数据条 | **实心单色**，长度编码数值；无渐变、无阴影、无圆角以外的装饰 |
| 分类色 | `--data-1..7` 固定序列（Carbon 顺序），≤7 类 |
| 非强调数据 | `--data-muted`（中性灰），让强调项跳出来 |
| 卡片 | `1px solid var(--border-subtle)` + `0 1px 2px rgba(0,0,0,.04)`；**不用 `backdrop-filter`** |
| 状态点 | 4 个语义色只用于点/徽标，不用于条形 |
| 趋势图 | 折线用同色相明度阶（浅→深表示时间），不用彩虹色 |
