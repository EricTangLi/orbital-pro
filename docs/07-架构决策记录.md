## ADR-001 独立产品，不复用 mnemon 代码

- **状态**：已采纳（2026-11-12）
- **背景**：用户已安装 `dsh-mnemon` 0.5.42 与 `@mnemon-dev/mnemon` 0.2.13，并明确说"不是复用 mnemon，而是**参考**"。
- **决策**：Orbital Pro 是独立可安装产品；借鉴 mnemon 的机制（分层、`edges`、`effective_importance`），**不引入其代码/二进制作为运行时依赖**。
- **被否方案**：
  - A. 直接读写 `~/.mnemon/data/*/mnemon.db`（零重复）→ 否：mnemon 无 `agent` 维度、schema 随版本变化、只服务 DSH 一个 agent，且违反"新电脑可独立安装"。
  - B. 把 mnemon 作为嵌入引擎（`mnemon embed` 子进程）→ 否：每次调用都是进程启动，注入热路径不可用；且它自己无多 agent 归属。
- **不许回退的理由**：一旦依赖 mnemon，用户换一台没有 mnemon 的电脑就装不上，产品定位直接崩塌。
- **影响**：需要自研 schema/检索；但可以把 mnemon 当作**只读数据源**做一次性导入（M3 的可选项）。

## ADR-002 SQLite 必须用 bundled，不用系统库

- **状态**：已采纳
- **背景**：SQLite 官方公告：WAL-reset 数据损坏 bug 存在于 **3.7.0–3.51.2**，3.51.3 才修复；本机系统库为 **3.51.1**（带 bug）。旧项目实测踩过。
- **决策**：`rusqlite` 使用 `features = ["bundled"]`，由编译期锁定 SQLite 版本，禁止链接系统库。
- **被否方案**：用系统 SQLite（体积小）→ 否：用户机器版本不可控，且已知有数据损坏缺陷。
- **不许回退的理由**：数据损坏不可逆；bundled 只增加约 1 MB 体积。
- **验证**：`cargo tree | findstr libsqlite3-sys` + 运行时 `SELECT sqlite_version()` 记录进文档。

## ADR-003 单写队列 + `BEGIN IMMEDIATE`

- **状态**：已采纳
- **背景**：SQLite 单写者模型；DEFERRED 事务在"先查重再插入"时会返回 `SQLITE_BUSY_SNAPSHOT`，`busy_timeout` 救不回来（旧项目实测）。
- **决策**：所有写走 `db::writer` 单队列，批提交（100 条或 50ms），事务显式 `BEGIN IMMEDIATE`，**先 COMMIT 再回执**。
- **被否方案**：
  - A. 多连接并发写 → 否：必然 `SQLITE_BUSY`，且分片并不会增加写并发（同一时刻只有一个写者）。
  - B. 写队列按 agent 分片 → 否：旧项目 ADR 已论证，实测 913 次/秒，分片只增加锁竞争。
- **不许回退的理由**：任何绕过 writer 的写入都会在并发下丢数据或报 BUSY。
- **已知限制**：写吞吐目标 1000/s，实测 913/s（差 8.7%），记为已知偏差而不是"已达成"。
- **例外（2026-11-12 增补，只此一条，不许扩散）**：**召回访问打点**（`last_accessed_at` / `access_count`）走读连接直接 `UPDATE`，不进写队列。
  - 为什么允许：访问计数**不是账本**——丢一次只影响排序权重，不影响任何数据的正确性、可恢复性或审计链；
    而每次读都产生一个写 job 会占用串行写队列，把真正的写入吞吐拖下来（写队列是全局单线程）。
  - 约束：①只更新本次召回命中的前 5 条；②错误一律吞掉（BUSY/锁冲突不重试）；③绝不让打点失败影响召回返回；
    ④只碰 `last_accessed_at` / `access_count` 两个字段，**不许**用它改内容、状态、软删标记。
  - 判据：`service.rs` 的 `touch_access()` 是唯一入口；若将来要给它加别的字段，必须新开 ADR。
  - 副作用提醒：这条例外意味着 `last_accessed_at` 的精度受 SQLite WAL 写者竞争影响，**不能当审计时间戳用**。

## ADR-004 三进程：单 exe spawn 子进程

- **状态**：已采纳（旧项目违反过，见下）
- **背景**：用户要求"不要点 4 个 exe"；旧项目因此做成"单进程多模式"，丢失进程隔离（用户判定为架构严重错误）。
- **决策**：一个启动器 exe，启动时 spawn 三个进程：
  - `hub-core`（记忆服务，127.0.0.1:8791，唯一写者）
  - `hub-proxy`（注入转发，127.0.0.1:8790，只读）
  - GUI（Tauri 主窗口）
  启动器负责端口检查、崩溃重启（≤3 次）、退出时优雅关闭。
- **被否方案**：单进程多模式（`--mcp/--proxy/--cli` 参数分派）→ 否：GUI 卡死会拖垮注入，proxy 崩溃会影响数据；本机 Hermes 曾因适配器阻塞事件循环 exit 75。
- **不许回退的理由**：隔离是可用性底线，且用户明确要"双击一次"——spawn 方案同时满足两者。
- **验证**：`taskkill` 掉 core → GUI 仍可响应 + 启动器在 N 秒内重启 core（M1 验收项）。

## ADR-005 身份硬门控在 SQL 层，不做后过滤

- **状态**：已采纳
- **背景**：调研中"跨 agent 串味"是高频事故（mem0 13 条 / TencentDB 10 条）。
- **决策**：
  - agent 身份由进程启动参数/凭据推导；
  - 请求里声明的 agent 只用于**比对**，不匹配返回 **403**，**绝不降级成 default**；
  - 检索 SQL 里直接 `WHERE agent = ?`（或作用域条件），不在应用层过滤。
- **被否方案**：先查全量再在内存过滤 → 否：并发下会漏，且大库内存开销不可控。
- **验证**：以 dsh 身份伪造 hermes 写入 → 403 且库内 0 行（旧项目已实测）。

## ADR-006 三通道数据模型（文本 / 结构化属性 / 图）

- **状态**：已采纳
- **背景**：非结构化记忆"只能被相似度检索后贴进 prompt，除此之外是终点"（Governed Memory 论文）；mnemon 真实库有 77,490 条 `edges`，旧项目 0 条。
- **决策**：三条通道并存：
  1. `memories`（自由文本，含 `agent`、双时态、`effective_importance`）
  2. `memory_facts`（`entity_type/entity_id/property/value/confidence`）
  3. `edges`（`source_id/target_id/edge_type/weight`）
- **被否方案**：只做文本 + 向量 → 否：无法按实体/属性过滤、无法做冲突检测、无法图扩展召回。
- **不许回退的理由**：这是"记忆表"与"记忆系统"的分界线。
- **待定**：`edges` 自动生成规则（写入时抽实体 vs 后台任务）需在 M3 用真实数据定，先写规则再实现。

## ADR-007 记忆作用域三层（private / shared / entity）

- **状态**：**待用户确认**（本轮新增设计）
- **背景**：一套库服务 4 个 agent，若只有 `agent` 列，会同时得到"互相看不见"和"互相污染"两个坏结果。
- **决策**：
  | 作用域 | 召回范围 | 典型内容 |
  |---|---|---|
  | `private`（默认） | 仅写入 agent | agent 自己的工作记忆 |
  | `shared` | 所有 agent | 用户明确要求记住的偏好/项目事实 |
  | `entity` | 按实体隔离，跨 agent 可见但必须带来源 | 实体属性（端口、路径、约定） |
- **被否方案**：单一全局库（所有记忆对所有 agent 可见）→ 否：噪声拉低召回、串味风险高。
- **待确认点**：默认作用域是否用 `private`；升级为 `shared` 是"agent 显式声明"还是"只有人能提升"。

## ADR-008 注入只读 + 超时跳过

- **状态**：已采纳
- **决策**：proxy 在热路径**只读**（cache/memory），从不写；单次注入超时 300ms 直接跳过，转发不受影响。
- **被否方案**：proxy 顺带把对话写进记忆 → 否：写放大、锁竞争，且失败会拖垮对话。
- **验证**：注入超时注入人为延迟 → 对话仍正常返回，日志记录 `inject_skipped=timeout`。

## ADR-009 遗忘必须可逆，禁止自动硬删

- **状态**：已采纳（**强约束**）
- **背景**：Graphiti 实测：4,651 条边退役 526 条，可归因的 479 条里 **75.6% 找不到任何合理替代**，人工盲标 **70% 是错误退役**——自动"忘掉"会把仍然为真的知识静默删掉。
- **决策**：四档处理，全部可逆：
  1. 时间衰减 → 只影响排序，不删；
  2. 退役候选 → 列表 + 人确认后才降权；
  3. 标记失效 → `valid_to`，保留历史，不再召回；
  4. 硬删除 → 只有人手动执行，软删 + 影响面提示 + 可恢复。
- **被否方案**：自动 `invalid_at`（Graphiti 式）→ 否：错误退役率 70%。
- **验证**：构造"宽事实 + 窄事实"用例（平台用 X / 某服务用 Y），窄事实不得退役宽事实。

## ADR-013 `effective_importance` 必须读时计算

- **状态**：已采纳（2026-11-12，来源：mnemon 代码级调研）
- **背景**：mnemon 的公式真实存在（`node.go:296-330`，半衰期 30 天），但它只在 `remember/import/gc` 时刷新，**recall 只 bump `access_count` 不改 EI**（`node.go:284-294`）。实测铁证：本机 `shared` 库 139 条活跃记忆里，按公式"现在重算"**0/139 命中**；**36 行 EI 全等 0.75**（= `0.5×1.0×1.0×1.5`，2026-10-17 批量 import 时算的），而这些行现在 `access_count` 已 32–263、按公式应 ≈4.18。⇒ 不是"没有算法"，是"算过但过期"，而 `gc --threshold` 恰恰建在这份过期数据上。
- **决策**：
  1. `ei` **读时计算**（召回排序、退役候选各算一次）；
  2. 若为性能落盘，必须带 `ei_computed_at`，且使用前校验「`ei_computed_at` > 最后访问时间 且 > 最后一条边的创建时间」，否则重算；
  3. 退役候选列表必须显示"按公式重算值"与"本次排序所用值"，避免拿过期快照做删除决策。
- **被否方案**：照抄 mnemon 的 `RefreshEffectiveImportance`（写入时算一次）→ 否：会把"写入时快照"缺陷一起继承。
- **不许回退的理由**：EI 直接驱动"该忘什么"，用过期值等于用错误的尺子做不可逆决策。

## ADR-014 不引入 AGPL 记忆库，只借机制

- **状态**：已采纳（2026-11-12，来源：开源横向对比）
- **背景**：8 个项目里**唯一严格满足"多 agent + 本地 + Windows"三项**的是 basic-memory，但它是 **AGPL-3.0**；OpenViking 同为 AGPLv3。两者都在本项目"不引入 GPL/AGPL 依赖"的红线内。
- **决策**：**只借机制，不引入包、不 fork、不复制代码**。具体借的四条落地见 `docs/04 §1.4 / §2.6 / §3.5 / §4`：
  1. `project_id` 式**向量分区键**（basic-memory `models/search.py:310-326`）；

- **被否方案**：直接把 basic-memory 装成依赖/底座 → 否：AGPL 传染性 + 无 GUI + 无 ACL + 无 agent 隔离。
- **不许回退的理由**：许可证问题一旦引入就无法"后期剔除"，且会污染产品分发。

## ADR-015 一个 exe 文件，spawn 自身成多角色进程

- **状态**：已采纳（2026-11-12）
- **背景**：用户要求"运行一个 exe 实现所有功能"；ADR-004 又要求三进程隔离。两者看似冲突，实际不冲突——**"一个 exe 文件"不等于"一个进程"**。旧项目当年被否的是"**一个进程**按参数分派所有职责"。
- **决策**：`OrbitalPro.exe` 启动后 `std::env::current_exe()` + `Command::new(...).arg("--role").arg("core"|"proxy")` spawn 自己；GUI 进程保留窗口与托盘。
  - GUI 进程 = 启动器 + 托盘 + 主窗口
  - `--role core`：无窗口，监听 :8791，唯一写者
  - `--role proxy`：无窗口，监听 :8790，只读注入
- **实现约束**：`main()` 第一件事解析 `--role`；非 GUI 分支**必须在创建任何窗口/WebView 之前**返回，否则会多出空白窗口与额外内存。
- **被否方案**：
  - A. sidecar（`externalBin` 打包 2 个额外 exe）→ 否：安装目录出现 3 个 exe，与"一个 exe"字面冲突；且 sidecar 的更新/签名要维护三份。
  - B. 单进程内嵌（core/proxy 做线程）→ 否：丢失隔离（ADR-004）。
- **不许回退的理由**：这是同时满足"单文件"与"隔离"的唯一低成本方案；回退任何一侧都会违背一条用户明确要求或一条架构约束。
- **验证**：M1 验收里必须有——`Get-Process OrbitalPro` 出现 3 个进程、`taskkill` 掉 core 后 GUI 仍在、启动器在 ≤5s 内重启 core。
- **实测（2026-11-12 T-M1-00 Spike，`spike/`）**：
  - 纯 Rust：3 进程同在 / 杀 core 后 6s 内新进程接管 8791（返回 `core`）/ 强杀 GUI 后重启识别 2 个孤儿并接管 / 退出后 0 残留、运行态文件清除；
  - 真实 Tauri：`--role core` 子进程**没有** `msedgewebview2` 子进程（GUI 有 1 个）⇒ headless 分支确实避开了 WebView2；
  - `single-instance`：启动 core **不触发** GUI 回调；启动第二个 GUI **触发** ⇒ 不误判。
  - 过程中修的两个真缺陷：孤儿 kill 后需等端口释放再 spawn；重启后必须刷新运行态文件。

## ADR-016 托盘常驻 + 单实例；不做"杀不掉"的防杀

- **状态**：已采纳（2026-11-12）
- **背景**：用户要求"程序常驻托盘，避免进程被杀掉"。
- **决策**：
  1. 关闭窗口 = 隐藏到托盘（不退出），首次提示一次；
  2. 只有托盘菜单「退出」或设置页「退出应用」才真正退出（退出时优雅关闭子进程 + flush journal）；
  3. 单实例用 `tauri-plugin-single-instance`，第二次启动**唤醒并聚焦**已有窗口；
  4. 子进程崩溃由启动器监督重启（1s/2s/4s，最多 3 次），失败则托盘标红；
  5. 开机自启为**可选**（默认关），用注册表 Run 键，不用计划任务。
- **明确不做**：Windows 服务（无托盘、交互差）、进程守护驱动、"无法被任务管理器结束"。
- **被否方案**：用 Windows 服务保活 → 否：服务不能有托盘 UI，且用户看不到状态；用驱动保护进程 → 否：属恶意软件行为，会被杀软误判，也剥夺用户控制权。
- **不许回退的理由**：把"常驻"误做成"不可关闭"，会让软件变成用户无法管理的黑盒——这与"操作台"的产品定位直接冲突。

## ADR-017 接入配置用「patch 关键字段 + 原子写 + 前滚」

- **状态**：已采纳（2026-11-12，来源：CC Switch 4.0.29 实现，`evidence/04 §4`）
- **背景**：本应用要改 4 个 agent 的配置文件（`cordis.patch.yml` / `mcp.json` / `config.yaml` / `models.json`）。这些文件里有用户自己的大量配置，写错一次就可能让 agent 起不来。
- **决策**（五件套）：
  1. **只 patch 关键字段**，不整文件覆盖——读取 → 只改 orbital 相关节点 → 写回；
  2. **原子写**：同目录临时文件 → `fsync` → `rename` 替换；
  3. **首写前字节级备份**（带 sha256），detach 时按备份还原并校验；
  4. **多文件写入前先落 `pending` 意图日志**；中途崩溃后重启**前滚**（继续完成），而不是回滚；
  5. **失败降级**：MCP 投影失败只记为警告并保留原配置，不整体报错。
- **被否方案**：
  - A. 整文件覆盖（简单）→ 否：会抹掉用户其他 provider/模型配置。
  - B. 失败后回滚到备份 → 否：回滚会连用户在应用外做的新改动一起抹掉；前滚只补完我们自己的意图，破坏面更小（这是 CC Switch 的刻意选择）。
- **不许回退的理由**：这是唯一能同时保证"改得动"与"不毁用户配置"的顺序。
- **验证**：M1 验收——接入/断开后目标文件 sha256 与备份逐字节一致；故意在写中途杀进程，重启后配置处于完整状态（前滚生效）。

## ADR-019 向量先存 BLOB + Rust 计算，暂不引入 sqlite-vec 扩展

- **状态**：已采纳（2026-11-12，来源：`docs/12` 一致性审计 §5）
- **背景**：`docs/04 §2.7` 写的是 `vec0` 虚表，但 `vec0` 属于 **sqlite-vec 扩展**，`rusqlite` 不带。要引入必须二选一：编译期静态链接（构建复杂）或运行时加载 DLL（多分发一个二进制 + Windows 要开 `enable_load_extension`）。
- **决策**：
  1. M1–M2 用**普通表** `memories_vec(memory_id, agent_id, embedding BLOB, dim, updated_at)`，余弦相似度在 Rust 里算（采样到内存，按 `agent_id` 分区过滤后再计算）；
  2. **不改** `docs/04` 的对外语义（仍然是"向量召回 + 按 agent 分区"），只换底层实现；
  3. M3 建完召回基线后，按实测数据决定是否升级到 sqlite-vec。
- **升级触发条件（任一满足才考虑引入）**：库内活跃记忆 > **5 万条**，或 recall P95 > **200ms**。
- **被否方案**：
  - 编译期静态链接 → 否：构建链复杂，且 Windows 下静态链接 C 扩展的坑未验证；
  - 运行时加载 DLL → 否：多一个需签名的二进制，分发与更新成本上升；
  - **直接不存向量** → 否：`docs/04` 的四路召回里向量是主力之一，丢掉会显著降低召回质量。
- **不许回退的理由**：在没有任何召回基线数据前引入扩展编译风险，属于过早优化；先把功能闭环、把尺子（基线）建起来，再决定要不要换引擎。
- **验证**：T-M1-02 验收里"向量能按 agent 分区查询"用**普通表 + Rust 计算**实现，性能数据留待 M3 基线阶段测。

## ADR-020 v1 schema 在 M1 交付前允许直接扩展（不写迁移）

- **状态**：已采纳（2026-11-12）
- **背景**：`T-M1-04` 需要给 `agents` 表加 `token_hash` / `token_issued_at` 两列；按常规应"改 DDL 必须 +1 版本并写迁移"。

## ADR-021 Agent 接入必须配置化（AdapterSpec），不许写死

- **状态**：已采纳（2026-11-12，用户指出：本产品要交付给其他用户，接入方式不能为本机定制）
- **背景**：T-M1-09 第一版把 4 个 agent 的路径/格式/替换逻辑写进一次性脚本（并硬编码到本机路径），
  后果是：**换个用户就完全不可用**——别人的 Hermes 不在 `%LOCALAPPDATA%`、别人装的 agent 不在名单里、
  别人可能用 Codex/Cursor/Claude Code…。这与"可交付产品"的目标直接冲突。
  旧项目 `agent-memory-hub` 已用 `AdapterSpec` 解决过同一问题（`crates/orbital-core/src/agents/adapter.rs`），
  其结论是：「**适配器配置化，不写代码**；新增 agent 只需加一条 spec」。
- **决策**：
  1. 引入 `AdapterSpec`（`crates/orbital-core/src/adapter.rs`）：用**数据**描述"怎么接入某个 agent"——
     `id / display_name / mcp_config_path（支持 %VAR% 与 ~）/ format(json|yaml) / mcp_key / supports_mcp / supports_proxy / note`；
  2. **内置 4 条**（hermes / pi / dsh / workbuddy）作为"开箱可用"的默认值；
  3. 用户可放 `~/.orbital/adapters/*.json`：**同 id 覆盖内置、新 id 直接追加**——接入新 agent 不需要改代码、不需要重编译；
  4. `attach` 系列函数只接受 `AdapterSpec`，不再接受散落的路径字符串；
  5. 每条 spec 必须带 `note`（写清该 agent 的坑），因为"路径之外的信息"才是接入难的地方。
- **被否方案**：
  - 硬编码 4 个 agent → 否：违反"可交付给其他用户"的产品前提；
  - 只提供一个"通用 JSON patch"让用户自己写脚本 → 否：用户不知道每个 agent 的配置格式差异（YAML/JSON/嵌套键），
    这正是产品该替他解决的问题；
  - 读 agent 的源码自动推断配置 → 否：不可靠且每次 agent 升级都会坏。
- **不许回退的理由**：一旦回退成硬编码，产品的"支持任意 agent"承诺就变成"支持我们测过的 4 个"，
  而且每次新增 agent 都要发版——这是把可配置问题错当成开发问题。
- **验证**：`adapter.rs` 单测（内置 4 条 / 用户覆盖同名 / 新增自定义 / 路径展开）；`attach` 由 spec 驱动。
- **与旧项目的差异（不照抄）**：旧项目把 `mcp_key` 当唯一差异点，但实测发现**同一 agent 的条目可能已存在且指向旧值**
  （Hermes/DSH 都踩到），所以本项目的 spec 额外要求"幂等判断必须比较 `command` 指向"，不能只看键是否存在。

## ADR-022 嵌入：一个模型规格 + N 个端点，兼容性靠探测句实测

- **状态**：已采纳（2026-11-12，沿用旧项目 ADR-014 的结论）
- **背景**：用户同时有本地 Ollama 与硅基流动 API，希望可配多个端点；
  但**不同模型/不同维度的向量不能混用**，混用会让召回彻底错乱（且很难被发现——相似度照样能算出一个数）。
  模型兼容性**无法靠名字判定**：实测反例——云端 `Qwen/Qwen3-Embedding-0.6B` 与本地 `qwen3-embedding:0.6b`
  是同一个模型，但名字完全不同。
- **决策**：
  1. **模型规格全局唯一一份**（`ModelSpec { id, name, dimensions }`），端点可以任意多个；
     兼容性问题从数据结构上就不存在——不是"运行时比对两个模型名"，而是"根本没有第二个模型"。
  2. 端点分 `cloud`（OpenAI 兼容 `/embeddings`）与 `local`（Ollama `/api/embed`）。
  3. **一致性验证**：用 5 条固定探测句，所有可用端点各算一遍，与基准端点逐条比余弦，
     **全部 ≥ 0.99** 才算同一向量空间（`BASELINE_PASS = 0.99`）。
  4. **维度校验前置**：写入前 `check_dimension()`，维度不符直接拒绝（换模型必须重建索引）。
  5. 配置优先级：环境变量 > `~/.orbital/secrets.json` > 内置默认；密钥永不进仓库。
- **被否方案**：
  - 「主模型 + 备模型」→ 否：主备是可用性冗余，不是"同时用两个模型"；一旦允许配两个模型，
    就永远要回答"它们兼不兼容"，而这个问题靠名字答不出来；
  - 靠模型名/版本号判断兼容 → 否：实测同名不同物、同物不同名的反例都存在；
  - 不校验直接混写 → 否：向量照样算得出数，错误会**静默**污染召回。
- **不许回退的理由**：回退成"多模型"就等于把"兼容性"从数据结构问题降级成运行时猜测问题，
  而这类错误在本项目里属于最难发现的一类（相似度永远能算出一个看起来合理的值）。
- **本机实测（2026-11-12）**：siliconflow `Qwen/Qwen3-Embedding-0.6B` 与 ollama `qwen3-embedding:0.6b`，
  5 条探测句最小余弦 **0.9992**（阈值 0.99）⇒ 判定同一向量空间。
- **另一个实测坑**：本机 `HTTP_PROXY=127.0.0.1:10808` 实为 SOCKS5，reqwest 当 HTTP 代理用会**静默超时**；
  嵌入请求默认 `no_proxy()`，需要代理的用户用 `ORBITAL_EMBED_USE_PROXY=1` 显式开启。

## ADR-023 shared 作用域的写权限三条（P1-5 定稿）

- **状态**：已采纳（2026-11-12，用户指示"调研最新权威资料 + 分析整个应用"后定稿）
- **背景**：`docs/11` 的 P1-5 只写了"shared 写权限三条"，**内容从未定义**。
  若不定义，任何 agent 都能往共享层写任意内容，共享层会迅速退化成"垃圾桶"，
  且无法追责（"这条是谁写的、凭什么算共享"）。
- **调研依据**（外部一手资料）：
  - [Equilateral AI 社区标准 agent-memory-governance](https://raw.githubusercontent.com/Equilateral-AI/EquilateralAgents-Community-Standards/refs/heads/main/patterns/agent-memory-governance.yaml)：
    "Gate memory writes by agent **role** — not all agents should have write access to shared memory stores"
  - [Letta Shared Memory](https://docs.letta.com/v1-sdk/memory/shared-memory)：共享块可设 `read_only=True`，
    "Agents can read the block but memory tools **refuse to modify** it"
  - [Mem0 Entity-Scoped Memory](https://docs.mem0.ai/platform/features/entity-scoped-memory)：
    "Mem0 **does not infer** that scope automatically"（作用域必须显式声明）
  - [SurrealDB 多 agent 共享记忆](https://github.com/surrealdb/docs.surrealdb.com/blob/8af7382b71ef84f37fe6bcb11bda0ba07fd8cb7b/src/content/agent-memory/cookbooks/build/multi-agent-shared-memory.mdx)：
    shared scope 与 supervisor/worker 两种模式
  - [Collaborative Memory (arXiv 2505.18279)](https://ar5iv.labs.arxiv.org/html/2505.18279)：
    细粒度访问控制，system / agent / user 三级
- **决策（三条，写进代码强校验）**：
  1. **`scope=shared` 必须 `origin=user_endorsed`**。
     理由：agent 自己推断出来的东西只能进 private；"共享"意味着**用户认过**。
     依据：Equilateral 的 role gating + Letta 的 `read_only` 只用于"参考数据/策略"。
  2. **升级到 shared 必须显式声明，不默认升级**。
     理由：Mem0 明确"不自动推断 scope"；静默升级会让私有信息泄漏到共享层。
  3. **shared 记忆的修改只归原写者**（其他 agent 只能读）。
     理由：Letta 的 `read_only` 语义 + 学术论文的"非对称访问"。
     其他 agent 要修正别人的 shared 记忆，只能**新建一条 + 建 `supersedes` 边**（保留历史与追责）。
- **被否方案**：
  - "谁都能写 shared" → 否：共享层会退化成垃圾桶，且无法追责；
  - "按 agent 白名单" → 否：白名单是运维负担，且没说清"写什么能共享"；
  - "默认 private，除非显式 confirm 参数" → 与决策 2 部分重合，但不够：还得约束 `origin`。
- **不许回退的理由**：一旦允许 `agent_derived` 直接写 shared，就等于承认"模型自己判断的东西可以自动成为所有 agent 的共识"——
  这正是 TencentDB 那条"缺字段填 default"同类错误的变体（把不确定的东西当成已确认）。
- **实现状态**：规则 1 已实现（`write()` 校验 + 单测）；规则 2 部分（`scope` 必须显式传，默认 private）；
  规则 3 待 M2（需要 update 时的"是否原写者"判定与 supersedes 流程）。

## ADR-024 proxy 的注入点是"改 agent 的模型 base_url"，且必须有直连兜底

- **状态**：已采纳（2026-11-12，用户提出"proxy 凭什么能拦到请求"后补齐）
- **背景**：`docs/04 §5` 画了 `agent → proxy → 上游`，但**从没写"agent 为什么会发给 proxy"**。
  这是设计的根本缺口：MCP 只能让 agent 主动查（pull），**无法在请求发出后改 prompt**。
  要让 proxy 注入，必须让它站在链路上——而 agent 默认直连上游。
- **决策**：
  1. **注入点 = 改写 agent 的模型端点**（`~/.workbuddy/models.json` 的 `url`、
     `~/.pi/agent/models-store.json` 的 `baseUrl`、或 `OPENAI_BASE_URL` 等环境变量），
     指向 `http://127.0.0.1:8790`；
  2. proxy **保存原始上游地址**（改写前从配置里读出），转发时用它；
  3. **直连兜底（硬性）**：core 不可用 / 记忆查询超时 / proxy 内部异常时，
     **原样转发到上游，绝不阻塞对话**（ADR-008 的落点）；
  4. **基址改写必须可一键还原**（`.bak.orbital` 备份 + detach）；
  5. MCP 与 proxy **并存**：MCP 负责写入与主动查询，proxy 负责自动注入。
- **被否方案**：
  - 只做 MCP、不做 proxy → 否：那就等于放弃"用户不用问，agent 也记得"这个核心价值；
  - 用系统级 HTTP 代理（`HTTP_PROXY`）→ 否：HTTPS 需 MITM 证书，安装与信任成本极高，
    且会影响该机器上**所有**程序（不只是 agent）；
  - 让 agent 每次都先调 MCP 查记忆再问模型 → 否：依赖 agent 自觉，且多一次往返；
- **不许回退的理由**：如果 proxy 不接管 base_url，"注入"就永远只是纸面功能；
  反过来，如果接管了却没有直连兜底，proxy 一挂，**用户的每一次对话都会断**——这比没有功能更糟。
- **⚠️ 2026-11-12 补充（用户质疑后）**：proxy 接管会**丢失 agent 的官方模型体系**——
  WorkBuddy 的积分/额度绑定官方端点（`~/.workbuddy/models.json` 的 `url` 与 `apiKey` 成对），
  改 `url` 后请求不再经过官方计费，**积分与模型路由全部失效**，且可能违反服务条款。
  ⇒ **proxy 必须默认关闭**，开启时明确提示"将失去 agent 官方模型与积分"，并一键可还原。
- **风险与缓解**：
  - 风险：proxy 成为单点故障；
  - 缓解：① 直连兜底（超时/异常立即原样转发）；② 熔断（连续失败 N 次后一段时间直接放行）；
    ③ GUI 明确显示"注入已关闭/降级"，不静默。
- **当前实现状态**：🔴 **未实现**（proxy 只有 `/health`）。这是 M1 验收未过项之一。

## ADR-025 采集/注入优先级：hook 旁路 > MCP > proxy

- **状态**：已采纳（2026-11-12，用户质疑"是否必须改所有 agent 的 API"后定稿）
- **背景**：`docs/04 §3.5` 原把 proxy 当注入主力。质疑成立：
  为了"注入记忆"而改写**所有** agent 的模型端点，代价过大——丢失官方模型/积分、构成单点故障、
  且每个 agent 都要改一次配置。
- **调研依据（本机代码级，非二手）**：
  - **claude-mem**（115,935 stars，20+ agent，Apache-2.0，最后推送 2026-11-11）：
    **hook 旁路**——不动 agent 的 API，hook 抓会话 → LLM 压缩 → 下次会话注入
  - **basic-memory**：`hooks/adapters/{claude,codex,pi}.py` 三家 hook 适配
  - **TencentDB**：`MemoryProxy :8096` 用 proxy（需改 base_url），并踩过
    issue #1133「网关故障对 agent 不可见，记忆消失数天」
  - 本机调研结论原话："hook 旁路采集是唯一现实可行的采集方式"
- **决策**：
  1. **hook 旁路 = 注入主力**。理由：不改配置、保官方模型与积分、覆盖 20+ agent（有实证）；
  2. **MCP = 精确操作主力**。理由：主动写/查/管理，可控可撤销，不依赖 hook 机制；
  3. **proxy = 可选高级功能，默认关闭**。唯一独有优势是"看到完整请求/响应"
     （用量统计、协议级回写）；代价是丢官方模型体系 + 单点故障。
- **被否方案**：
  - "proxy 做主力"（原设计）→ 否：代价被严重低估（见背景）；
  - "只做 MCP" → 否：MCP **无法自动注入**，等于放弃"用户不用问，agent 也记得"这个核心价值；

  这是**把记忆系统的接入成本转嫁给用户的模型配置**，且与 TencentDB 踩过的坑同型
  （网关故障导致记忆静默消失）。

## ADR-026 Hook 是注入主力（addionalContext 机制）；proxy 绝不可接管多模态端点

- **状态**：已采纳（2026-11-12，用户追问"hook 原理"与"多模型是否会失效"后定稿）
- **背景**：ADR-025 定了"hook 旁路优先"，但没说清 **hook 凭什么能注入**；
  同时未评估 proxy 接管对**多模态模型**（图像/音频/视频）的影响。
- **调研依据**：[Claude Code Hooks reference](https://code.claude.com/docs/en/hooks)（官方规范）
  - hook 是"agent 在生命周期点执行外部命令"；
  - 输入：事件 JSON 从 **stdin** 传入（含 `session_id` / `transcript_path` / `tool_name` 等）；
  - 输出：**stdout 的 JSON**，其中 `hookSpecificOutput.additionalContext` **就是注入**——
    agent 会把这段文本加进当前上下文；
  - 另有 `permissionDecision` 用于拦截/放行操作（记忆系统不用）；
  - handler 支持 5 种类型：command（最通用）/ http / mcp / prompt / agent。
- **决策**：
  1. **注入机制 = `additionalContext`**。在 `SessionStart`（或等价的会话开始点）hook 里查记忆并输出它；
  2. **采集机制 = `transcript_path`**。在 `Stop`（会话结束）/`PostToolUse` hook 里读对话文件并写入库；
  3. **hook 是注入主力**（ADR-025），因为它在会话边界工作、**完全不碰模型请求**；
  4. **proxy 只允许接管"纯文本模型"的端点**。多模态端点（图像/音频/视频）**禁止接管**，理由：
     - body 极大（base64 图片可达数十 MB），proxy 全量读进内存 → 内存与延迟压力；
     - proxy 不解析多模态 → **没有注入收益**；
     - 白白引入单点故障；
  5. proxy 必须能处理"上游是完整端点路径"的情况（如 `.../chat/completions`，不是 base）——`join_url()` 已覆盖。
- **被否方案**：
  - "hook 只做采集、注入仍靠 proxy" → 否：hook 本身就能注入（`additionalContext`），没必要为注入引入 proxy；
  - "proxy 接管所有模型" → 否：多模态无收益且有害（见决策 4）。
- **不许回退的理由**：把多模态端点也接管，等于用"单点故障 + 内存压力 + 零收益"换"统一入口"——
  而统一入口可以用 hook 的 `http` 类型实现，不必改模型端点。
- **实测状态**：hook 在四个 agent 上的**可用性未验证**（DSH/WorkBuddy 有明确线索，Hermes/pi 待测）。

## ADR-027 接入架构：MCP（存取）+ 三种注入适配；注入分"静态索引"与"动态检索"两层

- **状态**：已采纳（2026-11-12，用户问"架构是 mcp+hook+MEMORY.md 吗"与"如何注入对应记忆"后定稿）
- **背景**：经过 ADR-024/025/026 的多轮修正，接入方式已从"proxy 主力"演进为"多路并存"，
  但**没有一份文档把最终架构讲全**；更关键的是——用户指出 MEMORY.md 是静态文件，
  **它凭什么给"这次会话"注入"对应的"记忆**？
- **决策一：能力分两类，接入分四路**
  | 能力 | 手段 | 覆盖 |
  |---|---|---|
  | **存取（pull）** | **MCP**（9 工具） | 4/4 已实测 |
  | **自动注入（push）** | 见下表，按宿主能力适配 | 4/4 已找到路径 |
  | 观察全流量（可选） | proxy（改 base_url） | 默认关闭（丢官方模型/积分） |

  | agent | 注入适配 | 落点 |
  |---|---|---|
  | DSH | hook | `cordis.patch.yml` 挂 `dsh-hooks-claude-code` |
  | Hermes | hook | `config.yaml` 的 `hooks_auto_accept` |
  | pi | 扩展 | `~/.pi/agent/extensions/*.ts`（`before_agent_start` 返回 `{message}`） |
  | WorkBuddy | **文件注入** | `~/.workbuddy/user-<uid>-personal/MEMORY.md`（每次会话自动读） |

  **⇒ 架构不是"mcp + hook + MEMORY.md"三者并列，而是**：
  **MCP 是存取主干；hook / 扩展 / 文件是三种"注入适配器"，按宿主能力择一。**

- **决策二（关键）：注入必须分两层，因为静态文件无法知道"这次的问题"**
  | 层 | 机制 | 解决什么 | 局限 |
  |---|---|---|---|
  | **静态索引层** | hook `additionalContext` / pi `{message}` / MEMORY.md 区块 | 让 agent **知道"有记忆这回事"**，并看到最近的几条 | **不知道下次会问什么** → 只能是"最近/最相关的一批" |
  | **动态检索层** | MCP `memory_recall(query)` | 按**当前问题**取**对应**记忆（向量 + FTS） | 需要 agent **主动调用** |

  **⇒ 所以"通过 MEMORY.md 注入对应记忆"这个问法本身有个前提要纠正**：
  **MEMORY.md 注入的不是"对应记忆"，而是"索引 + 调用指引"。**
  "对应"是 agent 在对话中调 `memory_recall` 时才算出来的。

  这**不是妥协，而是设计的正确形态**（与 claude-mem 的结论一致）：
  1. 上下文预算有限 → 全文注入会挤爆；
  2. 会话开始前**不可能知道**用户会问什么 → "预判对应"必然猜错；
  3. 注入"索引"让模型自己判断要不要查，比硬塞更省 token 也更准。

- **决策三：静态索引层的三条硬约束**
  1. **只放索引**（标题 + ≤20 字摘要 + agent/时间），**不放正文**；
  2. **受控区块**：`<!-- orbital:begin --> ... <!-- orbital:end -->`，写入只替换这一段，
     **绝不碰用户自己的记忆内容**；
  3. **原子写**（temp + rename），因为宿主可能同时在读写该文件。

- **被否方案**：
  - "把最近 N 条记忆全文写进 MEMORY.md" → 否：文件膨胀会被宿主"限额/蒸馏"掉，且挤占上下文；
  - "会话开始时让 agent 先跑一次全量 recall" → 否：没有 query 的 recall 只能返回最近项，
    与"索引"等价但更贵；
  - "只靠 MCP，不做注入" → 否：agent 不会主动查，等于记忆系统不存在。
- **不许回退的理由**：若把注入做成"全文塞进文件"，会同时踩两个坑——
  上下文被挤爆（模型变傻）+ 文件被宿主压缩（内容丢失）；
  若只做 MCP 不注入，用户感受就是"它什么都不记得"。
- **实现状态（2026-11-12 更新）**：
  | 项 | 状态 |
  |---|---|
  | MCP 存取 | ✅ 4/4 已实测 |
  | 静态索引层生成器 | ✅ **已实现**：`orbital-mcp --sync <agent> [--limit N]` |
  | **自动触发** | ✅ **已实现**：`memory_write` 成功后异步 spawn sync（300ms 后，不阻塞回执） |
  | WorkBuddy 注入 | ✅ **已实测生效**（ORANGE-42 + 自动 sync 各一次） |
  | DSH/Hermes/pi 注入 | ⚠️ 路径已确认，**未实测生效** |
  | 动态检索接线（让 agent 主动调 recall） | ⚠️ 工具就绪，**"何时该调"的引导未做** |

  **自动 sync 实测**（本轮）：写入 1 条记忆 → 索引从 1 条自动变 2 条 → 新记忆出现在区块里 →
  用户原文一字未动。

## ADR-028 写入必须双模式：MCP 主动写 + 自动采集（与读取对称）

- **状态**：已采纳（2026-11-12，用户问"各 agent 写入记忆如何解决"后定稿）
- **背景**：ADR-027 解决了**读取**（静态索引 + 动态检索），但**写入**只做了一半——
  `memory_write` 工具就绪（4/4 agent 实测可调），但 **agent 不会主动写**：
  除非用户明确说"记住这个"，否则对话结束记忆就没了。
  这与读取的缺口是**镜像**的：读取不能只靠 pull（agent 不会主动查），写入也不能只靠 pull。
- **决策一：写入与读取一样，必须"推 + 拉"两条腿**
  | 方向 | 自动（推送） | 主动（拉取） |
  |---|---|---|
  | **读** | 静态索引层（hook/扩展/MEMORY.md 区块）✅ 已实现 | MCP `memory_recall` ✅ 已实现 |
  | **写** | **自动采集**（hook 事件 / 文件反向导入）❌ **未实现** | MCP `memory_write` ✅ 已实现 |

- **决策二：自动采集走两条路，优先级不同**
  | 路 | 做法 | 优点 | 缺点 | 优先级 |
  |---|---|---|---|---|
  | **A. hook 事件采集** | `Stop`/`SessionEnd` hook 读 `transcript_path`（完整对话文件）→ 摘要 → 写库 | 拿到**全过程**，含工具调用 | 需各 agent 有 hook；pi/WorkBuddy 需不同实现 | **中** |
  | **B. 文件反向导入** | 定期读各 agent 自己的记忆文件（`~/.mnemon/runtime/MEMORY.md`、`hermes/memories/MEMORY.md`、WorkBuddy 的 `MEMORY.md`）→ 解析条目 → 写库 | **素材已存在**（本机 4 份、合计 23 KB），零侵入、不改任何配置 | 只能拿到 agent **已沉淀**的结论，拿不到原始对话 | **高（先做这个）** |

- **决策三：文件导入的三条硬约束**
  1. **幂等**：以「来源文件 + 条目内容 hash」为去重键，重复导入不产生重复记忆；
  2. **保来源**：每条导入记忆带 `source_ref = "import:<agent>:<file>"`，可追溯"这条是从哪来的"；
  3. **只增不改**：导入只 append，不修改/删除 agent 自己的文件（单向读取）。

- **决策四：hook 采集（路 A）留给有 hook 的 agent**
  - DSH / Hermes 有 hook → 可用 `Stop` 事件采集完整对话；
  - pi 用扩展 → `agent_end` 时采集；
  - WorkBuddy 没有 hook → **只能走路 B**（读它的 MEMORY.md）。

- **被否方案**：
  - "只靠 MCP 主动写"（现状）→ 否：agent 不会自觉写，等于写入能力形同虚设；
  - "proxy 回写"→ 否：需改 base_url（丢官方模型/积分），为采集付出这代价不值得；
  - "读 transcript 全文存库"→ 否：对话原文体量巨大且噪声多，应先摘要再存。
- **不许回退的理由**：若写入只留 MCP pull，整个系统会退化成"用户手动记笔记"的工具——
  而这正是所有记忆系统失败的主因（mnemon、mem0 都踩过：靠自觉写入 = 几乎不写入）。

- **实现状态（2026-11-12 更新）**：
  | 项 | 状态 | 证据 |
  |---|---|---|
  | MCP `memory_write` | ✅ 已实现 | 4/4 agent 实测可调 |
  | **文件反向导入（路 B）** | ✅ **已实现** | `orbital-mcp --import <agent> [--dry]`；WorkBuddy 实测 **6 条导入 / 复跑 0 新增（幂等成立）** |
  | hook 采集（路 A） | ❌ 未实现 | — |
  | **全量维护命令** | ✅ **已实现** | `orbital-mcp --maintain [--dry]`：所有 agent 导入 + 更新索引 |
  | 定时自动跑 | ❌ 未实现 | 需 Windows 计划任务或 GUI 触发 |

  **全量维护实测（本轮，2026-11-12）**：
  ```
  dry-run:  dsh +15  pi +15  hermes +24  workbuddy +6   = 60 条候选
  真导入:   新增 39 / 已存在 21
  复跑:     新增 0  / 已存在 60        ← 完美幂等
  ```
  注意：`dsh` 与 `pi` 共用 `~/.mnemon/runtime/MEMORY.md` → 第一次导入 dsh 后，
  pi 的 15 条全部被判定"已存在"（**内容相同不重复存，这是正确的**）。

  **过程中修的两个真问题**：
  1. **解析器只认 `## ` 标题 → 3/4 agent 导入 0 条**。
     实测本机三种格式：WorkBuddy 用 `## `（7 个）、DSH/Hermes 用 `§` 分隔（14/9 个）。
     修：先按标题切，切不出来**降级按 `§` 切**。
  2. **身份门控拦住了跨 agent 导入**（`configured=workbuddy claimed=dsh` → 拒绝）。
     这是 ADR-005 **设计正确**的表现。修：导入只能用**当前 token 的 agent 身份**写入，

  - 复跑: 0 新增 / 6 已存在 → **幂等 ✓**
  - 端到端召回: `tauri build` ✓、`safe-delete` ✓（修 FTS bug 后）、`浏览器书签` ✗（见下）

     这正是"四路召回里必须有向量路"的原因（ADR-012 的基线要建起来）。

## ADR-029 卸载接入必须分两个动作：detach（删条目）与 restore（整体还原）

- **状态**：已采纳（2026-11-12，实现 detach 时发现 `docs/05` 验收第 9 条口径含糊）
- **背景**：`docs/05` M1 验收第 9 条写"detach 后配置文件 **sha256 还原**"。
  但实测发现：**删掉 orbital 条目后，JSON 重新序列化，sha256 与原始不同**
  （原文件可能是紧凑格式，重新 pretty-print 后字节变了）。
  ⇒ "删条目"与"字节级还原"是**两件事**，不能混在一个动作里。
- **决策**：拆成两个语义明确的操作
  | 操作 | 做什么 | sha256 | 会不会丢用户的其它修改 |
  |---|---|---|:--:|
  | **detach** | **只删 orbital 条目**，其它一字不动 | 可能变化（重新格式化） | ❌ 不丢 |
  | **restore** | 用 `.bak.orbital` **整体覆盖** | **必然还原** | ⚠️ 会丢（备份之后的修改） |
- **默认用 detach**：因为它不丢用户的其它修改（更安全）。
  restore 作为"彻底回到装机前"的显式选项。
- **detach 的实现要点**：
  1. **JSON**：只删 `mcpServers.<SERVER_KEY>`（`SERVER_KEY = "orbital"`，与 agent id 无关）；
  2. **YAML**：文本级删除 `- id: mcp-orbital` 块及其缩进内的行，**注释与其它条目保留**
     （实测 DSH 的实际格式是列表项 `- id: xxx`，首版只匹配 `id: xxx` 导致删不掉）；
  3. **没有条目时 `changed=false` 且不写文件**（保持字节不变）；
  4. **原子写**（temp + rename）；
  5. 返回处理后文件的 **sha256**，便于与备份对照。
- **被否方案**：
  - "detach 直接用备份整体覆盖"→ 否：会**丢掉 attach 之后用户自己做的修改**，
    而用户很可能在期间改过别的配置；
  - "detach 后强行 pretty-print 成原始格式"→ 否：无法可靠复原任意原始格式，
    且为"字节相等"去牺牲正确性是本末倒置。
- **不许回退的理由**：若把 detach 做成"整体覆盖备份"，一次误操作就会让用户丢掉
  接入期间的其它配置修改——这是不可逆的数据损失，比 sha256 不相等严重得多。
- **验收口径修正**：`docs/05` 第 9 条从"sha256 还原"改为
  **"detach 后不再有 orbital 条目；restore 后 sha256 与备份一致"**。
- **实现状态**：✅ `orbital-mcp --detach <agent>` 已实现；
  实测（WorkBuddy）：detach 后 orbital 消失且 JSON 合法；restore 后 sha256 完全一致（`b840dc32…`）。
  **restore 命令尚未实现**（目前靠 `.bak.orbital` 手工覆盖）。

## ADR-030 窗口可见性不得交给 window-state 插件；dev 端口必须避开 Windows 排除范围

- **状态**：已采纳（2026-11-12，实现三进程状态页时踩到两个"环境级"坑）
- **背景**：T-M1-13 真机验证时，GUI 进程活着但**主窗口永不显示**。
  排查发现两个互不相干的原因，都属于"环境/配置"而非业务代码。
- **决策一：`tauri-plugin-window-state` 不得管理 `visible`**
  - 实测：`.window-state.json` 里被写成 `"visible": false`，启动时插件把它恢复成隐藏，
    **覆盖了 `on_page_load` 里的 `show()`** → 窗口永远不出来；
  - ⇒ 要么给插件配置 `StateFlags` 排除 `VISIBLE`，要么启动时无条件 `show()`。
  - **不许回退的理由**：把可见性交给插件持久化，用户会遇到"进程在、托盘在、窗口就是不出来"，
    且**没有任何报错**——这是最难排查的一类故障。
- **决策二：dev 端口必须避开 Windows 端口排除范围**
  - 实测：`5173` 落在排除范围 **`5097-5196`**（Hyper-V/WSL 保留）→ `EACCES: listen 127.0.0.1:5173`；
  - 修：改用 `14321`，并显式 `host: '127.0.0.1'`（本机 `::1` 不可用）；
  - **排查命令**：`netsh int ipv4 show excludedportrange protocol=tcp`
- **决策三：交付物必须用 `tauri build`，`cargo build` 的 exe 只用于本地联调**
  - `cargo build` 出的 exe 走 **dev 上下文**：不内嵌前端，运行时去连 `devUrl`；
  - 双击它会看到 `ERR_CONNECTION_REFUSED`（因为没起 Vite）；
  - ⇒ 正式交付走 `tauri build`（内嵌 `dist/`），别把 dev exe 当成品。

## ADR-031 L0 原始对话独立成表；废弃 `memories.layer` 逻辑分层字段

- **状态**：已采纳（2026-11-12，数据结构评审 `docs/24` 后定案）
- **背景**：
  1. 设计里 `memories` 有一个 `layer INTEGER CHECK(0..3)` 字段，意图是**逻辑分层**（L0 原始对话 / L1 原子记忆 / L2 场景 / L3 画像）；
  2. **实现从未使用它**：全代码搜索，`layer` 只在 `schema.rs` 出现 1 次（定义），写入/查询/过滤**零引用**；运行时库 50 条记忆**全部 layer=1**；
  3. 同时 `docs/03` 的 UI 规格有分层卡（`L0 1583｜L1 166｜L2 7｜L3 1`）、`docs/02` 说"按 layer 渐进投递"、`M2` 任务卡写 `GROUP BY layer` —— **这些界面与查询建立在"layer 会被填"的假设上，但字段从不被填**。
  ⇒ 这是一个**跨文档 + 跨代码的静默矛盾**：设计稿有分层卡、任务卡有 GROUP BY、字段有定义，**唯独没有数据**。
- **决策一：L0 独立成表，不进 `memories`**
  ```sql
  CREATE TABLE conversations (          -- L0 原始对话，append-only
    id            TEXT PRIMARY KEY,     -- conv_<ULID>
    agent_id      TEXT NOT NULL,
    session_id    TEXT NOT NULL,
    round_index   INTEGER NOT NULL,
    role          TEXT NOT NULL,        -- user / assistant / tool
    content       TEXT NOT NULL,
    raw_json      TEXT,                 -- 原始事件（含工具调用）
    created_at    REAL NOT NULL,
    extracted_at  REAL,                 -- 抽取时间；NULL = 待抽取（可重放）
    extract_error TEXT                  -- 抽取失败原因（**不静默**）
  );
  CREATE UNIQUE INDEX ux_conv_round ON conversations(agent_id, session_id, round_index);
  CREATE VIRTUAL TABLE conversations_fts USING fts5(content, content='conversations', content_rowid='rowid');
  ```
  **理由（三条，都是硬约束）**：
  1. **体量差 1000 倍**：L0 一个会话几万字、一年几十 MB；L1 一条几十字。同表 → L0 拖慢所有 L1 查询；
  2. **字段零重叠**：L0 要 `role/content/round/raw_json`；L1 要 `importance/scope/valid_from`。同表 → 一半字段永远 NULL；
  3. **索引策略不同**：L0 只需 FTS；L1 要 FTS + 向量 + 图边。同表 → 索引互相拖累。
  **TencentDB 也是两张物理表**（`l0_conversations` vs `l1_records`），不是同表加字段。
- **决策二：删除 `memories.layer` 字段**
  - 物理分层后，"这条属于哪一层"**由它在哪张表决定**，不需要再存一个标记位；
  - 留着会诱导后来者"把 layer 填上"（那是错误方向），且它是**已证实从不被写入的死字段**。
- **决策三：UI 的分层卡改为"跨表统计"，不依赖 layer**
  - `L0 条数` = `SELECT count(*) FROM conversations`
  - `L1 条数` = `SELECT count(*) FROM memories WHERE deleted_at IS NULL`
  - `L2/L3` = M3 引入 scene/persona 后再各自 count
  - **`GROUP BY layer` 这种查询必须从任务卡里删掉**（字段不存在了）
- **被否方案**：
  - "保留 layer 并开始写入" → 否：会**继承同表的三个硬问题**（体量/字段/索引），修一个字段救不了结构；
  - "L0 也放 memories，只加一个 `is_raw` 布尔" → 否：只是把 `layer` 改名，问题一样；
  - "L0 不落库，只留文件" → 否：**无法重放抽取**（`docs/04 §3.5` 的核心要求是"抽取失败可以重放 l0"）。
- **不许回退的理由**：若把原始对话塞进 `memories`，会让**每条 L1 查询都扫过一年份的对话原文**——
  这是性能问题；更糟的是**字段语义崩塌**（`importance` 对对话原文无意义），
  后来者会分不清"这条是事实还是原话"。
- **迁移**：`SCHEMA_VERSION` 1 → 2。加 `conversations` 表 + 删 `layer` 列。
  旧库（v1）启动**拒绝服务并保留数据**（沿用 `db::tests::refuses_unknown_schema_version_and_keeps_data` 的语义）。
- **实现状态**：✅ **2026-11-12 已实现**（schema v2）
  - `schema.rs`：`SCHEMA_V2_ADDITIONS`（conversations + FTS + 3 触发器）、`SCHEMA_V2_DROP_LAYER`
  - `schema.rs`：**`SCHEMA_V1` 的 memories 定义已删除 `layer` 列**（新库直接建出无 layer 的 v2）
  - `db.rs`：`SCHEMA_VERSION = 2`；新库 = V1+V2；旧库（current < 2）自动迁移；**未来版本才拒绝**
  - 单测 3 个：新库有 conversations / 新库无 layer / **v1 库迁移后数据不丢**
  - `conversations` 的**写入**仍归 M3 采集层（hook/proxy 或读 agent 会话文件），当前恒空是已知状态

## ADR-033 数据可视化与配色标准 v3（**废止"渐变 + 阴影 + 多色"旧做法**）

- **状态**：已采纳（2026-11-12）
- **背景**：用户实测反馈"柱状图用阴影+颜色结合，界面看起来很脏"。
  代码取证（`src/styles.css`）：
  - `L1164` `.bar-l0 { background: linear-gradient(90deg, var(--info), #7aa2ff) }` ← **双色相渐变**
  - `L1168` `.bar-l1 { background: linear-gradient(90deg, var(--accent), #9b8bff) }` ← 渐变 + **硬编码 hex**
  - `L1046/1053` `backdrop-filter: blur(12px)` + `box-shadow: var(--card-shadow)` ← **毛玻璃 + 阴影叠加**
  ⇒ "脏"不是审美主观判断，是三条可指认的写法叠出来的。
- **一手依据**（本轮实取，HTTP 200）：

  | 来源 | 原文 | 对我们的约束 |
  |---|---|---|
  | IBM Carbon · Data viz color palettes（`carbondesignsystem.com/data-visualization/color-palettes/`） | "Multiple gradients are often inaccessible and are **discouraged** in our system… **Never use a gradient** in place of a sequential palette" | **数据元素禁止渐变**，顺序色阶代替 |
  | 同上 | 分类色板"applied **in sequence strictly** as described"，相邻色对比最大化 | 分类色有**固定顺序**，不许随机取 |
  | Datawrapper Academy（`academy.datawrapper.de/article/140`） | "**Consider the color grey as the most important color in Data Vis**" | 灰色是主色，彩色只用于强调 |
  | 同上 | "If you need **more than seven colors** in a chart, consider using another chart type" | 单图分类色 **≤7** |
  | 同上 | "**Don't use a gradient color palette for categories**"（读者会把明暗读成大小排序） | 类别不用明度阶表示 |
  | 同上 | "Use **lightness** to build gradients, not just hue" | 真要渐变只许同色相明度阶 |

- **决策（8 条硬规则，全部可机械检查）**：

  1. **数据元素零渐变**：`linear-gradient` 不得出现在 `.bar-*` / `.layer-bar` / 任何表示数值的块上。
  2. **数据条＝单色 + 长度编码**：长度承载数值，颜色只承载类别；不用颜色深浅表示大小（避免"暗示排序"）。
  3. **灰色优先**：非强调数据用中性灰阶（`--data-muted`），仅**当前选中/异常/今日新增**用强调色。一张图里彩色面积不超过 30%。
  4. **分类色 ≤7 且固定顺序**：`--data-1..7` 按 Carbon 顺序取自 Radix 色阶；第 8 个类别起改用"其它"聚合或换图型。
  5. **语义色只表状态**：`--ok/--warn/--danger/--info` 仅用于状态点、徽标、错误行；**不用于数据系列区分**。
  6. **阴影只做层级**：卡片 `box-shadow: 0 1px 2px rgba(0,0,0,.04)`；**禁止** `backdrop-filter: blur`（毛玻璃会让半透明层叠加出灰雾）；卡片边界用 `1px solid var(--border-subtle)` 而非阴影。
  7. **对比度**：正文/小字 ≥ 4.5:1，≥18px 大字 ≥ 3:1（WCAG AA，比 Datawrapper 建议的 2.5/4 更严）。
  8. **禁止互补色相邻**（红-绿、橙-蓝）用于同图相邻类别。

- **被废止**：

  | 旧做法 | 替代 |
  |---|---|
  | 数据条双色相 `linear-gradient` | 单色实心 |
  | 渐变里混硬编码 hex（`#7aa2ff` 等） | 只许引 `--data-*` token |
  | `backdrop-filter: blur` 做卡片层次 | `1px border` + 极轻阴影 |
  | 用 `--accent/--info` 直接当数据系列色 | `--data-1..7` 固定序列 |

- **判据（可加到 `check-docs.ps1`）**：`src/styles.css` 中 `.bar-*`/`.layer-bar` 规则块内出现 `linear-gradient` 即 FAIL；
  出现 `backdrop-filter` 即 WARN（过渡期）；任何 `#xxxxxx` 硬编码出现在数据元素规则内即 FAIL。

## ADR-034 GUI 写通道：过渡期由 GUI 进程直接持有 MemoryService（长期改为 core HTTP 接口）

- **状态**：已采纳（**过渡方案**，2026-11-12）
- **背景（两个实测缺口）**：
  1. **`--role core` 的 HTTP 服务从未实现**。`src-tauri/src/main.rs:62` 的 `serve_http()` 是手写
     `TcpListener`，对**任何**请求都只回一段固定 JSON：
     `{"status":"ok","role":"core","pid":…}`。它不解析方法、不解析路径、不碰数据库。
  2. **GUI 因此没有任何写通道**。`src-tauri/src/data.rs` 的 `open_ro()` 用
     `SQLITE_OPEN_READ_ONLY` 打开库，5 个 IPC 命令全是查询。前端做 `T-M2-02`（编辑）时
     `svc.update` 根本调不到。
- **决策**：
  - **过渡期**：`src-tauri` 依赖 `orbital-core`，GUI 进程内直接持有 `MemoryService`。
    这**不新增违规**——理由见下面的"现状说明"：服务层的写路径本来就不经 writer。
  - **长期**：`--role core` 实现真正的 HTTP API（`PATCH /v1/memories/:id` 等），GUI 改为 HTTP 调用，
    届时恢复"GUI 只读库"的分层。**这条写进 M2 的遗留任务，不许无限期拖**。
  - GUI 的写身份：首次启动时确保存在 `agents.id = 'gui'` 的本地 agent（display_name = "本机用户"），
    token 存本机配置（不落明文日志）。所有 GUI 发起的编辑，审计 `actor` 记为 `gui`。
- **现状说明（重要，避免下一个 AI 误判）**：红线 5 写的是「不许绕过 `db::writer` 直接 INSERT/UPDATE」，
  但**当前实现里只有 `write()`（新建）走写队列**：
  `service.rs` 有 **14 处** `conn.execute(` 直接跑在 `self.reader.conn()` 上，
  而 `update` / `forget` / `link` 全部如此（`writer.rs` 里 `conn.execute(` 为 **0** 处）。
  ⇒ 红线 5 的**字面要求与现状不符**。本 ADR 不掩盖这个事实。
- **为什么不顺手把 14 处都改成走 writer**：`writer` 的 `Job` 目前只承载 `WriteInput`（新建），
  要支持改/删/连边需要重构 `Job` 为多操作枚举 + 改批处理与回执语义，属于独立重构（估 1–2 天），
  与 `T-M2-02` 的前端 UI 混在一起做会互相牵连、无法分别验证。
- **不许回退的理由**：若继续让 GUI "读得到、改不了"，M2 里程碑的「8 个 JTBD 里 ≥6 个能在 GUI 完成」
  直接不成立——编辑是最基础的一个。
- **判据**：①GUI 发起的编辑在 `memory_events.actor` 必须为 `gui`；②编辑走的必须是
  `MemoryService::update`（唯一实现），**不许**在 `data.rs` 里再写一份版本链 SQL；
  ③长期方案完成后，本 ADR 的"过渡期"一段必须被新 ADR 取代（并入已废止清单）。

## ADR-036 合并重复 = 搬附属物（不拼内容），撤销靠 events 清单

- **状态**：已采纳（2026-11-13；T-M2-05 落地，真机验证见 `evidence/M2-05-*.png`）
- **背景**：`docs/03 §5.2` 规定三种决策（保留A删B / 保留B删A / 合并两者），
  但**没有定义"合并"到底合并什么**。多 agent 各自记录同一条事实时，两条近似重复上
  可能分别挂着不同标签、事实与关系——只删一条就会丢掉另一条的附属信息。
- **决策（5 条）**：

  | # | 决策 | 具体做法 | 理由 |
  |:--:|---|---|---|
  | 1 | **内容不拼接** | 保留 `keep` 原文，不把 `drop` 内容并进来 | 拼接会改变 `content_hash`（打破 `ux_mem_agent_content` 去重键）、让向量失效；且"近似重复"的全文拼起来只是更长的噪声 |
  | 2 | **搬 4 类附属物** | tags/entities 并集（保持 keep 顺序 + drop 独有追加）、`memory_facts` 改指、`edges` 改指 | "合并"的对象是附属物，不是正文 |
  | 3 | **facts 只删"完全同值"** | 实体+属性+值+有效期全同才去重；同属性**不同值**必须保留 | 同实体同属性多个有效值正是 `docs/04 §2.2`「冲突检测」的输入，删了就是丢信息 |
  | 4 | **edges 用 `INSERT OR IGNORE`** | 保留 keep 已有的边（不覆盖既有 weight）；改指后成自环（A→A）的边丢弃并计入 `self_loops` | 自环对图遍历无信息量；覆盖 weight 会篡改原有关系强度 |
  | 5 | **撤销靠清单，不靠反推** | `memory_events.detail` 记录 tags/entities 前后值、每条边的 old/new 三元组、自环清单、facts id 清单、被去重行的完整字段 | 合并后用户可能又改过 keep，**从当前状态反推必然算错** |

- **事务与身份**：整个合并/撤销在 `BEGIN IMMEDIATE` 事务内（失败全回滚，drop 一个字节不动）。
  GUI 走 `merge_local_owner`（`owner_of` 从库查真实 owner，ADR-034 模式）；
  MCP 走 `merge(va)`（两端都必须可见，与 `link` 同口径，防止借合并搬别人的私有记忆）。
- **被废止**：

  | 旧设想 | 替代 | 理由 |
  |---|---|---|
  | 合并 = 把两条内容拼成一条 | 合并 = 搬附属物 + 软删 drop | 破坏 `content_hash` 与向量，产物是噪声 |
  | 合并后硬删 drop | 软删（`deleted_at`，可恢复） | 合并是"去重"不是"销毁"；硬删不可逆 |
  | 撤销 = 再合并回去（或按当前状态反推） | 按 `memory_events.detail` 清单逆操作 | 反推依赖当前状态，用户改过就错 |

- **不许回退的理由**：
  ① 拼内容会让 `ux_mem_agent_content` 与 embedding 同时失效，等于把"去重操作"
  变成"改内容操作"，审计链也对不上；
  ② 硬删 drop = 用户点一次"合并"就永久丢一条，与 `docs/03 §1.3`「每个操作有回滚路径」直接矛盾。
- **判据**：①`merge` 后 `keep.content` 逐字节等于合并前；②合并后 tags ⊇ 并集、
  drop 相关 edges 数为 0；③`undo_merge` 后 A/B 的 tags/facts/edges 全部还原；
  ④`memory_events` 必须有 `merge` 与 `undo` 两类事件，`undo.detail.undo_of` 指向 merge 的 id。

## ADR-037 冲突收件箱是**表**不是视图；冲突期间不注入

- **状态**：已采纳（2026-11-13；T-M2-06 落地，真机 `evidence/M2-06-*.png`）
- **背景**：`docs/04 §7` 规定"同一 `(entity_type, entity_id, property)` 存在多个
  `valid_to IS NULL` 且 value 不同 → 冲突，进冲突收件箱"，但五张表里**没有 conflicts 表**
  （`docs/11` P1-4 列为待修，且明确要求"定为表"）。本轮把数据模型与注入行为一起定稿。
- **决策（5 条）**：

  | # | 决策 | 理由 |
  |:--:|---|---|
  | 1 | **冲突收件箱是表**（`memory_conflicts`，v3），字段含 `status`(open/resolved/ignored) / `resolution` / `resolved_at` | 视图存不下"裁决决定"；「都保留」必须能记 `ignored`，否则每次扫描都会把同组重新报出来，用户会以为处理没生效 |
  | 2 | **检测手动触发**（维护页「重新扫描冲突」，幂等） | M2 还没有 `memory_facts` 的写入路径（M3 才有），写时全表扫描是纯浪费；M3 接上 facts 后改增量检测 |
  | 3 | **冲突期间不注入**：`recall` 用 `NOT IN (memory_a, memory_b)` 排除 open 冲突关联的两条记忆 | `docs/04 §7`：持续暴露冲突记忆是唯一让所有模型都掉点的条件。裁决后（resolved/ignored）立即恢复召回 |
  | 4 | **裁决四选一**：`keep_a` / `keep_b`（把另一侧 fact 标 `valid_to=now`）/ `keep_both`（status=ignored）/ `merged`（先 merge 再标 resolved） | 对齐 `docs/03 §4.3` 的四按钮；冲突是**事实层**矛盾，裁决不删记忆内容 |
  | 5 | **重复组口径修正**：`content_hash` 相同且两条都 `valid_to IS NULL`（跨 agent），排除版本链旧条 | 原口径按"同 agent + 同 hash"统计，被唯一索引保证不可能出现 ⇒ **指标恒为 0**；且版本链旧条会被误算成重复 |

- **被废止**：

  | 旧做法 | 替代 | 理由 |
  |---|---|---|
  | 冲突用视图（不落表） | `memory_conflicts` 表（v3 迁移） | 视图存不下裁决，"都保留"永远无效 |
  | 冲突条目照常参与召回/注入 | open 期间从召回排除 | 持续暴露冲突记忆会让所有模型掉点（调研 A4） |
  | 重复 = 同 agent 同 content_hash | 重复 = 跨 agent 同 content_hash 且都有效 | 唯一索引让原口径恒为 0，是假指标 |

- **不许回退的理由**：退回视图方案 ⇒「都保留」在刷新后复活，用户无法让冲突消失；
  退回"冲突照常注入"⇒ 直接把已知让模型掉点的条件重新打开。
- **判据**：①`memory_conflicts` 存在且 `status` 只允许三值；②冲突期间 `recall` 0 命中
  （对抗测试 `conflict_memories_are_excluded_from_recall_until_resolved`）；
  ③裁决后召回恢复且另一侧 fact 已失效；④`detect_conflicts` 幂等（重复扫描不增数）。

## ADR-038 撤销 = 按审计事件逆操作；硬删不可撤销；5 秒窗口 + 活动日志

- **状态**：已采纳（2026-11-13；T-M2-07 落地，真机 `evidence/M2-07-*.png`）
- **背景**：`docs/03 §1.3` 要求"每个操作有回滚路径"。但"撤销"在本项目有**五种不同形态**
  （写回字段 / 恢复版本链 / 清 `deleted_at` / 清 `valid_to` / 按清单拆合并），
  且硬删物理删除后无从恢复。不定清楚就会出现"看起来能撤销、实际改错了东西"。
- **决策（4 条）**：

  | # | 决策 | 说明 |
  |:--:|---|---|
  | 1 | **逆操作按 `operation` 分派**（`undo_event`） | `update`→写回 `detail.before` 的 importance/tags/pinned；`supersede`→新条软删 + 旧条恢复有效 + 删 supersedes 边；`forget:soft`→清 `deleted_at`；`forget:invalidate`→清 `valid_to`；`merge`→委托 `undo_merge` |
  | 2 | **硬删无逆操作** | `undo_event` 对 `forget:hard` 明确拒绝；活动日志标"不可撤销"；只有 journal 快照可人工兜底 |
  | 3 | **supersede 撤销有安全前提** | 新版本必须仍有效且未被再次取代，否则拒绝——否则撤销会制造第三个版本，版本链语义崩掉 |
  | 4 | **两层入口** | 操作成功后 **5 秒内**页内「撤销」；超过窗口从维护页「最近操作」（活动日志）撤销。撤销本身写 `undo` 事件，`detail.undo_of` 指向原事件 |

- **被废止**：

  | 旧做法 | 替代 | 理由 |
  |---|---|---|
  | 撤销 = 再执行一次相反操作（如再改回去） | 按 events 逆操作 | 相反操作会再产生一条事件，版本链越拉越长，且回不到"操作前"这个精确状态 |
  | 撤销 = 从当前状态反推 | 读 `detail` 清单 | 用户可能已再次修改，反推必错（ADR-036 同理） |
  | 硬删也提供撤销按钮 | 明确标注不可撤销 | 物理删除后没有数据可恢复，假按钮是欺骗 |

- **不许回退的理由**：反推与"相反操作"两条都会把审计链变成噪声，且与 ADR-009（可逆遗忘）冲突。
- **判据**：①五类操作各撤销一次能回到操作前（`undo_tests` 六条测试）；②`undo` 事件
  `detail.undo_of` 指向原事件；③硬删 undo 返回 `INVALID_ARGUMENT` 且日志标"不可撤销"（测试+真机）；
  ④重复撤销被明确拒绝。

## ADR-040 图扩展不能作为独立召回通道参与 RRF（必须继承种子分数）

- **状态**：已采纳（2026-11-13；T-M3-04 的质量对照发现，证据 `evidence/graph-auto-20261113.md`）
- **背景**：T-M3-02 把图扩展做成第三路（FTS 种子的 1 跳邻居，按 `w/(k+rank)` 参与 RRF）。
  当时真实库 `edges=0`，图组与单路持平，问题被掩盖。T-M3-04 自动建边后用 fixture 边做对照，暴露：

  | 配置 | hit@1 | hit@5 | MRR |
  |---|---|---|---|
  | 单路 `fts` | 46/50 (92%) | 47/50 (94%) | 0.9267 |
  | `fts,graph` 等权 | **7/50 (14%) ⬇⬇** | 44/50 | 0.4940 |
  | `fts,graph` (2,1) | 40/50 (80%) ⬇ | 44/50 | 0.8307 |

- **根因（调试证据）**：q01 的融合 top5 全是 `channels=["fts","graph"]`（分数 ≈0.044），
  而只被 FTS 命中的正确答案只有 0.0328。两层原因：
  1. **图通道把"邻居"当独立排名**——邻居的相关性来自种子，与查询无关，却拿到 `w/(k+rank)`；
  2. **无关邻居与 FTS 弱命中叠加**——同一条邻居若同时被 FTS 的 rank 10+ 命中，`2/61+1/61` 就超过正确答案。
- **决策**：图扩展改为**继承分模式**，且**不引入新 id**：
  - 只对**已在 FTS/向量 top-K 内**的 id 做图加成：`score += seed_score × decay`（`decay` 建议 0.5，可配）
  - 不再把无关邻居塞进候选集
  - 改造任务：`T-M3-05`（不在对照任务里顺手改，避免"边改边测"）
- **被废止**：

  | 旧做法 | 替代 | 理由 |
  |---|---|---|
  | 图扩展作为独立通道，邻居按 rank 参与 RRF | 邻居继承种子分数、只对已有候选加成 | 邻居与查询无关，独立排名会系统性挤掉正确答案（实测 92%→14%） |

- **不许回退的理由**：任何"路由/邻居"类扩展（graph、related、共现）都有同样的相关性来源问题；
  它们只能**重排**或**加成**，不能自带独立排名。
- **判据**：①同一查询集 `fts,graph` 的 hit@1 **不低于**单路；②hit@5 不下降；
  ③图加成只改变已有候选的顺序，不产生新 id（测试断言 `hits ⊆ fts∪vec`）。

### ADR-040 补充（2026-11-13，T-M3-05 实施时实测）

原决策"`score += seed_score × decay`"在实践中**同样会伤 hit@1**：
RRF 下 rank0 与 rank1 只差 `1/(k+1) − 1/(k+2) ≈ 0.0005`，而 decay=0.5 的加成 ≈0.0082、
decay=0.1 仍有 ≈0.0016——**任何加法都能让弱命中反超正确答案**（实测 hit@1 46→37/38/40）。

⇒ 最终实现改为：**图连接不加分，只做"真平局仲裁"**（分数完全相同时，有图连接的优先）。
fixture 96 条边下：`fts,graph` = **46/47/0.9267**（与单路**完全一致**）；`fts,vec,graph` = 46/47/0.9300。

**如实结论**：在 RRF（按名次融合）下，图扩展**无法**在不伤 hit@1 的前提下加分——
要让它"有正面作用"，必须换融合方式（按加权分数而不是名次），那是 M4 之后的算法议题，不在 M3 承诺内。

## ADR-041 proxy 通过 core 的本地只读 HTTP 端点召回（不直读库、不起 MCP 子进程）

- **状态**：已采纳（2026-11-13；`T-M3-06` 开工前定）
- **背景**：注入要在 proxy 里完成，但 proxy 与 core 是**两个进程**，proxy 需要拿到召回结果。
  候选四条路，逐条评估：

  | 方案 | 为什么不选 |
  |---|---|
  | A. proxy 直接开 SQLite 跑召回 SQL | **绕过 service 的作用域门控**（`VISIBLE`/冲突排除/`touch_access` 口径），且 SQL 会与 core 漂移——我们做基线对照时明确"不复写 SQL"，注入路径更不能破例 |
  | B. proxy 复用 `MemoryService`（库调用） | `MemoryService::open` 会建表/迁移 schema/启动 writer 线程 ⇒ **违反"proxy 从不写库"（ADR-008）** |
  | C. core 新增**本地只读 HTTP** `127.0.0.1:8791/recall` | **采纳**：复用 service 全部门控，proxy 只发 HTTP，接口窄（一个只读端点） |
  | D. proxy 起常驻 MCP 子进程 | 进程生命周期/崩溃重启复杂度高，且 MCP 调用需要 agent 身份 token（proxy 不代表某个 agent） |

- **决策**：
  - core 新增只读端点 `GET /recall?q=<query>&agent=<agent_id>&limit=<n>`（**只绑 `127.0.0.1`**，无写路径）
  - 由 GUI（`src-tauri`）在启动时 spawn；proxy 用 `reqwest` 调它，**300ms 超时**，失败/超时一律跳过注入
  - 可选 `ORBITAL_LOCAL_TOKEN` 共享密钥（为空则不校验，仅回环可达）
  - proxy 的注入统计**写文件**（`%LOCALAPPDATA%\OrbitalPro\metrics\injection-YYYYMMDD.jsonl`），不写 DB（保持 ADR-008）
- **被废止**：无（新决策）。但**被否决** A/B/D 三条已记在上表，不许以"更简单"为由回退。
- **不许回退的理由**：A 会让门控失效——basic-memory 的共享句柄泄漏正是"绕过应用层过滤"的形态；
  B 会让 proxy 在启动时触发 schema 迁移（写库），违反 ADR-008 的硬约束。
- **判据**：①`crates/orbital-proxy` grep 无 `conn.execute`/`INSERT`；②proxy 对 core 只有 `/recall` 一种调用；
  ③core 端点绑定地址是 `127.0.0.1`（测试断言）；④超时 300ms 后原请求照发（有测试/冒烟证据）。

## ADR-042 proxy 注入只注入 `shared` 作用域的记忆（private 绝不进注入）

- **状态**：已采纳（2026-11-13；`T-M3-06` 注入冒烟时发现的真实缺口）
- **背景**：注入要在 proxy 里完成，但 **proxy 无法确认请求来自哪个 agent**
  （WorkBuddy 的 `models.json` 只配了 `url`，pi 的 `baseUrl` 同理，不带 agent 标识）。
  如果按某个固定身份召回：读到的是那个身份的记忆，可能把 A 的 private 注入给 B；
  如果全量召回：直接跨 agent 泄漏（违反 ADR-007 的 `private` 语义）。
  ← 实测证据：冒烟里 proxy 以 `proxy` 身份召回，真实库 50 条（全是 workbuddy private）→ **0 命中**。
- **决策**：proxy 的召回**只取 `scope='shared'`** 的记忆——
  "shared" 的语义本来就是"所有 agent 可见"（`docs/04 §4.1`）。`private` 永远不进 proxy 注入。
  - 实现：core 本地端点（ADR-041）加 `scope` 参数，proxy 固定传 `scope=shared`；
    端点侧召回后再按 `h.scope == "shared"` 过滤（不改 `recall` 签名）
  - 用户想让某条记忆被自动注入 → 把它标记为 `shared`（M4 的 GUI 会提供这个操作）
- **被废止 / 被否**：

  | 方案 | 为什么否 |
  |---|---|
  | 全量召回（不按 scope） | 跨 agent 泄漏 |
  | 按某个固定身份召回（如 `proxy` 或 `workbuddy`） | 读到的是那个身份的 private，同样泄漏；且换 agent 就错 |
  | 每个 agent 一个 proxy 端口来区分身份 | 配置爆炸，且用户改 base_url 时极易配错 |

- **不许回退的理由**：注入是"推"给模型的内容，用户看不到；一旦泄漏 private，
  等于把 A 的事悄悄喂给 B。scope 过滤是唯一不需要知道"请求来自谁"的安全边界。
- **判据**：①proxy 注入的条目 100% 是 `shared`（测试/冒烟断言）；
  ②以 `proxy` 身份检索 private 记忆 → 0 命中；③冒烟里 shared 记忆能被注入。

## ADR-043 entity 作用域的 fact 门禁放在**召回侧**，不是写入侧

- **状态**：已采纳（2026-11-13；全项目审计发现 `docs/04 §4.1` 的规则未落地且不可执行）
- **背景**：`docs/04 §4.1` 原文：
  > `entity` | **必须**绑定至少一个 `(entity_type, entity_id)`（至少一条 `memory_facts`），否则写入拒绝（`INVALID_ARGUMENT`）

  两个问题：
  1. **未落地**：`writer::write` 只校验了 `scope=shared` 的 origin 规则，没有任何 fact 检查；
  2. **不可执行**：`memory_facts` 是在记忆**写入之后**由 `add_fact` 添加的（T-M3-03），
     写入那一刻必然还没有 fact ⇒ 严格执行这条规则会让 **entity 记忆永远写不进去**。

- **决策**：
  - **写入允许** `scope='entity'`（不要求当时已有 fact）；
  - **召回/读取门控**要求该记忆**至少有一条有效 fact**，否则视同 `private`（只有写入者可见）；
  - 即 `VISIBLE` 从 `m.scope IN ('shared','entity')` 改为
    `m.scope='shared' OR (m.scope='entity' AND EXISTS(SELECT 1 FROM memory_facts f WHERE f.memory_id=m.id AND f.valid_to IS NULL))`
- **被废止**：

  | 旧写法 | 替代 | 理由 |
  |---|---|---|
  | entity 写入时必须已有 fact，否则 `INVALID_ARGUMENT` | 写入允许；**召回侧**要求有 fact 否则等同 private | facts 在写入后才添加，写入时校验不可执行（会锁死 entity 记忆） |

- **不许回退的理由**：把检查挪回写入侧 = 让 entity 作用域不可用；
  完全不检查 = "空实体记忆"对其他人可见，等于把一条没有事实支撑的记忆当成跨 agent 共享内容。
- **判据**：①无 fact 的 entity 记忆对**其他 agent** 0 命中；②写入者本人仍可见；
  ③`add_fact` 之后其他 agent 可见；④`docs/04 §4.1` 的表述已同步修订。

## ADR-044 旧库走**迁移**，不是"拒绝服务"

- **状态**：已采纳（2026-11-13；M7 文档收官审计发现 `docs/05` 的验收口径与实际实现不符）
- **背景**：`docs/05` M3 验收原文写的是
  > `conversations` 表建立且 schema v2 迁移通过；旧库（v1）**拒绝服务并保留数据**

  但实际实现（`db::open`）从 2026-11-12 起就是**逐版迁移**：`current < SCHEMA_VERSION` → 加表/删列 → 写回新版本。
  而且 `SchemaTooOld` 只在 `current > SCHEMA_VERSION`（**未来版本**）时触发。

  两者差别很大：**"拒绝 v1" 会让老用户升级后完全用不了**，而"迁移 v1" 让老用户无感升级。

- **决策**：**以迁移为准**（更好的用户体验，且已有真机证据 `evidence/migration-20261113.md`）：
  - `current < SCHEMA_VERSION` → **迁移**（幂等、逐步）
  - `current > SCHEMA_VERSION` → `SchemaTooOld`（拒绝，且不动数据）
  - `docs/05` 那条验收口径改为"旧库（v1）**迁移**到 v3 并保留数据；未来版本拒绝服务"
- **被废止**：

  | 旧写法 | 替代 | 理由 |
  |---|---|---|
  | 旧库（v1）拒绝服务并保留数据 | 旧库（v1）**迁移**到当前版本并保留数据 | 拒绝服务等于"升级即不可用"，与 M6 门禁"升级不丢数据"直接冲突 |

- **不许回退的理由**：一旦回退成"拒绝旧库"，已经升级过的用户（库是 v3）不受影响，但**任何停在中途版本的用户**
  都会被挡在门外；而且 M6-03 已用真机证明迁移不丢数据，没有理由再退回去。
- **判据**：①造 v1 库（带数据）→ 打开后 `user_version=3` 且行数不变；②造 v4 库 → `SCHEMA_TOO_OLD` 且版本仍为 4。
  （两条都在 `db::migration_tests` 里，`cargo test -p orbital-core migration_tests` 可复跑。）

## ADR-045 「宽事实不被窄事实退役」判据**废止**（不做语义宽窄判断）

- **状态**：已采纳（2026-11-13；M7 文档收官发现 `docs/05` M4 有一条无法验收的条目）
- **背景**：`docs/05` M4 验收原文：
  > 至少 1 条"错误退役"的防护测试：**宽事实（平台用 X）不被窄事实（某服务用 Y）退役**

  问题：**"宽/窄"是语义判断**，不是可观测量。同一句"平台用 X"在不同上下文里宽窄不同，
  要靠 LLM 或人工读语义才能分辨。而退役逻辑（`effective_importance` + 免疫规则）是**纯数值函数**，
  它不读语义。

- **决策**：**废止这一条验收**，理由是：
  - 免疫规则（pinned / importance ≥ 4 / access ≥ 3 / 创建 < 24h）已经在防止"重要记忆被退役"，
    这是**可验证的**（`retirement_tests` 有 3 条）；
  - 要做"宽窄判断"只能在退役前插一次语义分类，成本高且**误判后果不对称**：
    把窄事实误判成宽事实 → 该退役的永远不退役（库越积越脏）；
  - 真正的"错误退役"风险已被**可逆性**接住：降权只降 1 档、永不物理删除、5 秒撤销 + 恢复入口
    （M4 的 T-M4-02/03/05 已实现并真机验证）。
- **被废止**：

  | 旧写法 | 替代 | 理由 |
  |---|---|---|
  | 宽事实不被窄事实退役（语义判断） | 免疫规则（pinned/imp≥4/acc≥3/24h）+ 可逆降权（永不物理删除） | "宽窄"不可度量；误判代价不对称；可逆性已覆盖真实风险 |

- **不许回退的理由**：一旦引入"语义宽窄"再退役，就等于**用不可靠判断决定记忆去留**；
  而当前设计是"宁可少退役，也不误删"——这个方向不该被推翻。
- **判据**：①免疫规则有测试（`retirement_tests`）；②降权后行数不变（`retire_tests`）；
  ③降权可撤销（5 秒 + 活动日志）。三条均已有测试/真机证据。

## ADR-046 「对话重放抽取」验收**废止**（列与索引保留，抽取能力不做）

- **状态**：已采纳（2026-11-13；T-M9-01 逐条清理时发现 `docs/05` M3 这条从未实现）
- **背景**：`docs/05` M3 原文：
  > `extracted_at IS NULL` 的对话可被重放抽取（造一条失败样本验证）

  实际状况（本轮 grep 全体 `crates/**`）：
  - `conversations.extracted_at` **列存在**、部分索引 `WHERE extracted_at IS NULL` **也建了**；
  - 但**没有任何代码读写它**（无 replay / extract 函数）。

  也就是说：表结构为"将来抽取"留了位，**抽取能力本身从未实现**。

- **决策**：**废止该条验收**，理由：
  1. **抽取需要语义能力**（把一段对话判定成"值得记住的事实"），不是纯代码可定；
     用规则硬抽会产出大量噪声记忆，反而污染库（与"忘记比记住重要"的 M4 方向相反）；
  2. **与现有写入路径重复**：4 个 agent 都通过 MCP 工具**主动写**记忆，
     比"事后从对话里猜"更准、更省 token；
  3. 列与索引**保留**（成本为零，为将来"本地模型抽取"留位），但**不承诺**何时实现。
- **被废止**：

  | 旧写法 | 替代 | 理由 |
  |---|---|---|
  | `extracted_at IS NULL` 可重放抽取 | 由 agent 主动 `write()` 写入；列/索引保留为将来留位 | 抽取需语义判断，规则抽取会污染库；主动写入更准 |

- **不许回退的理由**：一旦"自动从对话抽取"成为默认，用户会失去对"库里存了什么"的控制；
  而本项目反复强调"宁可少记，不可乱记"（M4 遗忘 + ADR-045）。将来做也必须**默认关闭 + 可审阅**。
- **判据**：`docs/05` 该条改为删除线 + 本 ADR 编号；`conversations.extracted_at` 列保留（`schema.rs` 不动）。

## ADR-047 合并撤销必须区分「合并创建的边」与「keep 原有边」（按 `inserted` 标志）

- **状态**：已采纳（2026-11-13；T-M10-04 实现，红绿测试 `merge_undo_keeps_existing_edge_of_keep`）
- **背景**：M10 走查（`evidence/M10-01-metrics/op-8jtbd.md`）后复核发现——
  当 `keep` 与 `drop` **都有指向同一第三方、同 `edge_type`** 的边时：

  1. merge 的 `INSERT OR IGNORE` 因主键 `(source_id,target_id,edge_type)` 冲突被**忽略**（keep 原边保留，这步是对的）；
  2. 但 `moved_edges` **无条件**记录这条"新边"（`:2805-2831`）；
  3. `undo_merge` **无条件** `DELETE` 这条"新边"（`:2987-2995`）⇒ 删掉的是 **keep 原有的边**；
  4. 随后只 `INSERT` 回 drop 的旧边 ⇒ **keep 原边永久丢失**。

  实测（SQL 层模拟，副本库）：`A→C 0.5` + `B→C 1.0` → merge → `A→C 0.5`（正确）→ undo → **`A→C` 消失**。
  端到端已由新测试复现（修复前 `left: 0, right: 1` 红，修复后绿）。

- **决策**：
  1. `merge_inner` 记录 `inserted = tx.execute("INSERT OR IGNORE ...")? > 0`，写进 `edges_moved` 的每一项；
  2. `undo_merge` **只在 `inserted != false` 时** DELETE 新边；`inserted=false` 表示"这条边本来就在 keep 上"，不碰；
  3. 旧 merge 事件没有 `inserted` 字段 → `unwrap_or(true)` **保持旧行为**（不破坏历史撤销）；
  4. `MergeOutcome.edges_moved` 与结果文案的"搬走 N 条关系"只算**真正插入**的边；
  5. **"keep↔drop 的边变自环被丢弃"维持现状**——那是有意设计（自环对图遍历无信息量），
     且 `undo_merge` 有专门分支恢复（`:3013-3023`），不属于本缺陷。
  6. 结果文案追加"；N 条边变成自环已丢弃"（有自环时才显示）。

- **被否方案**：

  | 被否做法 | 为什么不行 |
  |---|---|
  | undo 时用 `created_at` 判断"边是否合并前就有" | `INSERT OR REPLACE` 会覆盖时间戳，无法可靠区分（`docs/29` §2.3） |
  | undo 干脆不 DELETE，只 `INSERT OR REPLACE` 回旧边 | 合并时**真正新建**的边会残留（变成指向已恢复 drop 的幽灵边） |
  | 合并时先删 keep 的同 key 边再插入 drop 的 | 会用 drop 的权重/元数据覆盖 keep 的，属于"静默改数据" |
  | 把自环也恢复成边 | 自环对图遍历无意义，正是 `docs/04` 图扩展要排除的形态 |

- **不许回退的理由**：撤销是本项目对用户的核心承诺（"每个操作有可回滚路径"，`docs/03 §1.3`）。
  一个"撤销后反而丢数据"的路径，比不提供撤销更糟——用户会以为数据已经回来了。
  另外这条缺陷**只在特定边形态下触发**（两个重复条都有同类边），一旦回退，会长期潜伏。

- **判据**：
  - 新测试 `merge_undo_keeps_existing_edge_of_keep` 必须存在且绿；
  - `cargo test --workspace` 全绿（当前 129 个）；
  - 代码位置：`service.rs` 的 `merge_inner` 边循环与 `undo_merge` 的 `edges_moved` 分支。

## ADR-048 `total` 口径保持「排除软删」，版本链旧条用**界面加注**显式化（不改 SQL 语义）

- **状态**：已采纳（2026-11-13；T-M10-05 实现）
- **背景**：M10 走查时界面「记忆 89 条」与库内 `memories` 95 行不一致。复核结论（`docs/29` §4）：
  - 差 6 条是**软删**（`deleted_at IS NOT NULL`），`89 + 6 = 95` 自洽，且与"可恢复 6 条"同源 ⇒ **这部分完全正确**；
  - 但 89 里有 **1 条版本链旧条**（`superseded_by` 非空，`deleted_at` 仍为 NULL）⇒ 真正"三空有效"只有 88；
  - 口径不一致：召回已过滤 `valid_to`（T-M2-04），但**列表与总数不过滤 `superseded_by`**。

- **决策**：
  1. **不改 `total` 的 SQL**（仍是 `deleted_at IS NULL`）——它被总览、托盘、体检、备份校验四处消费，改语义会连锁；
  2. `Overview` 新增 `total_history`（`superseded_by IS NOT NULL OR valid_to IS NOT NULL` 且未软删的条数）；
  3. 界面在记忆数旁加注「当前有效 N · 历史版本 M」，**M = 0 时不显示**（不干扰正常用户）；
  4. `docs/04` 写清两个口径各自的含义与消费方。

- **被否方案**：

  | 被否做法 | 为什么不行 |
  |---|---|
  | 把 `total` 改成"三空有效" | 「记忆 90」会突然变 88，用户第一反应是"数据丢了"；且历史版本从列表消失（有人要看历史） |
  | 只在 `docs/04` 写文档、界面不动 | 文档解决不了用户在界面上的困惑（`docs/29` §4.3 方案 C 的缺点） |
  | 列表也过滤 `superseded_by` | 与 `total` 同步变，但用户失去"查看旧版本"的入口，且要动 `list_memories` 的 where 拼接（风险高于收益） |

- **不许回退的理由**：`total` 是四个消费方共用的数字。任何"静默改变它含义"的改动都会同时影响总览、托盘角标、体检判据与备份校验，
  而这些地方都没有"口径版本"标记——回退时无法判断哪份快照对应哪个口径。
  加注方案把差异**摆在台面上**，不改变任何已有语义。

- **判据**：
  - 副本库 SQL 对照：`total=89` / `total_history=1` / `真正三空=88`；
  - 界面：历史版本为 0 的库不出现加注；
  - `docs/04` 有一节明确写两个口径。

## ADR-049 注入统计**只读 proxy 的 metrics JSONL**，不建表、不写库；MVP 不按 agent 分组

- **状态**：已采纳（2026-11-14；T-M10-06 实现，3 个单测）
- **背景**：PRD J6「怀疑记忆没被用上 → 看到注入次数/条数/token」，走查时**GUI 无任何入口**（`evidence/M10-01-metrics/op-8jtbd.md`）。
  但数据其实已经在：`crates/orbital-proxy/src/main.rs` 的 `record_metric` 每次注入写一行
  `%LOCALAPPDATA%\OrbitalPro\metrics\injection-YYYY-MM-DD.jsonl`，
  字段 `{ts, protocol, hits, tokens, elapsed_ms, status, cache}`。缺的只是"读 + 展示"。

- **决策**：
  1. **数据源就是 JSONL**：`status::injection_stats(days)` 只读文件聚合，**不新建 SQLite 表、不写库**
     （ADR-008 红线：proxy 从不写库；读侧也不许借机落库）；
  2. **窗口按"文件名的日期"截断**（不是 mtime）：目录一天一个文件，取最后 N 天聚合，语义稳定；
  3. **四种空态分别返回原因**，前端分别显示，不给 `0%` 假绿（对齐 M9-01 的 waived 口径）：
     `no-dir`（proxy 从没写过）/ `no-file` / `no-rows` / `all-off`（有请求但全未注入）；
  4. **MVP 不按 agent 分组**：JSONL 里没有 agent 字段（proxy 只看到 HTTP 请求）；
     要分组需 agent 侧传头（改 4 个 agent 配置），列为增强项（`docs/30 §2.3`）；
  5. **不跟状态页的 3 秒轮询**：统计只在切窗口时读一次——3 秒扫一次文件是无谓 IO；
  6. **不引入图表库**：趋势用内联柱（`docs/10` 只特批 recharts + Cytoscape）。

- **被否方案**：

  | 被否做法 | 为什么不行 |
  |---|---|
  | 新建 `injection_metrics` 表、proxy 写库 | 违反 ADR-008（proxy 热路径不写库）；且内存表会与 JSONL 两处真相 |
  | 用 mtime 判断"最近 N 天" | 文件被复制/备份会改 mtime，窗口会漂；文件名日期是确定值 |
  | 空态一律显示 0 | 用户会以为"注入了但没省 token"，实际可能是开关没开（`all-off`） |
  | 按 agent 分组（用 URL/头猜） | proxy 看不到稳定身份；猜错会给出错误的归因 |
  | 引入 recharts 画趋势 | `docs/10` 只特批 recharts+Cytoscape；一个 7 根柱不值得加库 |

- **不许回退的理由**：把统计落进 SQLite 会让"proxy 从不写库"这条红线失效
  （一旦允许，下一次就会有人"顺手"在注入热路径里写库）。JSONL 已经是 append-only 的真相，
  读侧聚合是纯函数，坏了可以删目录重来，不影响记忆库。

- **判据**：
  - 单测 3 个：`aggregates_fixture_and_counts_bad_lines`（聚合并跳过坏行）、
    `reports_four_empty_reasons`（四种空态）、`window_keeps_last_n_days`（窗口截断）；
  - 真机：状态页「注入统计」卡片可切今日/7 天/30 天；空目录显示 `no-dir` 文案。

## ADR-050 `--role proxy` 必须 spawn 真正的 `orbital-proxy.exe`，禁止空壳冒充

- **状态**：已采纳（2026-11-14；0.91.0 修复）
- **背景**：M10 要求证明"注入能用"，实测发现**系统里从未有过一条 `status="on"` 的注入记录**。
  追查两层原因：
  1. **`src-tauri/src/main.rs` 的 `"proxy"` 分支调的是 `serve_http`**——它对**任何请求**
     都返回同一份 `/health` JSON（`:110-124`），**不转发、不注入**；
     真正的 `crates/orbital-proxy` 二进制**从未进过安装包**（安装目录只有 `OrbitalPro.exe` + `orbital-mcp.exe`）。
  2. 库内 89 条记忆全 `private`、0 条 `shared`（注入按 ADR-042 只注 shared）。
  后果：核心卖点"自动注入"在发布版里根本不存在，而界面「3/3 进程健康」是**假绿**（空壳也回 health）。

- **决策**：
  1. `--role proxy` 改为 **spawn `orbital-proxy.exe`**（同目录），透传其退出码；
     **找不到二进制就报错退出**，绝不用空壳假装"proxy 已就绪"；
  2. `tauri.conf.json` 的 `bundle.resources` 必须包含 `orbital-proxy.exe`（与 `orbital-mcp.exe` 同级）；
  3. 判据：真 proxy 对 `POST /chat/completions`（无 upstream）返回 **502 `upstream_not_configured`**，
     而不是 health JSON——这是"壳 vs 真"的一行可验证差异。

- **被否方案**：

  | 被否做法 | 为什么不行 |
  |---|---|
  | 保留空壳，把注入逻辑塞进 `serve_http` | 那等于把 async reqwest + 注入管线搬进 GUI 主程序，破坏"三进程隔离"（ADR-004） |
  | 空壳也吐一份假的 `inject:"on"` 让界面好看 | 假绿；本轮已经踩过一次（3/3 健康但注入不存在） |
  | 只改打包、不改 `--role proxy` | spawn 的仍是空壳，问题不变 |

- **不许回退的理由**：空壳的健康响应与真 proxy 的**格式不同**（真 proxy 有 `upstream_configured` / `inject` / `core_url` 字段）。
  如果回退成空壳，界面与体检都无法区分"proxy 还活着"与"proxy 根本没在工作"——
  这正是本轮"3/3 健康却零注入"的根因。宁可启动失败（可见），也不要静默成功（不可见）。

- **判据**：
  - 安装目录存在 `orbital-proxy.exe`；
  - 进程树里 `--role proxy` 的子进程是 `orbital-proxy.exe`；
  - `POST /chat/completions` → 502 `upstream_not_configured`；
  - 配假 upstream 后 100 次请求全部 `x-orbital-inject: on(3)`，metrics `status="on"`（`evidence/M10-01-metrics/injection-first-success.md`）。

## ADR-051 proxy 配置走 `proxy.conf.json`（界面可编辑），环境变量降为回退；保存后由 watchdog 重启

- **状态**：已采纳（2026-11-14；T-M10-11 实现，0.91.1）
- **背景**：`ADR-050` 修好"空壳 proxy"后，用户要开注入仍得自己设 `ORBITAL_UPSTREAM` / `ORBITAL_INJECT`
  环境变量并重启 GUI——**界面里没有任何入口**（`docs/16` 说上游配置属 M3，但从未落地）。
  环境变量的根本问题是：它只能在**进程 spawn 时**确定，用户改不了运行中的进程。

- **决策**：
  1. 新增配置文件 `%LOCALAPPDATA%\OrbitalPro\proxy.conf.json`：
     `{ "upstream": "...", "inject": true, "core_url": "http://127.0.0.1:8799" }`；
  2. **优先级：文件 > 环境变量 > 默认**（保持开发期用 env 的习惯仍然可用）；
  3. proxy 启动时读该文件；文件不存在/格式坏 → 只 warn 并回退（**不拒绝服务**）；
  4. GUI 保存流程：原子写文件（tmp + rename）→ **kill `--role proxy` 子进程** →
     启动器已有的 watchdog（指数退避）自动拉起新进程 → 新进程读新配置；
  5. 设置页新增一组「上游与注入」（输入框 + 开关 + 保存按钮 + 当前生效来源 + 文件路径）。

- **被否方案**：

  | 被否做法 | 为什么不行 |
  |---|---|
  | proxy 加 `/reload` 端点做热重载 | 要处理并发请求中途换配置、缓存失效等状态；而"重启一个新进程"语义最干净 |
  | 直接改环境变量 | 进程环境不可变；改了要重启整个 GUI |
  | 用 SQLite 存配置 | 配置是"启动期只读、人改一次"的数据，属于文件而非账本；且 proxy 不该连库 |
  | 让 proxy 监听文件变化自动重载 | 引入 inotify 复杂度与半更新窗口；保存后显式重启更可预测 |

- **不许回退的理由**：这类"用户要改但只能靠环境变量"的配置，是**发布版最常见的能力漏洞**
  （本轮 ADR-050 的空壳 proxy 就是同一条链上的问题）。有了文件 + 显式重启，
  "配置在哪、谁改了、什么时候生效"三件事都可见；回到纯环境变量就再次不可见。

- **判据**：
  - 设置页「上游与注入」组可见，保存后显示"proxy 正在重启"；
  - 保存后 `proxy.conf.json` 存在且内容正确；
  - proxy 重启后 `/health` 的 `inject` 字段与配置一致。

## ADR-052 注入主通道改为"挂 agent 生命周期"（provider/hook），proxy 降级为可选

- **状态**：已采纳（2026-11-14；定位审计后修正）
- **背景**：用户 2026-11-14 指出"设计目标没达到，Orbital 变成了外挂共享库"。
  审计（`docs/31-产品定位审计与真正实现路径.md`）确认：
  1. **hook 注入完全没做**——全仓 grep `hook|additionalContext|SessionStart` 在业务代码 **0 命中**；
  2. `docs/04 §5` 把 **proxy 写成唯一注入路径**，而 `ADR-025` 早已改成"hook 优先"——文档未同步，
     实现按 `docs/04` 做了 proxy，且 proxy 只支持 OpenAI 一种协议、**没有任何改 base_url 的代码**；
  3. 业界 5 家主流项目（claude-mem 116k★ / mem0 69k★ / OpenViking 42k★ / TencentDB 31k★ / basic-memory）
     **没有一家靠改 agent 的模型 API 注入**，全部挂宿主生命周期（hook / 插件/provider）。

- **决策**：
  1. **注入主通道 = 挂 agent 自己的生命周期**：
     - DSH：写 `dsh-mnemon-provider-orbital`（首选，mnemon 自带 `./extension-sdk` 与 10 个 provider 范本）
       或薄原生插件（`agent/pre-step` → `decision.messages`）；
     - Hermes / pi / WorkBuddy：各按 ADR-025 已实测的机制（hook / 扩展 / MEMORY.md）；
  2. **MCP 保留为写入与深查主力**（10 工具已实现，不动）；
  3. **proxy 降级为"高级用户可选"**，默认关闭；保留 ADR-024 的直连兜底设计；
  4. **注入必须可观测**：每轮记录"注入了多少条/多少字符/耗时/是否 degraded"，状态页可见；
  5. **注入失败必须显式降级**（返回 `degraded` 标记），不许返回空串假装"没有相关记忆"
     （依据：TencentDB-Agent-Memory issue #1133，网关故障导致 10 天记忆静默消失）。

- **被否方案**：

  | 被否做法 | 为什么不行 |
  |---|---|
  | 继续投 proxy（改 agent 的 base_url） | 业界零采用；ADR-024 自己写了会丢 agent 官方模型/积分；单点故障 |
  | 只做 MCP，不做注入 | 等于把"记忆是否生效"押在模型自觉性上（OpenViking 官方原话明确反对） |
  | 补装官方 `dsh-hooks-claude-code` 桥 | 本机未装、其 peer `dsh-hook-protocol` 也缺失；`configPath` 进程级只读一次，改配置要重启 |
  | 给每个 agent 建独立 store | REJECTED-IDEAS #45 已实测否定：会拆散跨 agent 记忆 |

- **不许回退的理由**：如果继续把注入押在 proxy 上，就等于**要求用户把每个 agent 的模型端点都指到我们**，
  这是把接入成本转嫁给用户的模型配置（ADR-025 已论证）；而 hook/provider 路线**不改 API、不丢积分、不是单点故障**。
  回退 = 回到"装完看起来能用、实际什么都不注入"的假绿状态，这正是本次审计要终结的形态。

- **判据**（每条都要本轮实测）：
  - DSH 会话存档里出现 `source.kind="orbital"` 的注入消息；
  - 停掉 mnemon 的本地文件后，DSH 仍能说出 Orbital 里的记忆；
  - 状态页显示"最近一轮注入：N 条 / M 字符 / 耗时 / degraded"。

## ADR-053 多 agent 注入 = 四根独立"管子"，统一契约 + 一键接入

- **状态**：已采纳（2026-11-14；产品化方案见 `docs/32`）
- **背景**：用户要求"装上即用、一键连接、4 agent 全覆盖、记忆共享"。三路源码级调研确认：
  4 个 agent 的自动注入通道**各不相同**，且 MCP 管不了注入：

  | agent | 注入通道 | 硬上限 | 时机 |
  |---|---|---|---|
  | DSH | 插件/provider（`agent/pre-step` → `decision.messages`） | 12,000 字符 | 每轮 |
  | Hermes | shell hook `pre_llm_call` | 无（>10k spill） | 每轮 |
  | pi | 扩展 `before_agent_start`（改 `sections`） | 无 | 每 run |
  | WorkBuddy | MEMORY.md 受控区块 | **4,000 字符** | 每 run |

- **决策**：
  1. **统一契约**：四个适配器都调 `GET 127.0.0.1:8799/recall?q=&agent=<自身>&limit=N`，不各自连库；
  2. **各写薄适配器**，不追求"一套代码通吃"；
  3. **预算按字符算**（不按条数），超限逐级整项丢弃；
  4. **共享靠 `scope=shared`**：默认 private，用户在 GUI 手动「提升为共享」；注入优先召回 shared；
  5. **一键接入 = 探测 → 写 MCP → 部署适配器 → 自检 → 状态表**；
  6. **必须可观测**：每次注入记 `source/chars/hits`，0 条要区分 `no-hits` / `degraded` / `off`。

- **被否方案**：

  | 被否做法 | 为什么不行 |
  |---|---|
  | 只用 MCP，不写注入适配器 | 无法自动注入（OpenViking 官方原话明确反对） |
  | 继续用 proxy 改 base_url | 业界零采用；丢官方模型/积分；单点故障 |
  | 写一个通用注入器通吃四家 | 四家方言不同（hook 协议/扩展 API/文件格式），通吃必然哪家都不对 |
  | 记忆全文写进 WorkBuddy MEMORY.md | 4,000 字符上限，与用户自己的 6,619 字符争空间，必然截断 |
  | 让 WorkBuddy 走 hook | 桌面版不支持 hooks（asar 内 `hooksConfig`/`runHook` 等 0 命中） |

- **不许回退的理由**：这是唯一"不改 agent 模型配置、不丢用户内容、四家都能覆盖"的路径。
  回退到"只做 MCP"= 回到本次审计前的状态（用户看到的"外挂库"）。

- **判据**：四个 agent 各自"新会话能复述 Orbital 注入内容"实测 + 状态页按 agent 分组的注入统计。

## ADR-054 托盘面板**不参与窗口状态持久化**；定位一律用物理像素，失焦隐藏带 400ms 布防

- **状态**：已采纳（2026-11-16；T-M10-46 实现，0.94.8）

- **背景**：T-M10-38~45 五轮修补后，用户仍反馈"面板只显示一半 / 底部被遮挡 / 弹窗收不回"。
  真机取证（2880×1800、缩放 **175%**）后确认，前几轮的修改有**三处从未真正生效**：
  1. `tauri-plugin-window-state` 把 `tray-panel` 写进 `%APPDATA%\com.orbital.pro\.window-state.json`
     （实测 `560×735 @ (44,44)`），启动时恢复 ⇒ 代码里的 `inner_size(320,520)`/`set_position(…)` 全被覆盖；
  2. `inner_size` 是**逻辑**像素、`Monitor::work_area()` 是**物理**像素，混算 ⇒ 底部溢出屏幕 131px；
  3. 从**溢出区**右键时，溢出面板收起动画把焦点还给主窗 ⇒ 面板刚 `show()` 就收到 `Focused(false)`
     ⇒ 立刻 hide（"闪一下就没"）。

- **决策**：
  1. 窗口状态插件加 `.with_denylist(&["tray-panel"])` —— 面板是**临时窗口**，永远不该有"上次位置/尺寸"；
  2. `position_panel` 全程物理像素（`Rect` 的 `Logical` 分支乘 `scale_factor`），并显式 `set_size(PhysicalSize)`；
  3. 失焦隐藏用 `PANEL_ARMED` 原子标志：每次 show 先撤防 **400ms** 再布防；
  4. 面板逻辑尺寸定为 **320×300**（内容实测 ~257 逻辑高，留呼吸；`overflow-y:auto` 兜底）。

- **被否方案**：

  | 被否做法 | 为什么不行 |
  |---|---|
  | 让 window-state 继续管面板（原实现） | 面板位置必须跟**托盘图标**走；恢复"上次位置"等于每次右键都可能出现在错误的地方 |
  | 保留逻辑单位、把 `work_area` 反算成逻辑 | 转换链更长、更易错；`TrayIconEvent::rect` 官方给的就是物理像素，顺势用物理最稳 |
  | 干脆删掉 window-state 插件 | 主窗大小/位置记忆是用户价值（"关闭=隐藏到托盘"依赖它） |
  | 只用 `Focused(false)` 不设布防标志 | 第二次 show（复用窗口）仍会被瞬时失焦误关；实测"闪一下就没"可复现 |
  | 把面板高度改成"内容自适应"（ResizeObserver + set_size） | 当前 4 个 agent 固定，300 逻辑已够；动态 resize 需同时保持"底边贴图标"，引入的复杂度高于收益 |

- **不许回退的理由**：
  这三处是**互相掩盖**的。只修 1，面板还是会因单位混算溢出屏幕；只修 2，window-state 仍会把尺寸改回旧值；
  只修 3，溢出区右键仍会闪没。任何一处被回退，都会让另外两处的修复在用户眼里"看起来没生效"，
  进而诱发下一轮"再改一次高度/位置"的无效循环（T-M10-43~45 就是这样连做三轮）。

- **判据**：
  - `.window-state.json` 退出后**只剩 `main`**，无 `tray-panel`；
  - 面板外框 584×539 = 内容 560×525（320×300 @175%），底部 1632 < 工作区 1716；
  - 溢出区右键后窗口列表存在面板且 `focused=true`（不再闪没）；
  - × / Esc / 点别处 三路都能让 `IsWindowVisible = False`。

## ADR-055 端口被占时**自动顺延**（不持久化）；界面与诊断一律以运行态实际端口为准

- **状态**：已采纳（2026-11-16；T-M10-47 实现，0.94.9）

- **背景**：本机 `xray.exe`（代理软件）把 **8791** 当出口长期占用（`0.0.0.0:8791` Bound + ESTABLISHED），
  core 子进程 `bind` 直接 `os error 10013`（WSAEACCES）→ exit 2 → watchdog 重启 3 次后放弃
  ⇒ 界面永久"进程 2/3"。而 `launcher.rs` 的文件头早就写着"冲突时由启动器顺延"——
  **注释写了、代码没写**（`wait_port_free` 的返回值没人检查），与前几轮托盘问题的模式完全一样。

  同时发现第二处假信号：状态页"端口一览"里 8790 长期显示"被其他服务占用（应为 proxy）"，
  实际 proxy 一切正常——`port_probes` 只认 `/health` 里的 `"role"`，而 proxy 返回的是 `"service"`。

- **决策**：
  1. 新增 `pick_free_port(preferred, skip)`：从首选起扫 20 个端口，跳过另一角色已占的；
     `start()` 与 watchdog 重启都先顺延；
  2. 顺延**不持久化**（不写 env、不写 `proxy.conf.json`），只在 `launcher-events.ndjson` 记 `port_shift`；
  3. 新增 `actual_port(role, fallback)`：**运行态（`launcher.ndjson`）→ 环境变量 → 默认**，
     界面进程数、端口一览、首启引导、诊断导出全部改用实际端口；
  4. 新增 `served_role(body)`：同时识别 core 的 `role` 与 proxy 的 `service`；
  5. recall 端点（8799）**本轮不顺延**——它牵连 proxy 的 `ORBITAL_CORE_URL` 传递约定，属独立任务。

- **被否方案**：

  | 被否做法 | 为什么不行 |
  |---|---|
  | 顺延后写回环境变量 / `proxy.conf.json` | 临时值被写死成"新默认"，换机器/换时机口径不一致；且写配置文件需要额外的并发与回滚处理 |
  | 端口被占就报错退出、让用户手动改配置 | 用户不知道是谁占的（本机是 xray），也看不懂 10013；"能自愈"比"能报错"对普通用户更重要 |
  | 把 proxy 也算成 `role`（改 proxy 的 health 输出） | 改的是**对外接口**（proxy health 已被诊断脚本消费），改判据成本更低、风险更小 |
  | recall 也一起顺延 | proxy 需要知道 recall 地址（`ORBITAL_CORE_URL`），顺延要同步改 proxy 启动 env + 配置契约，超出本轮范围 |

- **不许回退的理由**：
  8791 被第三方软件占用是**无法预防的外部事实**（本机 xray 随机选出口端口）。
  回退到"只等 3 秒再绑"会让"重启一次就 2/3"随机复发，而用户看到的只是"记忆中枢坏了"，
  根本无从排查。顺延是唯一能让普通用户"什么都不用做"的形态。

- **判据**：
  - 独占占用 8791 后启动：日志 `want=8791 actual=8792`，`launcher.ndjson` core=8792；
  - 界面侧栏 3/3、一键体检"三进程健康 3 个进程"；
  - 端口一览三条全"符合端口表"（改前 8790 那条是假异常）。
